PK가 `(DOC_MNG_NO, DOC_VRS_SNO)`이고 `DOC_VRS_SNO`가 항상 1이므로 두 번째 활성행은 **PK 위반으로 저장 자체가 안 된다**. 즉 "버전 전환을 잠금·원자 갱신으로 처리한다"는 요구는 **전환 로직이 없어 적용 대상이 아니다**. ② **정작 구조적 위험은 `BCOSTM`에 있다**(원 기술에 언급 없음) — `Bcostm.java:28` 주석이 다중 버전을 전제하고 `CostService.createCost:94`가 `getNextSnoValue`로 일련번호를 늘려 새 행을 만드는데 `CostDto.java:216`이 `.lstYn("Y")`로만 저장하고 이전 행을 내리지 않는다. 세 Repository의 `.distinct()` 우회 주석("버전 전환 중 `lstYn='Y'` 중복 행으로 팬아웃")이 지목하는 것이 이것이다. `.distinct()`는 행 수만 줄일 뿐 **어느 버전이 채택되는지는 정하지 않아** 조인이 가져오는 `abusNm`/`cttNm`이 비결정적일 수 있다. ③ **Phase 0 진단 실행 결과(2026-08-08, 로컬 DB)**: 중복 활성 키가 **5개 테이블 전부 0건**이다. 나아가 `BCOSTM`은 전체 22행 / 고유 키 22개 / `MAX(BG_SNO)=1`, `BPROJM`은 26행 / 26키 / `MAX(SNO)=1`로 **다중 버전 경로가 한 번도 실행된 적이 없다**(다중 버전 키 0건) — `createCost`가 항상 빈 `costBgNo`로 호출돼 새 번호를 채번하기 때문으로 보인다. 집행 문서 3종은 로컬 데이터가 0건이라 이 진단으로 판정되지 않지만 ①의 구조적 결론이 그대로다. **한계**: 로컬은 22~26행 규모 개발 데이터셋이라 dev/prod 재확인이 필요하다. 다만 `MAX(SNO)=1`은 데이터 규모와 무관한 구조적 신호다. **결론**: 중복 정리·원자적 전환(계획 Phase 1-A)은 **착수 근거가 없고**, 남는 것은 코드가 전제하는 불변식을 DB가 강제하게 하는 스키마 방어(Phase 1-B)뿐이라 🟠 High 근거가 사라졌다. ④ **Phase 1-B(a) 통합 테스트 완료**(2026-08-08, `it_backend` `7c102134`): `ExecutionDocumentActiveVersionIt` 4건으로 전제를 실측 고정했다. 영속성 컨텍스트를 비운 뒤 다시 persist해 JPA의 `EntityExistsException` 단축 경로가 아니라 실제 INSERT가 DB 제약에 걸리게 하고, 단언은 예외 종류가 아니라 **`ORA-00001`을 직접 확인**한다(종류만 보면 NOT NULL 누락 같은 다른 이유로 실패해도 통과한다). 실행 로그에서 세 테이블 각각 `PK_TPRMPP_BD…`·`BC…`·`BP…`에서 `ORA-00001`이 난 것을 확인했다. **네 번째 케이스가 반대편을 남긴다** — `docVrsSno`만 다르면 같은 문서에 활성행이 둘 생긴다. DB가 막는 것은 "같은 버전의 중복"이지 "활성행의 유일성"이 아니며, 버전 기능이 실제로 추가되는 날 이 구멍이 열린다. **잔여: Phase 1-B(b) 함수 기반 UNIQUE 인덱스** — DB 스키마 변경이라 별도 승인과 DBA 인계 노트가 따른다. 지금은 데이터·코드 양쪽에서 위험이 실현되지 않아 급하지 않다. |
