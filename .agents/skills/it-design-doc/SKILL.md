# IT Portal 분석/설계서 작성

## 핵심 계약

Git 이력·PRD·설계 문서에서 확인한 사실만으로 `template.md` 양식의 공공기관 공문서 스타일 분석/설계서를 만든다. 확인되지 않은 요청자 정보·일정·영향도는 지어내지 않고 `(미기재)`·`(예정)`으로 표시한다.

- 문체: 명사형 종결("~함", "~임", "~개선"), 존칭 없음, 날짜는 `'YY.MM.DD(요일)`, 본문 날짜는 `YYYY-MM-DD`.
- 형식: 본문은 **표 셀 또는 목록 항목**으로만 쓴다. 문단(줄글)을 두지 않는다. 한 셀·한 항목은 명사구 40자 안팎이며 넘치면 `·`로 나열하거나 행을 나눈다. 한 항목에 두 문장 이상 쓰지 않는다.
- 강조: 목록 항목의 첫 토큰과 표의 구분 열은 굵게 쓴다 — `**요건 1.**`, `**(배경)**`, `**(개요 도식)**`, `**현행**`, `**TC-01**`, `**'26.09.14(월)**`. 그 밖의 본문에는 굵게를 쓰지 않아 키워드만 눈에 띄게 한다.
- 절 구성: 템플릿의 절만 만든다. `[붙임]`·참고 문서 목록·수집 결과 경로 절을 추가하지 않는다. 근거 문서는 "개발 요건 / 관련 화면"의 요청 경위 열과 "요건 목록"의 출처 열에만 적는다.
- 산출물: `docs/design-docs/{작성일 YYYY-MM-DD}-analysis-design-since-{시작일 YYMMDD}.md`. 사용자가 경로나 파일명을 지정하면 그것을 따른다.
- 저장소 상태를 바꾸지 않는다. 커밋·스테이징·되돌리기를 하지 않는다.

## 입력 해석

| 입력 | 해석 |
| --- | --- |
| `YYMMDD일 이후`, `9.14일 00시부터` | 시작 시각. 날짜만 있으면 그날 00:00. 연도가 없으면 오늘 기준 가장 최근 과거 연도 |
| `현재까지`, 종료일 없음 | 종료 시각 = 지금. 미커밋 작업도 포함하고 `(미커밋)`으로 표시 |
| 요청부서·요청자·문서번호 | 사용자 지시 → 구간 내 PRD(`prds/ing`, `prds/done`)의 기본정보 표 → `(미기재)` 순서로 채움 |
| 작성자명 | 사용자 지시 → `git config user.name` |
| PRD·과제 ID 지정 | 구간 대신 그 문서가 가리키는 커밋·파일을 범위로 삼는다 |

## 워크플로우

1. 루트 `CLAUDE.md`를 읽는다. 저장소 4개가 독립 Git이므로 수집도 4개를 모두 돈다.
2. 수집 스크립트를 루트에서 실행한다. 출력은 `tmp/`(미추적)에 둔다.

```powershell
./.agents/skills/it-design-doc/scripts/collect-changes.ps1 -Since 260914 -Output tmp/design-doc/changes-260914.md
```

   `-Until 260915`로 종료일을 줄 수 있다(그날 23:59:59까지). 결과 Markdown은 저장소별 커밋·파일, 분류별 집계, 일자별 활동, 참고 문서 후보를 담는다.
3. 수집 결과의 "참고 문서 후보"를 모두 읽는다. PRD는 요청자 정보·배경·개발 요건·관련 화면의 1차 출처, `docs/superpowers/specs`·`plans`는 설계 방향·영향도·제외 범위의 출처, `TASK.md`는 구간 내 등록된 후속 과제의 출처다.
4. 커밋 제목과 참고 문서를 대조해 **요건 단위**(사용자 관점 기능 1건)로 묶는다. PRD 요구사항 번호가 있으면 그 번호를 쓰고, PRD에 없는 작업(결함 수정·설계 문서 기반 기능)은 자체 개선 요건으로 추가한다. 순수 리팩터링·의존성 상향·문서·도구는 "기타" 요건 1건으로 합친다. 하나의 커밋이 여러 요건에 걸치면 파일 단위로 나눈다. "기능 개선"처럼 제목이 모호한 스쿼시 커밋은 파일 목록·diff·i18n 키·테스트 `describe`를 읽어 요건을 역추적한다. 구간 안에서 추가 후 되돌린 변경은 순변경 기준으로 한 요건에 적고 경위를 남긴다.
5. 관련 화면은 변경된 `app/pages/**` 경로로 잡고 화면명은 해당 페이지의 i18n 제목이나 PRD 표기를 쓴다. 페이지 변경 없이 컴포넌트·composable만 바뀌었으면 그 파일을 import하는 곳을 `grep`으로 찾고, 결과가 또 컴포넌트면 페이지에 닿을 때까지 반복 추적한다(예: `PdfViewer` → `ApplicationViewerDialog` → `/approval/list`).
6. 요건을 사용자 관점 **영역 3~5개**로 묶어 ①②③ 번호를 매긴다(개요 도식과 요건 목록의 영역 열에 쓴다). 영역명은 화면·업무 단위의 쉬운 말로 짓는다.
7. `template.md`를 채운다. 섹션별 규칙은 아래 표를 따른다.
8. 검증 체크리스트를 통과시킨 뒤 산출물 경로와 `(미기재)`·`(예정)`으로 남긴 항목을 사용자에게 보고한다.

## 섹션별 작성 규칙

| 섹션 | 규칙 |
| --- | --- |
| 배경 및 개요 | `(배경)`·`(요청)`·`(수집 구간)` 각 한 줄. `(개요 도식)`은 아래 "개요 도식" 규칙. `(요건 목록)` 표는 요건당 한 행, 한 줄 요약은 명사구 40자 이내, 영역 열은 도식의 ①②③ 번호 |
| 개요 도식 | eli5 원칙: 그림 크게, 말은 적게. 요건을 사용자 관점 **영역 3~5개**로 묶고(예: 예산 목록·조회 / 예산 작성 폼 / 결재·신청서 PDF / 공통 기반) 영역당 키워드 2~4개만 쓴다. 파일명·클래스명·API 경로·전문용어를 넣지 않는다. 마지막 `[효과]` 줄은 사용자가 체감할 결과 키워드 3개. ```flow 블록에 템플릿 형태(요청 상자 → 영역 가지 → 효과 상자)를 유지한다 |
| 개발 요건 / 관련 화면 | 요건당 한 행. 요청 경위는 PRD의 요청자·경로(유선·Q&A 등), 없으면 "자체 개선" |
| 설계 방향 | 요건마다 `**요건 N. 요건명**` 항목 + `현행/변경/영향도` 3행 표. 각 행은 한 줄(넘치면 `·`로 나열). `·` 항목이 6개를 넘으면 `**변경(백엔드)**`·`**변경(프론트)**`처럼 행을 나눈다. 영향도는 변경 파일을 import·호출하는 화면과 API 소비처를 근거로 적고 추정이면 "추정"을 붙인다 |
| 화면 | `app/pages` 신규 파일=신설, 기존 파일 또는 사용 컴포넌트 변경=변경. 없으면 해당없음 |
| DB | `it_database/migrations/V*` 신규 스크립트만 신설·변경으로 기록. 엔티티 변경만 있고 스크립트가 없으면 "해당없음"에 사유를 덧붙인다 |
| 수정대상 | EAI는 이 프로젝트에 인터페이스 변경 흔적(`eai`, `interface`, 배치 스케줄러)이 없으면 해당없음. 기타에는 문서·PRD·`versions.lock`·의존성 파일 |
| 변경대상 파일 목록 | 수집 결과의 `[신설]/[변경]/[삭제]/[이동]`을 그대로 사용. 수집 스크립트는 구간 안에서 신설된 뒤 옮겨진 파일을 새 경로 `[신설]` 한 건으로 합치므로 `[이동]`은 구간 이전부터 있던 파일의 이동만 뜻한다. `[이동]`은 현재 경로만 적고 수정대상 표에서는 변경으로 합산. 한 파일이 여러 요건에 걸치면 주 요건에 한 번만 적고 "(요건 N 공유)"를 붙인다. 테스트 파일은 개수만 |
| 테스트 시나리오 | 변경된 테스트 파일에서 도출. `tests/unit`=Vitest, `src/test/java`=Jacoco(JUnit), `tests/e2e`=E2E. 요건마다 사용자 시나리오를 최소 1건 추가. 총 건수는 표 행 수와 일치 |
| 진행경과 및 계획 | 한 줄 = 한 사건: `**'YY.MM.DD(요일)** 요건 N 단계 · 키워드 (해시)`. 단계는 설계·구현·검증·수정 중 하나. 같은 날 같은 요건이라도 단계가 다르면 줄을 나눈다. `versions.lock` 갱신 커밋은 검증 완료 근거. 개발계·운영계 적용일은 사용자가 주지 않으면 `**'YY.MM.--(예정)** 개발계 적용`처럼 일자를 `--`로 비운다 |

템플릿의 `{…}` 자리표시자를 산출물에 남기지 않는다. 표의 값 칸에는 값만 두고 출처(`git config`, PRD 경로)는 표 아래 `※` 주석 한 줄로 뺀다.

## 검증 체크리스트

- 요청자 정보 4항목·작성자 정보 2항목이 모두 채워졌거나 `(미기재)`로 표시됐다.
- 변경대상 파일 목록의 모든 경로가 현재 워킹트리에 존재하거나 `[삭제]`로 표시됐다. `Test-Path -LiteralPath`를 쓴다(`[id].vue` 같은 대괄호 경로는 일반 `Test-Path`가 와일드카드로 해석해 거짓 누락을 낸다).
- 테스트 시나리오 제목의 "총 N건"이 표 행 수와 같다.
- 수정대상 표의 신설·변경·삭제 합계가 수집 결과의 저장소별 파일 수와 일치한다(테스트·문서 포함 여부를 비고에 명시).
- 화면·DB 절에 근거 없는 "신설"이 없다. DB 절이 해당없음이면 `it_database` 커밋 0건인지 확인했다.
- 진행경과의 날짜가 모두 수집 구간 안이며 요일이 맞다.
- 줄글이 없다: 코드 블록(```) 안과 빈 줄을 제외하고 `-`·`|`·`#`·`※`·공백으로 시작하지 않는 줄은 "해당없음" 한 줄뿐이다. 확인: `awk '/^```/{c=!c;next} !c && !/^(\s*$|\s*[-|#※])/' 파일`
- `[붙임]` 절이 없다. 개요 도식 안에 파일명·클래스명·API 경로가 없다.

## 흔한 실수

- 커밋 제목만 보고 요건을 나눈다 → "기능 개선" 커밋은 반드시 파일 목록으로 판단한다.
- PRD 요구사항과 커밋을 1:1로 가정한다 → PRD에 있으나 구간에 커밋이 없는 요건은 "미착수"로 표에 남긴다.
- 테스트 파일 이름을 그대로 시나리오명으로 쓴다 → 점검 포인트는 `describe`/`@DisplayName`의 검증 의도로 적는다.
- 스냅샷 `.snap`, `api.d.ts` 같은 생성 파일을 설계 대상으로 설명한다 → 기타·생성물로 표시하고 원인 변경(DTO·OpenAPI)을 설계 항목으로 쓴다.
- 설계 방향을 문단으로 풀어 쓴다 → 현행/변경/영향도 3행 표. 설명이 길면 셀 안에서 `·`로 끊는다.
- 개요 도식에 요건 20개를 그대로 나열한다 → 영역 3~5개로 묶고 요건은 아래 표에 둔다.
- 요건 번호를 `**요건 1.**`처럼 굵게 하지 않거나 본문 곳곳을 굵게 한다 → 강조는 첫 토큰과 구분 열에만.

## 후속

산출물을 보고·인쇄용 PDF로 만들 때는 `it-design-doc-pdf`를 사용한다. 사용자가 Markdown을 손본 뒤 변환하는 흐름을 전제하므로 이 스킬은 PDF를 직접 만들지 않는다.
