# 정통법(Detailed FP) 기준 기능점수 산정 가이드

본 워크플로우는 소프트웨어 사업 대가산정(KOSA 가이드)의 핵심인 정통법 기능점수(Detailed FP) 산정을 위한 구체적인 절차를 안내합니다. 간이법과 달리 각 기능의 상세 구성 요소(필드 수, 연관 테이블 수)를 세밀하게 분석하여 정확한 규모를 산출합니다.

## 대상
- C:\it\it_frontend
- C:\it\it_backend

## 용어 정의 체계

정통법에서는 각 데이터/트랜잭션 기능의 복잡도를 판단하기 위해 다음 기준값을 사용합니다.

- **DET (Data Element Type, 데이터 요소 유형):**
  - 화면에 보이는 입력/출력 필드의 수 (예: 이름, 부서명, 결재상태 등)
  - 에러 메시지, 시스템 자동 생성 필드 등을 포함
- **RET (Record Element Type, 레코드 요소 유형):**
  - ILF/EIF 내에 논리적인 부분 그룹(서브 테이블 구조)의 수
  - 예: '부서 정보' 안에 '팀 정보'가 포함되어 있다면 RET는 2개
- **FTR (File Type Referenced, 참조 파일 유형):**
  - 트랜잭션 수행 시 읽거나 쓰는 ILF나 EIF의 수
  - 예: '예산 정보' 등록 시 '부서 정보'에서 부서 코드를 읽어온다면 FTR은 2개(예산, 부서)

## 단계별 산정 워크플로우

### Step 1: 산정 범위 및 경계 설정
- 어떤 시스템이나 애플리케이션의 개발 범위를 측정하는지 정의합니다.
- 시스템 경계(System Boundary)를 그려, 내부 영역(ILF 유지관리)과 외부 영역(EIF 참조)을 명확히 구분합니다.

### Step 2: 데이터 기능 산정 (ILF, EIF)
시스템 논리 데이터 모델(ERD 등)을 기반으로 산정합니다.

1. **내부논리파일 (ILF - Internal Logical File) 식별**
   - 우리 시스템 경계 내에서 유지, 관리(C/R/U/D)되는 데이터 베이스 테이블 군
2. **외부인터페이스파일 (EIF - External Interface File) 식별**
   - 우리 시스템 경계 밖에서 관리되나, 참조용으로만 읽어오는 데이터 (쓰기 불가)
3. **복잡도(Low/Average/High) 판단 및 점수 부여**
   - 식별된 ILF/EIF에 대해 해당 파일의 RET와 DET 개수를 파악하여 매트릭스 적용

**[데이터 기능 복잡도 매트릭스 (RET vs DET)]**
| RET \ DET | 1 ~ 19 DET | 20 ~ 50 DET | 51개 이상 DET |
|-----------|------------|-------------|-------------|
| 1개       | Low        | Low         | Average     |
| 2 ~ 5개   | Low        | Average     | High        |
| 6개 이상  | Average    | High        | High        |

**[점수(FP) 부여]**
- **ILF:** Low(7), Average(10), High(15)
- **EIF:** Low(5), Average(7), High(10)

### Step 3: 트랜잭션 기능 산정 (EI, EO, EQ)
제공될 UI(화면), API, 배치 처리 사양서를 기반으로 산정합니다.

1. **기능 유형 식별**
   - **외부입력 (EI):** 시스템 경계 밖의 데이터를 받아 내부파일(ILF)을 갱신하거나, 시스템 상태를 변경하는 기능 (예: 등록, 수정, 삭제)
   - **외부출력 (EO):** 계산, 파생 데이터 생성 작업이 수반되어 밖으로 보여주는 기능 (예: 집계 통계, 리포트 출력)
   - **외부조회 (EQ):** 계산이나 파생 데이터 생성 없이 단순히 ILF/EIF 데이터를 조회하여 보여주는 기능 (예: 목록 조회, 상세 조회)
2. **복잡도(Low/Average/High) 판단 및 점수 부여**
   - 기능별로 참조하는 파일(FTR) 개수와 처리되는 항목(DET) 개수를 세어 매트릭스 적용

**[외부입력(EI) 복잡도 매트릭스 (FTR vs DET)]**
| FTR \ DET | 1 ~ 4 DET | 5 ~ 15 DET | 16개 이상 DET |
|-----------|-----------|------------|-------------|
| 0 ~ 1개   | Low       | Low        | Average     |
| 2개       | Low       | Average    | High        |
| 3개 이상  | Average   | High       | High        |

*EI 점수:* Low(3), Average(4), High(6)

**[외부출력(EO) / 외부조회(EQ) 복잡도 매트릭스 (FTR vs DET)]**
| FTR \ DET | 1 ~ 5 DET | 6 ~ 19 DET | 20개 이상 DET |
|-----------|-----------|------------|-------------|
| 0 ~ 1개   | Low       | Low        | Average     |
| 2 ~ 3개   | Low       | Average    | High        |
| 4개 이상  | Average   | High       | High        |

*EO 점수:* Low(4), Average(5), High(7)
*EQ 점수:* Low(3), Average(4), High(6)

### Step 4: 미조정 기능점수(UFP) 합산
- `미조정 기능점수(UFP) = (ILF 총점) + (EIF 총점) + (EI 총점) + (EO 총점) + (EQ 총점)`

### Step 5: 값 조정 인자(VAF) 적용 및 최종 개발비용 산출 (소프트웨어 대가산정 가이드 적용)
1. 기능점수 csv 작성 — **`FP/fp-estimate-YYYY-MM-DD.csv`** (산정 수행일 기준, 날짜별 누적)
    - 세부 업무명 (도메인)
    - 단위프로세스명 (기능명)
    - 단위프로세스설명 (기능설명)
    - FP 유형 (EO, EQ, EI, ILF, ELF 등)
    - RET/FTR
    - DET
    - **변경내용** — 직전 산정본 대비 이 행이 왜 달라졌는지 (예: `응답 DTO 필드 15개 추가로 DET 10→25`)
      - 수치가 그대로면 비워 둡니다. 최초 산정본은 전 행 `최초 산정`.
      - 수치가 바뀌었는데 비어 있으면 생성기가 경고합니다(반대로 변동이 없는데 적혀 있어도 경고).

   CSV는 코드베이스(`it_frontend`/`it_backend`)를 실측해 매 산정 시 새 날짜 파일로 작성합니다.
   과거 산정본을 덮어쓰지 않으므로 날짜 간 규모 변화를 비교할 수 있습니다.
   Step 6 생성기는 **같은 날짜의 CSV만** 입력으로 읽으며, 없으면 오류로 중단합니다.

   ⚠️ 필드에 쉼표(`,`)를 넣지 마십시오. 파서가 단순 split이라 열 개수 검증에서 실패합니다.
2. **보정계수 산출** (각 항목별 난이도 계수표 참조)
   - 규모 보정계수
   - 애플리케이션 유형 보정계수
   - 언어 보정계수
   - 품질 및 특성 보정계수
   - 다중 사이트 보정계수 (해당 시)
3. **보정 후 기능점수 계산**
   - `보정 후 기능점수 = 미조정 기능점수(UFP) × 규모 보정 × 타입 보정 × 언어 보정 × 품질 보정 (등)`
4. **최종 금액 산정 (공공사업 기준)**
   - `개발원가 = 보정 후 기능점수 × FP 당 단가`
   - FP 당 단가는 **보정 전 개발원가 단가 600,000원/FP** 기준 (`generate-report.mjs`의 `CONFIG.unitPrice`)
   - + **이윤 20%** 추가 후 **부가세 10%** 포함 처리
   - `최종 금액 = 개발원가 × 1.2 × 1.1`

### Step 6: 리포트 생성 (자동화)

본 워크플로우를 수행할 때마다 **동일한 형태의 리포트를 날짜별로** 생성합니다.
리포트는 손으로 작성하지 않고 반드시 생성기를 실행합니다.

```bash
node FP/generate-report.mjs                    # 오늘 날짜로 생성
node FP/generate-report.mjs --date=2026-07-17  # 특정 날짜로 생성
```

- **입력**: `FP/fp-estimate-YYYY-MM-DD.csv` (Step 5-1 산정 명세, 리포트와 **같은 날짜**) + 코드베이스 실측
- **출력**: `FP/reports/fp-estimate-report-YYYY-MM-DD.html` (날짜별 누적, 같은 날 재실행 시 해당 파일만 갱신)
- 해당 날짜의 CSV가 없으면 생성기는 오류로 중단합니다. Step 5-1을 먼저 수행하십시오.
- **직전 산정 대비 변경** 섹션이 자동 생성됩니다. 기준은 해당 날짜보다 **이전인 가장 최근
  `fp-estimate-*.csv`** 이며, 없으면 최초 산정으로 표시됩니다. 비교 키는 `도메인/단위프로세스명`이라
  기능명을 바꾸면 삭제+추가로 잡히므로 `변경내용` 열에 개명 사유를 남기십시오.
- **Markdown 리포트(`fp-estimate-report.md`)는 더 이상 생성하지 않습니다.** HTML 리포트로 대체되었습니다.

**생성기 구조** — 리포트 형태를 바꾸려면 아래 파일을 고칩니다(생성된 리포트를 직접 편집하지 마십시오).

| 파일 | 역할 |
|------|------|
| `FP/generate-report.mjs` | 리포트 진입점 |
| `FP/lib/config.mjs` | **보정계수·FP당 단가·이윤율(`CONFIG`)** 과 금액 산식. 리포트·아티팩트가 공유하므로 단가 교체는 여기 한 곳만 고칩니다 |
| `FP/lib/fp-rules.mjs` | Step 2·3 복잡도 매트릭스와 점수표 |
| `FP/lib/csv.mjs` | `fp-estimate-YYYY-MM-DD.csv` 파싱·검증 |
| `FP/lib/scan.mjs` | 테이블·화면·API 실측 |
| `FP/lib/aggregate.mjs` | 유형별·영역별 집계, UFP 산출 |
| `FP/lib/diff.mjs` | 직전 산정본 대비 추가·삭제·수정 및 UFP 증감 비교 |
| `FP/lib/render.mjs` | 리포트 레이아웃(HTML/CSS) |

**설계 원칙**

- **수치는 CSV를 신뢰하지 않고 재계산**합니다. 생성기가 `RET/FTR`·`DET`에 Step 2·3 매트릭스를
  다시 적용해 복잡도·점수를 산출하므로, 같은 입력이면 항상 같은 결과가 나옵니다.
  CSV의 `복잡도`/`FP점수` 열과 어긋나면 콘솔 경고와 리포트 본문에 불일치 목록이 표시됩니다.
- **규모 지표(테이블·화면·컨트롤러·엔드포인트)는 하드코딩하지 않고** 매 실행 시 소스에서 계수합니다.
- **테이블 수의 SoT는 `it_database/ITPOWN_DDL_live.sql`의 CREATE TABLE**(`FLYWAY_SCHEMA_HISTORY` 제외)입니다.
  JPA `@Table`만 세면 엔티티 없는 잔여 테이블이 누락되므로, 물리 테이블과 엔티티 매핑을 각각 세고
  차이를 리포트·콘솔에 고아 목록으로 노출합니다. 덤프가 없으면 엔티티 기준으로 폴백합니다.
  덤프가 낡으면 `unmapped` 경고가 뜨므로 스키마 변경 후에는 덤프를 갱신하십시오.
- 매트릭스를 수정할 때는 본 문서(Step 2·3)와 `lib/fp-rules.mjs`를 **함께** 고칩니다.

### Step 7: 보고용 아티팩트 생성 (선택)

경영진·발주처 보고가 필요할 때 실행합니다. Step 6 리포트가 "산정이 정확한가"를 검증하는
실무 문서라면, 아티팩트는 "규모와 금액이 얼마인가"에 결론부터 답하는 보고 문서입니다.

```bash
node FP/build-artifact.mjs                    # 가장 최신 산정본 기준
node FP/build-artifact.mjs --date=2026-08-09  # 특정 산정본 기준
```

- **입력**: `FP/fp-estimate-*.csv` 전체(추이용) + 지정 날짜 CSV(본문용) + 코드베이스 실측
- **출력**: `FP/artifact/fp-artifact-YYYY-MM-DD.html`
- 산정 로직을 새로 만들지 않고 `lib/`의 파서·집계기·실측기를 그대로 재사용하므로,
  같은 산정본이면 리포트와 아티팩트의 수치가 항상 일치합니다.
- 279행 전수 명세는 담지 않습니다. 그 역할은 Step 6 리포트가 맡습니다.
- 물리 규모(테이블·화면·엔드포인트)는 **생성 시점** 코드베이스 실측이라 산정 기준일의
  스냅샷과 다를 수 있으며, 아티팩트 본문에 그 사실을 명시합니다.
- 생성 후 Claude Code의 Artifact 도구로 게시하면 공유 가능한 웹 페이지가 됩니다.

| 파일 | 역할 |
|------|------|
| `FP/build-artifact.mjs` | 진입점. 산정본 선택·추이 조립·출력 |
| `FP/lib/artifact-render.mjs` | 보고 페이지 레이아웃(HTML/CSS/인라인 SVG 차트) |

⚠️ 차트는 외부 라이브러리 없이 인라인 SVG로 그립니다. 아티팩트 CSP가 CDN·외부 폰트·
원격 이미지를 차단하므로 `<script src>`나 웹폰트 URL을 추가하면 조용히 깨집니다.

## 팁 & 체크리스트
- **DET 카운팅 주의:** 한 화면에 있는 단순 라벨/아이콘은 DET가 아닙니다. 사용자가 직접 입력/선택하거나 의미를 담아 데이터베이스와 교환되는 단위만 카운팅합니다. 페이징 버튼이나 액션 버튼(저장, 조회)은 전체를 하나 또는 두 개(명령어 요소)로 잡습니다.
- **EO vs EQ 구분:** 조회의 결과로 그래프가 그려지거나, 합계/평균 등 내부적인 수학 연산(파생)이 개입하면 EO입니다. 있는 값을 그대로 꺼내 보여주면 EQ입니다.
- **ILF vs EIF 구분:** EIF는 다른 시스템의 DB 테이블, 파일, 또는 OPEN API가 될 수 있습니다. 우리 DB에 저장하지 않는 외부 REST API 실시간 호출 데이터는 EIF 처리와 함께 이 데이터를 보여주는 트랜잭션 규모로 잡습니다.
