# 운영 증거 수집·정책 결정 승인 요청

> 기준일: 2026-08-09
> 대상: `BE-03`, `BE-18`, `BE-23`, `LOG-03`, `LOG-04`
> 범위: 운영 읽기 자료 수집과 정책 결정만 요청하며 DDL·운영 데이터 변경은 수행하지 않는다.

## 1. 요청 요약

현재 `TASK.md`의 DDL 없는 활성 항목은 모두 운영 자료 또는 담당자 결정이 선행돼야 한다. 저장소 안에서 확인 가능한 코드·로컬 로그·운영 가이드는 이미 감사했으나, 운영 배포 이력·AWR·운영 로그·기관 정책은 로컬 저장소에 없다.

다음 두 사항을 승인받으면 항목별 증거를 수집해 판정표를 작성한다.

1. 아래 명시한 운영 원본의 **읽기 전용 수집·검토** 승인
2. `BE-23`과 `LOG-04`에 필요한 **소유팀·정책 결정 요청** 승인

승인만으로 기능 전환·레거시 제거·파일 이전·삭제 작업을 실행하지 않는다. 증거가 기준을 충족하면 변경 계획과 영향 범위를 별도로 제시하고 다시 구현 승인을 받는다.

## 2. 공통 제출 규칙

- 관측 시간은 KST와 시스템 timezone을 함께 기재한다.
- 배포 ID, Git SHA, 배포 시작·완료 시각을 포함해 어느 버전의 자료인지 식별한다.
- AWR SQL text, 로그의 사번·문서번호·토큰·세션ID는 판정에 필요하지 않은 부분을 마스킹한다.
- 비밀번호, JWT, SSO 원본 바이너리, 계약서 원문은 이 저장소나 승인 답변에 첨부하지 않는다.
- 증거는 접근 통제된 운영 저장소의 경로·티켓 번호·리포트 ID로 참조하고, 이 문서에는 요약값과 체크섬만 기록한다.
- 서로 다른 기간의 동시 사용자·API 지연·AWR 값을 결합하지 않는다. 같은 관측 구간 자료만 한 판정에 사용한다.

## 3. 항목별 증거와 판정 기준

### EV-BE03 — Project·Cost 추가 projection 판단

**요청 소유자:** DBA/AWR 담당자 + 백엔드 운영 담당자
**관측 기간:** 동일 릴리스가 안정 운영된 연속 14일 이상

필수 증거:

1. 릴리스 ID·백엔드 Git SHA·배포 완료 시각
2. `GET /api/projects`, `GET /api/projects/{prjMngNo}`, `GET /api/cost`, `GET /api/cost/{itMngcNo}`별 일 호출 수, p50·p95·p99, 최대 지연, 5xx 비율
3. 위 경로가 실행한 Project/Cost 검색 SQL의 AWR `SQL_ID`, plan hash, executions, elapsed time, CPU time, buffer gets, disk reads, rows processed
4. 일자별 상위 SQL 목록에서 같은 SQL이 반복 병목인지 확인할 수 있는 순위 또는 DB time 비중
5. 관측 중 장애·배치·통계정보 갱신 등 비정상 구간과 제외 사유

판정:

- 호출량이 의미 있게 존재하고 p95 지연 또는 AWR DB time·buffer gets가 반복 병목으로 확인된 API만 추가 경량 계약·projection 설계 대상으로 승인한다.
- 호출이 없거나 지연·DB 부하가 낮으면 현 wide 계약을 유지하고 다음 관측일만 정한다.
- UI 응답에 필요한 필드를 삭제하지 않는다. 계약 분리가 필요하면 신규 경량 목록 응답을 먼저 추가하고 기존 응답의 호환 기간을 별도 승인한다.

### EV-BE18 — 구 검토자 API 제거

**요청 소유자:** 배포 관리자 + 애플리케이션 로그 관리자
**관측 기간:** 전역 경로 포함 릴리스 배포 완료 뒤 연속 14일

필수 증거:

1. 전역 `GET /api/reviews/reviewers`가 포함된 운영 릴리스 ID·Git SHA·배포 완료 시각
2. 해당 시각 이후 14일 전체 애플리케이션 로그에서 정확한 WARN 문구 `폐기 예정 검토자 경로가 호출되었습니다` 검색 결과
3. 로그 롤링·수집 누락 구간이 없다는 수집 시스템 상태 또는 누락 구간 목록
4. 결과가 0건이면 검색 조건·기간·대상 인스턴스 수가 보이는 리포트 또는 티켓

판정:

- WARN 0건이고 로그 누락도 없을 때만 `GET /api/reviews/{docMngNo}/reviewers`, `ReviewerController.getReviewersLegacy`, 대응 테스트 제거 계획을 승인 요청한다.
- 1건 이상이면 호출 주체를 식별해 전역 경로로 전환한 뒤 14일 관측을 처음부터 다시 시작한다.

### DEC-BE23 — SSO 벤더 자료의 사내 아티팩트 저장소

**요청 소유자:** SSO 운영 담당자 + 사내 아티팩트 저장소 관리자 + 계약/보안 담당자

필수 결정:

1. 저장소 URL과 저장 형식(Nexus raw/Maven, Artifactory 등)
2. 제품명·버전이 식별되는 group/artifact/version 또는 디렉터리 좌표 규칙
3. 업로드 소유팀, 읽기 허용 주체, 쓰기·삭제 승인 주체
4. 공급 계약상 원본 보존기간과 계약 종료 후 처리 방식
5. 공급사 체크섬 또는 서명 검증 방법과 내부 반입 체크섬 기록 위치
6. 장애 대응 시 원본 회수 절차, 접근 불가 시 대체 연락처

판정:

- 여섯 값이 확정되면 벤더 원본을 승인된 저장소로 이전하고 `it_backend/sso/README.md`에는 좌표·소유권·검증 절차만 기록한다.
- 원본 파일이나 자격증명은 Git에 추가하지 않는다.

### EV-LOG03 — 실시간 로그 push 전환

**요청 소유자:** 모니터링/APM 담당자 + DBA/AWR 담당자
**관측 기간:** 대표 업무일의 동일 연속 구간, 임계 지속시간을 포함할 것

필수 증거:

1. 관리자 실시간 로그 화면의 동시 활성 세션 시계열(1분 단위 권장)
2. `GET /api/admin/realtime-logs`의 분당 호출 수, p50·p95·p99, 최대 지연, 4xx·5xx 비율
3. 같은 구간의 애플리케이션 CPU·heap·thread와 DB session/DB time
4. 관련 SQL의 AWR `SQL_ID`, executions, elapsed, CPU, buffer gets, 상위 부하 반복 여부
5. 현재 폴링 간격 분포(3초·5초·10초)와 화면 비활성 시 호출 억제 여부

재개 임계치 중 하나:

- 관리자 동시 활성 세션 20명 이상이 30분 지속
- API p95가 1초를 초과한 상태가 10분 지속
- 관련 SQL이 동일 관측 구간의 AWR 상위 부하에 반복 등장

판정:

- 하나라도 원본 증거로 충족되면 SSE를 우선 후보로 별도 설계한다. 양방향 명령이 필요하다는 별도 요구가 있을 때만 WebSocket을 비교한다.
- 모두 미충족이면 현재 5초 기본 폴링과 3·5·10초 선택 기능을 유지한다.

### DEC-LOG04 — DB 감사로그 보존·아카이브 정책

**요청 소유자:** 정보보호/준법 또는 기록관리 책임자 + DBA 운영 책임자 + 시스템 소유자

필수 결정:

1. 온라인 조회 보존기간
2. 암호화 백업·아카이브 위치와 전체 보존기간
3. 삭제 승인 주체와 이중 승인 필요 여부
4. 백업·삭제 실행 주체와 실패 통보 대상
5. 복구 표본 범위, 복구 점검 주기, 성공 기준, 결과 보관 위치
6. 법규·내부 규정·감사 요구사항의 문서 ID와 예외 승인 절차
7. 법적 보존 중지(legal hold) 또는 사고 조사 시 삭제 중단 절차

판정:

- 일곱 값이 승인되기 전에는 DB 감사로그 삭제·아카이브 자동화를 구현하지 않는다.
- 승인 후에도 먼저 읽기 전용 보존 현황 리포트와 복구 훈련을 만들고, 실제 삭제 작업은 별도 운영 변경 승인으로 분리한다.
- `logback-spring.xml`의 파일 로그 12개월/3GB 설정은 이 DB 감사로그 정책을 대신하지 않는다.

## 4. DDL 대상이라 이번 실행에서 제외한 항목

| ID | 운영 확인 가능 항목 | 제외 이유 |
| --- | --- | --- |
| BE-24 | 운영 데이터의 활성 최신 버전 중복 건수와 버전 기능 사용 여부 | 최종 조치가 함수 기반 UNIQUE 인덱스이므로 DDL 승인 없이는 완료할 수 없다. |
| BRD-02 | 게시판별 건수, 본문 검색 p95, Oracle 실행계획 | 실제 Oracle Text 인덱스·동기화 객체 도입이 DDL이므로 이번 구현 범위에서 제외한다. |

위 두 항목의 읽기 전용 진단까지 함께 수집하려면 승인 답변에 `DDL-DEFERRED 진단 포함`을 명시한다. 진단 결과가 임계치를 넘더라도 DDL은 별도 승인 전 실행하지 않는다.

## 6. 승인 후 수행 순서

1. 자료의 기간·릴리스·인스턴스 완전성과 마스킹 상태를 검증한다.
2. `EV-BE18`처럼 제거 조건이 단순한 항목부터 판정한다.
3. `EV-BE03`과 `EV-LOG03`은 같은 구간의 API·AWR 값을 결합해 병목 여부를 판정한다.
4. `DEC-BE23`·`DEC-LOG04`는 승인된 정책값을 운영 문서와 체크리스트에 먼저 반영한다.
5. 코드 변경이 필요한 항목은 별도 RED/GREEN 계획과 배포·롤백 조건을 제시하고 구현 승인을 다시 받는다.
