# TASK.md 비DDL 과제 순차 처리 설계

## 1. 목표

현재 작업 트리의 `TASK.md`에 남은 활성 과제 중 DDL 변경이 필요하지 않은 모든 항목을 작은 단위부터 순차 처리한다. 코드로 완료할 수 있는 항목은 테스트와 근거를 갖춰 `TASK_DONE.md`로 이관하고, 운영 관측·외부 합의·업무 정책이 없어서 완료할 수 없는 항목은 임의로 닫지 않고 확인 결과와 재개 조건을 활성 항목에 현행화한다.

## 2. 전역 제약

- `it_database/migrations/`, live DDL, 테이블·인덱스·시퀀스 정의를 변경하지 않는다.
- 사용자가 이미 작업 트리에서 제거하거나 정리한 BRD·EAI 행은 사용자 소유 변경으로 보존하고 별도 커밋에 포함하지 않는다.
- `it_backend/graphify-out/`은 기존 비추적 산출물이므로 읽거나 커밋하지 않는다.
- 독립 저장소는 각각 자체 테스트와 커밋을 만들고, 교차 저장소 계약 변경은 백엔드 → 프론트엔드 → 루트 문서 순서로 커밋한다.
- 활성 과제는 구현 완료, 현재 동작 수용(`Accepted`), 또는 외부 조건 미충족이 객관적으로 확인된 경우에만 상태를 바꾼다.
- 외부 조건 미충족은 완료가 아니다. 해당 행은 `TASK.md`에 남기고 확인 일자·증거·다음 확인 방법을 기록한다.
- 기능·버그·리팩터링은 RED 테스트를 먼저 만들고 실패 원인을 확인한 뒤 최소 구현으로 통과시킨다.

### 3.2 DDL 필요로 제외

| ID | 제외 근거 |
| --- | --- |
| BE-24 | 활성 최신 버전 단일성의 최종 해소가 함수 기반 UNIQUE 인덱스 추가이며 스키마 변경이 필요함 |

BE-25는 새 PK·UNIQUE를 만들지 않고 이미 존재하는 물리 복합 PK에 ORM을 맞추는 경로만 허용하므로 실행 대상에 포함한다.

## 4. 접근 방식 비교

### 선택: 구현 + 정직한 차단 상태

실행 가능한 과제는 완료하고, 외부 증거가 없는 과제는 활성 상태로 유지한다. 완료 수를 부풀리지 않으면서 모든 비DDL 항목에 실제 진척과 재현 가능한 다음 행동을 남긴다.

### 제외: 조건부 과제를 모두 Accepted로 이관

문서 행 수는 빠르게 줄지만 운영 트리거가 충족됐는지 확인하지 않은 채 의무를 없애므로 사용하지 않는다.

### 제외: 코드 과제만 처리하고 운영 과제는 무시

구현 속도는 빠르지만 사용자가 요청한 “모든 과제”를 충족하지 못하고, 다음 담당자가 같은 조사를 반복하게 되므로 사용하지 않는다.

## 5. 실행 파동과 의존성

### Wave 1 — 저비용 감사와 정책 정렬

1. FE-29 문구 규칙 감사 자동화
2. BE-32 상태 전이 의미 조사 및 가능한 범위 정렬
3. BE-18·BE-23·LOG-03·LOG-04의 외부 조건 증거 확인
4. BE-03의 운영 관측 부분과 코드 실행 부분 분리

이 파동은 작은 변경 또는 명확한 차단 근거를 먼저 만든다. 외부 자료가 로컬에 없다는 사실만으로 완료 처리하지 않으며, 저장소 안에서 확인 가능한 배포 문서·로그 설정·메트릭·운영 가이드를 모두 검색한다.

### Wave 2 — 프론트 구조 상환

1. CQ-22의 extension barrel 계약 테스트와 모듈 분해
2. CQ-22의 툴바 하위 컴포넌트 분해
3. CQ-15의 나머지 기준선 파일 분해
4. CQ-18의 범용 UI 이동과 명시 import 전환
5. FE-19의 CSS 위반 제거와 면제 회수

CQ-22는 CQ-15 기준선 네 파일을 직접 줄이므로 먼저 수행한다. CQ-18은 명시 import 한 줄 때문에 CQ-15 기준선을 깨뜨릴 수 있으므로 관련 소비 파일이 800줄 이하가 된 뒤 수행한다. FE-19는 파일 이동과 SFC 분해가 끝난 뒤 실행해 같은 CSS를 두 번 고치지 않는다.

### Wave 3 — API 계약과 ORM 정렬

1. FE-15 OpenAPI required·nullable 보강과 생성 타입 점진 적용
2. BE-03의 코드 실행 가능 프로젝션 잔여
3. BE-25의 복합 PK ORM 정렬과 Oracle 통합 테스트

OpenAPI 계약은 백엔드가 먼저 확정되고 프론트 생성물이 뒤따른다. BE-25는 물리 구조를 바꾸지 않지만 영속성 동작 위험이 높으므로 각 엔티티를 별도 RED/GREEN 커밋으로 처리한다.

## 6. 테스트와 검증

### 프론트엔드

- 각 변경의 표적 Vitest를 RED → GREEN으로 실행한다.
- 파동별로 `npm test`, `npm run format:check`, `npm run check`를 실행한다.
- CSS 변경 파동은 `npm run lint:css`를 추가한다.
- FE-15는 `npm run codegen:check`를 추가한다.
- Tiptap 사용자 흐름은 프론트·백엔드·DB 기동이 가능하면 관련 Playwright spec을 실행한다. 기동 불가 시 단위·계약 테스트로 대체했다고 완료 처리하지 않고 E2E 미실행 사유를 기록한다.

### 백엔드

- 각 변경의 표적 JUnit을 RED → GREEN으로 실행한다.
- 파동별로 `./gradlew test`와 `./gradlew check`를 실행한다.
- BE-25와 새 QueryDSL/JPQL 조회는 `./gradlew integrationTest`로 실제 Oracle 매핑을 검증한다.
- DB 접속 정보가 없거나 Oracle이 기동하지 않으면 BE-25를 완료 처리하지 않는다.

### 루트 추적 문서

- 완료 또는 Accepted 항목만 `TASK_DONE.md`로 옮긴다.
- 활성 유지 항목은 `TASK.md`에 조사 근거와 재개 조건을 갱신한다.
- 각 독립 저장소 커밋 후 `scripts/update-versions-lock.ps1`을 실행한다.
- `git diff --check`와 커밋별 변경 파일 검사를 수행해 DDL 변경이 없음을 확인한다.

## 7. 커밋과 사용자 변경 격리

- 기능별 RED 커밋과 GREEN 커밋을 분리할 수 있는 경우 분리한다.
- 프론트·백엔드 변경은 해당 서브레포에서 먼저 커밋한다.
- 루트 `TASK.md`는 HEAD에서 이번 과제 행만 바꾼 인덱스 blob을 만들어 사용자 BRD·EAI 변경을 스테이징하지 않는다.
- 루트 문서 커밋은 해당 파동의 서브레포 SHA를 `TASK_DONE.md`와 `versions.lock`에 함께 기록한다.

## 8. 종료 조건

- 실행 대상 13건 각각이 완료·Accepted 또는 증거가 있는 외부 차단 상태 중 하나로 분류되어 있다.
- 완료로 분류한 모든 코드 변경은 요구된 테스트와 정적 검사를 통과한다.
- `it_database`의 DDL·마이그레이션 변경이 0건이다.
- 사용자 소유 `TASK.md` 변경과 기존 `graphify-out/`이 보존된다.
- 남은 활성 비DDL 항목은 누가 무엇을 언제 확인해야 하는지 한 번의 읽기로 알 수 있다.
