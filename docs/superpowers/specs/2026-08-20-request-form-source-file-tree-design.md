# 편성요청서 반입 원본 파일 트리·다운로드·진행 표시 설계

## 목표

편성요청서 반입 과정에서 업로드한 부서·사업·하위 폴더 구조를 원본 파일 조회 시에도 보존한다. 원본 파일 다이얼로그는 표준 헤더·푸터, 선택 기능, 형식별 아이콘, 폴더 구조를 유지하는 ZIP 다운로드를 제공한다. [반영] 실행 중에는 별도 표준 다이얼로그에서 배치 진행률과 최종 결과를 표시한다.

## 범위

- 신규 반입 파일의 업로드 상대경로를 공통 파일 메타데이터에 선택적으로 저장한다.
- 반입 원본 파일 조회 응답에 상대경로를 포함한다.
- 신청서별 전체 또는 선택 파일을 폴더 구조가 유지된 ZIP으로 내려받는다.
- 반입 원본 파일 다이얼로그를 전체 펼침 폴더 트리와 선택 가능한 파일 목록으로 변경한다.
- [반영] 실행 전용 진행 다이얼로그를 추가한다.
- 상대경로가 없는 기존 파일은 루트 파일로 표시하여 하위 호환성을 유지한다.

편성요청서 파싱, 원장 생성 규칙, 사전검증 결과표의 업무 판단 로직은 변경하지 않는다.

## 데이터 모델과 API

### 상대경로 저장

공통 파일 테이블 `TPRMPP_CFILEM`에 nullable `APG_FL_PTH`(첨부파일경로, `VARCHAR2(255)`) 컬럼을 추가한다. 이 이름과 길이는 `meta/meta.txt`의 기존 표준 용어를 따른다. 값은 브라우저가 보낸 `fileKey`를 `/` 구분자로 정규화한 상대경로다. 파일명 `FL_NM`은 현재처럼 실제 파일명만 유지한다.

반입 manifest에 이미 포함된 `fileKey`를 `RequestFormSourceFileArchiver.ArchivePlanItem`까지 전달한다. 첫 물리 저장과 다른 신청서로의 메타 연결 모두 같은 상대경로를 보존한다. 일반 파일 업로드는 이 값을 전달하지 않으므로 기존 동작이 유지된다.

상대경로는 다음 규칙으로 정규화한다.

- `\\`를 `/`로 변환한다.
- 빈 세그먼트와 `.`을 제거한다.
- `..`, 절대경로, 드라이브 접두어, 제어문자를 거부한다.
- 마지막 세그먼트가 실제 파일명과 일치하지 않으면 서버가 실제 파일명으로 교체한다.
- 저장 길이는 신규 DB 컬럼 한도 안에서 검증하며 초과 시 해당 원본 보관 실패로 기록한다.

### 조회 응답

공통 `FileDto.Response`에 nullable `relativePath`를 추가한다. 모든 파일 조회 API에서 같은 응답 타입을 사용하되 일반 파일과 기존 반입 파일은 `null`일 수 있다. 프론트 `FileRecord`도 선택 필드로 선언한다.

### ZIP 다운로드

편성요청서 반입 원본 전용 `POST /api/files/request-form-source/archive` ZIP 다운로드 API를 추가한다. JSON 요청은 `apfMngNo`와 nullable `fileIds`를 받는다. `fileIds=null`이면 전체 다운로드이고, 배열이면 하나 이상의 파일 ID를 요구하는 선택 다운로드다. 빈 배열은 검증 오류다.

서버는 다음을 보장한다.

- 현재 사용자가 해당 신청서의 반입 원본을 읽을 권한이 있는지 기존 파일 읽기 권한 계약으로 검증한다.
- 전달받은 모든 파일 ID가 `PK_COL_NM=편성요청서반입`, `PK_CONE=신청관리번호`에 연결됐는지 검증한다.
- ZIP 엔트리명은 저장된 상대경로를 재정규화하고, 상대경로가 없으면 파일명을 사용한다.
- 같은 ZIP 경로가 중복되면 확장자 앞에 `(2)`, `(3)`을 붙여 모든 파일을 보존한다.
- 빈 결과는 성공한 빈 ZIP이 아니라 검증 오류로 응답한다.
- 응답 파일명은 신청관리번호를 포함하는 안전한 `.zip` 이름을 사용한다.

## 프론트엔드 구조

### 원본 파일 트리

`RequestFormSourceFiles`는 파일 표시와 선택 상태를 담당한다. 상대경로 배열을 순수 트리 모델로 바꾸는 로직은 별도 유틸로 분리하여 단위 테스트한다. 모든 폴더는 다이얼로그가 열릴 때 기본 펼침 상태이며 사용자가 개별 폴더를 접거나 펼칠 수 있다.

표시 구조는 다음과 같다.

- 본문 상단: 전체 선택 체크박스, 전체 파일 수, 선택 파일 수
- 폴더 행: 깊이에 따른 들여쓰기, 펼침 토글, 폴더 아이콘, 폴더명
- 파일 행: 체크박스, 형식 아이콘, 파일명, 크기, 등록일시
- 상대경로가 없는 파일: 트리 루트의 파일 행

파일 아이콘은 확장자를 대소문자 구분 없이 판정한다.

| 확장자 | 표시 |
| --- | --- |
| `.xls`, `.xlsx` | Excel 아이콘·녹색 계열 |
| `.pdf` | PDF 아이콘·적색 계열 |
| `.hwp` | HWP 아이콘·청색 계열 |
| `.hwpx` | HWPX 아이콘·청록 계열 |
| 기타 | 일반 파일 아이콘 |

파일명 클릭에 의한 단건 다운로드는 유지한다.

### 표준 다이얼로그

`ApplicationViewerDialog`의 반입 원본 모드는 기존 `AppDialogHeader`를 유지하고 `AppDialogFooter`를 추가한다. 푸터 버튼 순서는 [닫기], [전체 다운로드], [선택 다운로드]다. 선택 파일이 없으면 [선택 다운로드]를 비활성화한다. 다운로드 중에는 관련 버튼을 비활성화하고 로딩 상태를 표시한다.

ZIP 응답은 인증 쿠키가 포함되는 `$apiFetch` 또는 프로젝트의 blob 다운로드 공통 패턴으로 받아 Blob URL을 통해 저장한다. 생성한 Blob URL은 다운로드 시작 직후 해제한다.

### 반영 진행 다이얼로그

[반영] 버튼을 누르면 API 호출 전에 진행 다이얼로그를 연다. 진행 중에는 닫기 버튼, ESC, 배경 클릭을 막아 실행 중 상태를 숨길 수 없게 한다.

진행 다이얼로그는 다음 상태를 가진다.

- `running`: 현재 백분율, 완료 배치 수/전체 배치 수, 처리 중 문구, ProgressBar
- `succeeded`: 100%, 반영 결과 요약, [확인]
- `failed`: 마지막 완료 백분율, 공통 오류 매핑으로 정제한 메시지, [닫기]

`useRequestFormUpload`은 기존 `completedBatches`를 공개하고 실행 시작 시 0으로 초기화한다. 실패 시 완료된 배치 수는 유지하고 결과 데이터도 이미 받은 배치까지 유지한다. 다이얼로그를 닫은 뒤에만 다음 실행을 위한 표시 상태를 초기화한다.

## 오류 처리와 접근성

- 폴더 토글, 체크박스, 다운로드 버튼에는 의미 있는 접근성 이름을 제공한다.
- 전체 선택 체크박스는 일부 선택 시 indeterminate 상태를 사용한다.
- ZIP 생성 실패와 반영 실패는 서버 원문을 직접 노출하지 않고 기존 공통 오류 매핑을 사용한다.
- 네트워크 오류 중에도 기존 화면 데이터와 완료 배치 수를 성공 상태로 오인하지 않는다.
- 다운로드 파일 ID는 화면에서 조작 가능하므로 서버가 소유권과 종류를 최종 검증한다.
- ZIP 엔트리 경로는 저장값을 신뢰하지 않고 다운로드 시 다시 검증하여 Zip Slip을 방지한다.

## 테스트 전략

모든 운영 코드 변경은 실패하는 테스트를 먼저 작성하는 TDD 순서로 구현한다.

### 백엔드

- 상대경로 정규화의 정상·역슬래시·절대경로·`..`·파일명 불일치 사례
- 반입 보관 시 상대경로 저장과 `linkExistingFile` 메타 복제
- 공통 파일 조회 응답의 nullable `relativePath`
- ZIP 전체/선택 다운로드와 폴더 구조 보존
- 다른 신청서 파일 ID, 다른 파일 종류, 빈 선택, 권한 없음 거부
- 중복 ZIP 경로 이름 조정과 기존 파일의 루트 배치
- OpenAPI 계약 테스트

### 프론트엔드

- 상대경로에서 폴더 트리 생성, 안정된 정렬, 기존 파일 루트 표시
- 모든 폴더 기본 펼침과 개별 접기/펼치기
- 전체 선택·부분 선택·indeterminate·선택 다운로드 비활성 조건
- Excel/PDF/HWP/HWPX/기타 확장자 아이콘
- 표준 푸터와 전체/선택 ZIP 요청
- 진행 다이얼로그 running/succeeded/failed 전환과 닫기 제한
- 완료 배치 수와 실패 시 마지막 진행률 유지
- 관련 Playwright 사용자 흐름

### 검증 명령

- 백엔드: 관련 단위·MVC 테스트 후 `./gradlew test`, 필요 시 `./gradlew check`
- 프론트엔드: 관련 Vitest 후 `npm run format:check`, `npm run check`, `npm test`, `npm run lint:css`, 관련 `npm run test:e2e`
- API 응답 타입 변경 후 백엔드를 기동하여 `npm run codegen` 및 `npm run codegen:check`

## 배포와 호환성

DB 마이그레이션을 먼저 적용하고 백엔드, 프론트엔드 순으로 배포한다. 신규 컬럼은 nullable이므로 기존 행과 일반 업로드에는 영향이 없다. 백엔드 응답 필드 추가는 구버전 프론트에서 무시되며, 신버전 프론트는 필드가 없거나 null인 응답도 처리한다.

세 저장소의 호환 변경이 완료되면 루트 `versions.lock`을 갱신한다. 기존 반입 파일의 폴더 구조는 과거에 저장되지 않았으므로 복원하지 않으며 루트 파일로 표시한다.
