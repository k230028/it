# 정보화사업 금액 의미 리팩토링 설계

## 1. 목적

정보화사업 품목과 사업 마스터의 금액 컬럼을 아래 업무 의미로 통일한다.

- 품목 `AMT`는 전체기간 금액이 아니라 당해 요청금액의 원화 환산값이다.
- 품목 `MPL_AMT`는 `AMT`에 포함된 일부 금액이 아니라 내년 이후 요청금액이다.
- 사업 `MPL_AMT`와 `DFR_AMT`, `TOT_RQM_AMT`는 모두 원화다.
- 당해 요청금액에서 예정금액을 차감하지 않는다.
- 사업 총소요금액은 당해 요청금액, 예정금액, 기 지급금액의 합이다.

기존 업무 데이터는 전량 삭제하고 새 계약으로 다시 입력한다. 기존 행의 의미 변환, 과거 금액 보정, 신·구 계약 동시 지원은 이 설계의 범위가 아니다.

## 2. 용어와 불변식

### 2.1 품목 금액

| 통화 | `BITEMM.AMT` | `BITEMM.FC_AMT` | `BITEMM.MPL_AMT` |
| --- | --- | --- | --- |
| 원화 | 당해 요청금액 원화 | `NULL` | 내년 이후 요청금액 원화 |
| 외화 | `FC_AMT × XCR`로 계산한 당해 요청금액 원화 | 당해 요청금액 외화 원금 | 내년 이후 요청금액 외화 원금 |

품목의 `AMT`와 `MPL_AMT`는 서로 독립된 금액이다. `MPL_AMT <= AMT` 관계를 요구하지 않는다. 당해 요청금액이 0이고 예정금액만 있는 품목과 예정금액이 당해 요청금액보다 큰 품목을 모두 허용한다.

외화 품목의 당해 요청금액과 예정금액은 동일한 `CUR_C`, `XCR`, `XCR_BSE_DT`를 사용한다. 예정금액 전용 통화·환율 컬럼은 추가하지 않는다.

### 2.2 사업 금액

활성 최신 품목 집합을 `I`라고 할 때 사업 금액을 다음과 같이 계산한다.

```text
currentRequestAmt = SUM(i.AMT)

plannedAmt = SUM(
  KRW 품목: i.MPL_AMT
  외화 품목: round(i.MPL_AMT * i.XCR, 3, HALF_UP)
)

paidAmt = NVL(BPROJM.DFR_AMT, 0)

totalRequiredAmt = currentRequestAmt + plannedAmt + paidAmt
```

사업 마스터 저장 계약은 다음과 같다.

```text
BPROJM.TOT_RQM_AMT = totalRequiredAmt
BPROJM.MPL_AMT     = plannedAmt
BPROJM.DFR_AMT     = 사용자가 입력한 기 지급금액(원화)
```

모든 사업 응답은 아래 불변식을 만족해야 한다.

```text
prjBgAmt = tyyBgAmt + mplAmt + NVL(dfrAmt, 0)
```

## 3. 설계 선택

### 3.1 선택안: 중앙 계산기와 명시적 스냅샷

금액 의미와 환산을 백엔드의 단일 도메인 계산기에 둔다. 품목 변경 트랜잭션에서 활성 최신 품목을 다시 집계하고 `BPROJM` 금액 3종을 함께 갱신한다. 목록과 외부 연계는 저장된 사업 스냅샷을 사용하고, 상세 조회 및 검증은 같은 계산기로 품목 파생값을 확인할 수 있다.

이 방식을 선택한 이유는 다음과 같다.

- `DFR_AMT`가 사업 마스터에 있으므로 품목만 조회해서 총소요금액을 완성할 수 없다.
- 목록·협의회·대시보드에서 반복 집계를 피할 수 있다.
- 서비스 중심의 현재 구조와 맞고 DB 트리거 의존성을 만들지 않는다.
- 계산 계약을 단위 테스트로 독립 검증할 수 있다.

### 3.2 선택하지 않은 방식

- 조회 시 전량 실시간 파생: 다수 조회 경로의 쿼리와 성능이 복잡해지고 마스터 금액 컬럼의 역할이 사라진다.
- DB 트리거·집계 뷰 중심: JPA 영속성 컨텍스트와 DB 갱신 시점이 분리되고 테스트·운영 책임이 복잡해진다.

## 4. 백엔드 컴포넌트

### 4.1 품목 금액 정규화

기존 `BudgetAmountCalculator`의 외화 당해금액 환산 규칙을 재사용하되 품목 저장 경계에서 다음 계약을 명시한다.

원화 품목:

```text
AMT     = 요청 AMT
FC_AMT  = NULL
MPL_AMT = 요청 MPL_AMT
```

외화 품목:

```text
FC_AMT  = 요청 FC_AMT
AMT     = round(FC_AMT * 서버 조회 XCR, 3, HALF_UP)
MPL_AMT = 요청 MPL_AMT
```

`ProjectItemSynchronizer.clampMpl()`과 `MPL_AMT <= AMT` 보정은 제거한다. 음수 금액은 0으로 조용히 변경하지 않고 요청 검증 오류로 반환한다.

### 4.2 사업 금액 계산기

프로젝트 도메인에 다음 값 객체와 순수 계산 책임을 둔다.

```java
public record ProjectAmountSummary(
        BigDecimal currentRequestAmt,
        BigDecimal plannedAmt,
        BigDecimal paidAmt,
        BigDecimal totalRequiredAmt) {}
```

계산 인터페이스의 논리 계약은 다음과 같다.

```java
ProjectAmountSummary calculate(
        Collection<Bitemm> activeItems,
        BigDecimal paidAmt);
```

계산기는 다음만 책임진다.

- 원화·외화 품목의 예정금액을 원화로 환산한다.
- 당해 요청금액, 예정금액, 기 지급금액, 총소요금액을 계산한다.
- `NUMBER(18,3)`에 맞게 금액 스케일과 반올림을 통일한다.
- null 금액을 업무상 0으로 해석한다.

품목 선택, 저장, 권한, 트랜잭션은 계산기 밖의 기존 서비스 책임으로 유지한다.

### 4.3 저장 흐름

사업 생성·수정 시 다음 순서를 하나의 명령 트랜잭션에서 수행한다.

```text
요청 검증
  → 서버 환율 조회
  → 품목 금액 정규화
  → 품목 추가·수정·삭제 및 최신행 처리
  → 활성 최신 품목 재조회
  → ProjectAmountSummary 계산
  → BPROJM 금액 스냅샷 갱신
  → 트랜잭션 커밋
```

기 지급금액은 음수 여부만 검증한다. `DFR_AMT <= SUM(AMT)` 검증은 제거한다. 현재 모델에는 기 지급금액의 독립적인 상한으로 사용할 계약총액이 없기 때문이다.

`DFR_AMT` 미입력 여부는 DB에서 `NULL`로 보존할 수 있지만 계산에서는 0으로 처리한다. `TOT_RQM_AMT`와 `MPL_AMT` 스냅샷은 계산된 0을 저장해 목록 응답의 null 분기를 줄인다.

### 4.4 조회 흐름

- 목록·협의회·대시보드: `BPROJM`의 원화 스냅샷을 사용한다.
- 상세: 스냅샷을 응답하되 활성 최신 품목의 파생 합계를 동일 계산기로 검증할 수 있게 한다.
- 스냅샷 불일치: 운영 응답에서 임의의 값을 선택하지 않고 저장 스냅샷을 정본으로 응답한다. 파생 합계와의 차이는 백엔드 로그에 남기지 않는다(2026-09-11 결정으로 경고 로그 제거).

스냅샷 갱신 경로가 애플리케이션 명령으로 한정되므로 상세 조회마다 자동 복구하지 않는다. 별도 운영 재집계 명령이 필요해질 때만 독립 기능으로 추가한다.

## 5. API 계약

사업 응답 금액 필드를 다음 의미로 고정한다.

| API 필드 | 의미 | 출처 |
| --- | --- | --- |
| `tyyBgAmt` | 당해 요청금액 원화 | 활성 최신 품목 `AMT` 합계 |
| `mplAmt` | 내년 이후 예정금액 원화 환산 합계 | `BPROJM.MPL_AMT` |
| `dfrAmt` | 기 지급금액 원화 | `BPROJM.DFR_AMT` |
| `prjBgAmt` | 총소요금액 원화 | `BPROJM.TOT_RQM_AMT` |

품목 응답은 원통화 표시를 위해 `curC`, `xcr`, `xcrBseDt`, `fcAmt`, `mplAmt`, `amt`를 유지한다. 외화 품목에서는 `fcAmt`와 `mplAmt`가 외화 원금이고 `amt`만 원화 환산값이라는 점을 OpenAPI 설명에 명시한다.

`totRqmAmt`라는 이름을 사용하는 다른 도메인(사업계획 등)은 이 리팩토링 대상이 아니다. 이름이 같다는 이유로 계산식을 일괄 변경하지 않는다.

## 6. 연계 업무 변경

### 6.1 사업 요약과 협의회

당해예산 계산을 `SUM(AMT) - SUM(MPL_AMT)`에서 `SUM(AMT)`로 변경한다. 협의회 목록·상세에서 별도로 품목을 조회해 기존 차감식을 적용하는 로직을 제거하고 사업 스냅샷 또는 중앙 계산기 결과를 사용한다.

### 6.2 예산작업과 계획작성

예산연도 대상 요청금액은 이미 `BITEMM.AMT`에 담겨 있다. 따라서 다음 로직을 제거한다.

- `MPL_AMT / AMT` 비율 산출
- 편성요청액에서 예정금액 비율 차감
- 편성액에서 예정금액 비율 차감
- 차감 후 음수를 0으로 숨기는 보정

예산작업의 요청·편성 금액은 당해 금액만 사용한다. `MPL_AMT`는 장기 예정금액 및 총소요금액 표시에만 참여한다.

### 6.3 계속사업 생성

현재 `MPL_AMT`는 내년 이후 전체 금액이며 연도별 내역이 없다. 어느 금액이 새 기준연도의 당해분인지 판별할 수 없으므로 계속사업 생성 시 금액을 자동 이월하지 않는다.

- 품목명, 비목, 통화, 지급주기, 근거 등 비금액 정보는 복사한다.
- `AMT`, `FC_AMT`, `MPL_AMT`는 0 또는 미입력 상태로 시작한다.
- 사용자가 신년도 당해·예정 금액을 다시 입력한다.
- 기존 품목관리번호는 신규 품목에 재사용하지 않는다.

연도별 예정금액 자동 이월은 연도별 금액 모델이 도입될 때 별도 설계한다.

## 7. 프론트엔드 변경

프론트엔드는 서버 금액 의미를 그대로 표시하며 사업 단위 원화 합계를 재계산하지 않는다.

- 품목의 당해 요청금액과 내년 이후 요청금액을 독립 입력으로 취급한다.
- 외화 행은 당해 요청금액에 `FC_AMT`, 예정금액에 `MPL_AMT`를 원통화로 표시한다.
- 원화 행은 당해 요청금액에 `AMT`, 예정금액에 `MPL_AMT`를 표시한다.
- `MPL_AMT > AMT`를 막는 화면 검증과 자동 보정을 제거한다.
- 사업 목록·상세·엑셀·PDF에서 `tyyBgAmt`는 "당해 요청금액", `prjBgAmt`는 "총소요금액"으로 표시한다.
- 예정금액과 지급금액을 총소요금액의 구성요소로 분리해 표시한다.
- 대시보드와 승인 문서가 당해 예산을 요구하면 `tyyBgAmt`, 전체 사업 규모를 요구하면 `prjBgAmt`를 사용한다.

## 8. 검증과 오류 처리

다음 입력은 400 업무 검증 오류로 처리한다.

- `AMT`, `FC_AMT`, `MPL_AMT`, `DFR_AMT` 중 음수 값
- 외화 품목인데 `CUR_C`, `FC_AMT` 또는 유효한 서버 환율이 없음
- 원화 품목인데 `FC_AMT`가 입력됨
- 환산 또는 합산 결과가 `NUMBER(18,3)` 범위를 초과함

다음 입력은 허용한다.

- `MPL_AMT > AMT`
- 당해 요청금액 0, 예정금액 양수
- 당해 요청금액 0, 기 지급금액 양수
- 예정금액 0 또는 미입력
- 기 지급금액 미입력

환율 조회 실패 시 클라이언트가 보낸 환율을 대신 신뢰하지 않는다. 저장을 거부하고 기존 공통 오류 계약으로 안내한다.

## 9. 데이터베이스와 초기화

컬럼 추가·삭제는 필요하지 않다. 기존 데이터는 전량 삭제하므로 금액 의미를 변환하는 DML 마이그레이션을 만들지 않는다.

초기화는 별도 승인된 운영 절차에서 정확한 대상 테이블과 FK 순서를 확인한 뒤 수행한다. 이 설계는 스키마 drop이나 실행용 삭제 SQL을 포함하지 않는다. 초기화 대상에는 최소한 사업·품목 마스터와 해당 데이터에 종속된 업무 테이블이 포함될 수 있으므로, 실제 삭제 범위는 실행 전에 DB 관계를 기준으로 확정해야 한다.

새 Flyway 마이그레이션이 필요한 경우는 컬럼 코멘트 또는 DB 제약을 새 의미로 명시할 때뿐이다. 적용된 기존 마이그레이션은 수정하지 않는다. 다음 메타데이터와 문서는 새 의미로 갱신한다.

- `meta/table.txt`
- `Bprojm`, `Bitemm` 및 변경로그 엔티티의 컬럼 설명
- 데이터 모델 가이드와 OpenAPI 설명
- 테스트 픽스처의 금액 의미

## 10. 테스트 전략

### 10.1 계산기 단위 테스트

| 사례 | 입력 | 기대값 |
| --- | --- | --- |
| 원화 기본 | `AMT=100`, `MPL=500`, `DFR=20` | 당해 100, 예정 500, 총 620 |
| 외화 기본 | `FC=100`, `MPL=50`, `XCR=1400` | 당해 140000, 예정 70000 |
| 혼합 통화 | KRW·USD·JPY 복수 품목 | 통화별 환산 후 원화 합계 |
| 예정금액 우위 | `AMT=100`, `MPL=500` | MPL 손실 없이 유지 |
| 당해금액 없음 | `AMT=0`, `MPL>0` | 정상 계산 |
| 지급금액 우위 | `DFR>SUM(AMT)` | 정상 계산 |
| 반올림 | 환산 결과 소수 3자리 초과 | `HALF_UP`, scale 3 |

### 10.2 서비스 테스트

- 사업 생성·수정·품목 삭제 후 사업 스냅샷을 다시 계산한다.
- 최신 활성 품목만 합산하고 삭제·과거 이력행을 제외한다.
- 음수 금액을 자동 보정하지 않고 거부한다.
- 목록·상세·협의회에서 같은 금액 의미를 반환한다.
- 예산작업과 사업별 편성 결과에서 예정금액을 차감하지 않는다.
- 계속사업 생성 시 금액을 복사하지 않는다.
- 모든 응답에서 `prjBgAmt = tyyBgAmt + mplAmt + NVL(dfrAmt, 0)`을 만족한다.

### 10.3 API·프론트 테스트

- OpenAPI 필드 설명과 nullable 계약을 검증한다.
- 원화·외화 품목 입력 payload가 올바른 필드에 매핑된다.
- `MPL_AMT > AMT` 입력이 프론트와 서버에서 허용된다.
- 목록·상세·엑셀·PDF의 당해 요청금액과 총소요금액을 구분한다.
- 대시보드와 승인 문서 합계가 의도한 API 필드를 사용한다.
- 기존 "MPL 차감" 회귀 테스트를 새 의미의 음성 검증으로 교체한다.

### 10.4 DB 검증

데이터 초기화 후 신규 픽스처로 다음을 확인한다.

- 음수 금액 0건
- 외화 품목 필수정보 누락 0건
- 원화 품목 `FC_AMT IS NOT NULL` 0건
- 사업 스냅샷 불변식 위반 0건
- 활성 최신 품목 집계와 사업 `MPL_AMT`, `TOT_RQM_AMT` 불일치 0건

## 11. 적용 순서

1. 계산기 단위 테스트와 새 금액 계약을 추가한다.
2. 품목 저장에서 `MPL_AMT <= AMT` 보정과 관련 검증을 제거한다.
3. 사업 스냅샷 계산을 `ProjectAmountSummary`로 통합한다.
4. 협의회·예산작업·계획작성의 예정금액 차감 로직을 제거한다.
5. API 설명과 프론트 표시·입력·보고서를 새 의미로 변경한다.
6. 계속사업 금액 자동 복사를 제거한다.
7. 기존 업무 데이터를 승인된 절차로 초기화한다.
8. 신규 의미의 검증 픽스처를 입력하고 전체 Health Stack을 실행한다.
9. 스냅샷 불변식과 주요 화면·보고서를 확인한 뒤 배포한다.

DB 초기화는 되돌리기 어려운 작업이므로 구현 코드 배포와 별도의 실행 승인 및 백업 정책을 따른다. 이 설계의 승인은 데이터 삭제 실행 승인으로 간주하지 않는다.

## 12. 범위 제외

- 예정금액을 연도별로 분리하는 신규 테이블
- 당해와 예정금액에 서로 다른 환율을 적용하는 기능
- 기존 업무 데이터의 의미 변환 및 보존
- 변경로그 과거 금액의 재작성
- 다른 도메인의 동명 `TOT_RQM_AMT` 의미 변경
- 데이터 삭제 명령의 실제 실행

## 13. 완료 기준

- 품목 `AMT`가 모든 저장·조회·편성 경로에서 당해 요청금액으로만 사용된다.
- 외화 품목의 예정금액이 동일 품목 환율로 원화 환산되어 사업 `MPL_AMT`에 반영된다.
- 사업 `TOT_RQM_AMT`가 당해 요청금액, 예정금액, 지급금액의 합과 일치한다.
- 예정금액을 당해금액에서 차감하거나 `AMT`로 상한 보정하는 코드와 테스트가 없다.
- 목록·상세·협의회·예산작업·대시보드·엑셀·PDF가 동일한 필드 의미를 사용한다.
- 계속사업 생성 시 금액이 자동 복사되지 않는다.
- 백엔드·프론트엔드·DB 검증과 프로젝트 Health Stack이 통과한다.
