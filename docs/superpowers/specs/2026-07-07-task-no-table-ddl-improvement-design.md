# TASK 무테이블 DDL 개선 설계

## 목적

`TASK.md` 잔여과제 중 DB 테이블 구조 변경이 필요 없는 항목만 선별해 개선한다. 여기서 제외하는 범위는 신규 테이블, 컬럼 추가/변경, PK 변경처럼 물리 테이블 구조를 바꾸는 작업이다. 인덱스, 뷰, 쿼리, API, 프론트엔드, 테스트, 운영 설정 변경은 포함한다.

## 범위

### 포함

| 영역 | 대상 |
| --- | --- |
| 보안 | `SEC-01`, `SEC-02` |
| 에러 처리 | `ERR-01`, `ERR-02` |
| 프론트엔드 | `FE-01`, `FE-02` |
| 백엔드 | `BE-01`, `BE-02`, `BE-03`, `BE-04`, `BE-05`, `BE-06` |
| Tiptap 변수 입력 | `TIP-01`, `TIP-02`, `TIP-03`, `TIP-04`, `TIP-05` |
| 실시간 로그 | `LOG-01`, `LOG-02`, `LOG-03`, `LOG-04`, `LOG-05`, `LOG-06`, `LOG-07` |
| 공통 게시판 | `BRD-01` 정책/검증 범위, `BRD-02`, `BRD-03`, `BRD-04`, `BRD-07`, `BRD-08`, `BRD-09`, `BRD-10` |
| EAI | `EAI-02`, `EAI-03`, `EAI-04`, `EAI-07` |

### 제외

| 영역 | 대상 | 제외 이유 |
| --- | --- | --- |
| 공통 게시판 | `BRD-05` | 다운로드 카운트 컬럼 추가 필요 |
| 공통 게시판 | `BRD-06` | 댓글 첨부파일 저장 매핑/분류 변경이 테이블 정책 변경으로 이어질 수 있음 |
| 공통 게시판 | `BRD-11` | 첨부파일 UI/API 연결은 기존 스키마로 가능한지 선확인 전에는 파일 매핑 변경 가능성이 있음 |
| 사전협의 | `REV-01` | 실제 인증 연동이 선행조건이라 현재 개선 범위에서는 워크플로우 기준이 불안정함 |
| 사전협의 | `REV-02`, `REV-03` | 검토의견 응답 DTO/API 확장 범위이며, 사전협의 워크플로우 재설계와 함께 별도 처리 |
| EAI | `EAI-01`, `EAI-05`, `EAI-06` | 외부 운영팀/KDB 확인 의존 |
| 메타 용어사전 | `META-01`, `META-02`, `META-03` | 운영 데이터 이관 또는 PK 정합 등 테이블 구조/데이터 정합 이슈 |

## 실행 웨이브

| Wave | 목표 | 대상 | 산출물 |
| --- | --- | --- | --- |
| P0 | 보안 잔여 위험 봉합 | `SEC-01`, `SEC-02` | Refresh Token 동시성 불변식, 무부서 사용자 조회 차단 정책 |
| P1 | 사용자 영향 결함과 업무 결정 정리 | `ERR-01`, `ERR-02`, `BE-04` | 문서 조회 실패 상태, 무시형 실패 진단, 환율 규칙 결정/적용 |
| P2 | 프론트 기능 정리와 Tiptap 즉시 체감 개선 | `FE-01`, `FE-02`, `TIP-01`, `TIP-04` | 운영 데이터 연동, 표시 유틸 통합, 변수 prop 확대, 작성 직후 변수 해석 |
| P3 | 테스트/품질 기반 강화 | `BE-01`, `BE-02`, `BE-03`, `BE-05`, `BE-06`, `TIP-02`, `TIP-03`, `TIP-05` | 회귀 테스트, 통합 테스트, 목록 프로젝션, 문구/Javadoc 정리, Tiptap 검증 |
| P4 | 운영 확장 기능 | `LOG-01~07`, `EAI-02~04`, `EAI-07`, `BRD-01~04`, `BRD-07~10` | 실시간 로그 개선, EAI 연결, 게시판 정책/검색/알림/페이지네이션 개선 |

## 설계 원칙

- 테이블 구조 변경이 감지되면 해당 항목은 즉시 범위 밖으로 이동한다.
- 기존 API/테이블/엔티티를 재사용하고, 신규 API는 조회/집계/동작 보강 범위로 제한한다.
- 사용자에게 보이는 오류는 빈 데이터와 구분한다.
- 보안 항목은 프론트 UX 보호가 아니라 백엔드 서비스/쿼리 계층에서 최종 보장한다.
- 테스트는 변경 위험도에 맞춰 단위 테스트, 통합 테스트, Playwright 순서로 보강한다.

## 데이터 흐름

보안과 조회 정책은 백엔드 인증 주체에서 사용자 역할·부서코드를 해석한 뒤 서비스 또는 Repository 조건에 반영한다. 프론트엔드는 서버 응답의 성공/실패 상태를 그대로 표시하고, 클라이언트 저장소는 사용자 편의 설정에만 사용한다.

Tiptap과 문서/내보내기는 기존 문서 HTML과 변수 토큰을 입력으로 받아 서버 해석 또는 클라이언트 변환 결과를 표시한다. 실패 시에는 빈 본문/빈 배열 대신 오류 상태나 경고 상태를 분리한다.

실시간 로그와 게시판은 기존 조회 테이블·뷰·쿼리를 기반으로 기능을 확장한다. 필요 시 인덱스나 뷰 개선은 허용하지만 테이블 컬럼 추가는 별도 과제로 분리한다.

## 에러 처리

- API 조회 실패는 화면별 오류 상태로 보존한다.
- 자동 폴링·클립보드 같은 반복성 작업은 사용자 방해를 줄이되, 중복 제한된 진단 로그 또는 상태 플래그를 남긴다.
- EAI 발송은 부수효과로 유지하고 실패를 원 트랜잭션에 전파하지 않는다.
- Refresh Token 회전 충돌은 다중 활성 토큰 생성이 불가능하도록 서버 측 불변식으로 차단한다.

## 테스트 전략

| 범위 | 검증 |
| --- | --- |
| 보안 | Refresh Token 동시 요청, 무부서 비관리자 조회 차단 단위/통합 테스트 |
| 프론트 | 에러 상태 표시, 파일/금액 포맷, Tiptap 변수 해석 단위 테스트 |
| 백엔드 | 환율 규칙, 목록 프로젝션, 알림 문구 유틸, Javadoc 경고 감소 확인 |
| 실시간 로그 | 관리자/일반/미인증 접근, since 커서, Playwright E2E |
| 게시판 | 페이지네이션, 검색 제한, 깊이 제한, 서비스 단위 테스트 |
| EAI | enabled 설정, 도메인 상태전이 후 발송 호출, 실패 무전파 테스트 |

## 완료 기준

- 포함 대상 중 테이블 구조 변경 없이 처리 가능한 항목별 구현 계획이 작성된다.
- 구현 중 테이블 구조 변경이 필요한 항목은 제외 목록으로 이동한다.
- 각 웨이브는 자체 검증 명령과 롤백 가능한 변경 단위로 분리된다.
- 완료된 항목은 `TASK_DONE.md`로 이동하고 `TASK.md`에서는 삭제한다.
