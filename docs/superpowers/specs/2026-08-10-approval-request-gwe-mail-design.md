# 결재요청 그룹웨어 메일 연동 설계

## 목표

결재요청 시 다음 결재자에게 그룹웨어 메일을 발송한다. 결재완료·반려 알림은 기존 인앱 알림으로 유지한다.

## 발송 흐름

1. 결재 신청 또는 중간 승인 트랜잭션이 커밋되면 다음 대기 결재자를 수신자로 하는 알림 이벤트를 처리한다.
2. 알림 outbox 행을 GWE 채널로 적재한 뒤 EAI를 호출한다.
3. GWE 개별부는 메일 규격으로 생성한다.
   - `Msg_gubun`: `3`
   - `Msg_key`: `mailt` + 애플리케이션코드 + 업무레벨 + 시각 + 난수
   - `Dest_gubun`: `1`
   - `Recv_ids`: 공백을 제거하고 대문자로 정규화한 다음 결재자 사번
   - `ATT_FLAG`: `0`
   - 메신저 전용 `URL`: 빈값
4. 메일 본문은 결재 제목과 결재 화면 링크를 포함하는 HTML로 생성한다. 링크는 `app.frontend-url`과 `/approval/list?tab=pending`를 결합한 절대 URL이다. 기준 URL의 후행 슬래시 유무와 관계없이 슬래시는 하나만 사용한다.

## EAI 성공 및 오류 판정

- `eai.enabled=false`에서는 기존과 같이 실제 통신을 생략한다. 이 설정은 EAI 통신이 불가능한 로컬·테스트 환경에 사용한다.
- HTTP `204 No Content`만 EAI 접수 성공으로 판정한다.
- HTTP `200 OK`는 EAI 오류 응답이다. 응답 표준전문에서 `RLT_TC=2`, `MSG_IDCT_TC=1` 및 `SEEAI` 오류 메시지를 추출해 실패 결과로 반환한다.
- 그 밖의 HTTP 상태, 응답 파싱 실패, 연결 오류와 타임아웃도 실패로 처리한다.
- 실패 결과는 기존 알림 실패 상태와 재시도 스케줄러를 사용한다. 원 결재 트랜잭션은 롤백하지 않는다.
- 로그와 DB 오류내용에는 비밀정보나 전문 전체를 남기지 않고 EAI 오류 코드와 안전하게 제한한 메시지만 기록한다.

## 설정

- 메일 링크의 기준 URL은 기존 `app.frontend-url` 설정을 사용한다.
- `dev`와 `prod`에서만 운영 배포 환경이 `eai.enabled=true`와 해당 환경의 `eai.url`을 주입한다.
- 코드에 개발·운영 EAI URL을 하드코딩하지 않는다.

## 테스트

- 최초 결재요청과 중간 승인 후 다음 결재요청이 GWE 메일 채널을 선택하는지 검증한다.
- 결재완료·반려 알림이 GWE 채널을 선택하지 않는지 검증한다.
- 메일 전문의 `mailt` 키, `Msg_gubun=3`, `ATT_FLAG=0`, 빈 URL을 바이트 위치 기준으로 검증한다.
- 메일 본문에 `app.frontend-url` 기반 절대 링크가 포함되는지 검증한다.
- 수신자 사번 대문자 정규화를 검증한다.
- HTTP 204 성공, HTTP 200 EAI 오류, 기타 HTTP 오류, 파싱 불가 응답과 네트워크 예외를 검증한다.

## 범위 제외

- 결재완료·반려·회수의 그룹웨어 외부 발송
- 그룹웨어 발송 결과 테이블의 `FLAG`/`REMARK` 후속 조회
- 첨부파일, 참조 및 숨은참조 수신자
