# 내부망 MFA 연동 설계

## 1. 목적과 범위

`mfa.md`에 정의된 지정맥, FIDO, mOTP를 다음 사용자 행위에 적용한다.

- 수동 로그인: 사번·비밀번호 검증 후 MFA를 완료해야 로그인 토큰을 발급한다.
- 전자결재: 사용자가 수행하는 신청, 승인, 반려, 회수 등 결재 상태 변경 전에 MFA를 검증한다.

SSO 로그인, 개발용 사용자 전환, 외부 전자결재 시스템의 서버 간 콜백은 이번 MFA 적용 대상에서 제외한다. 서버 간 콜백은 기존 인증·인가 정책을 유지한다.

적용 프로파일은 `local-ext`, `local-int`, `dev`, `prod`이다. `local-ext`는 실제 선택 대화상자와 API 흐름을 유지하되 사용자가 확인 버튼을 누르면 MFA가 항상 성공한다. `local-int`, `dev`, `prod`에서는 우회 설정을 허용하지 않는다.

## 2. 핵심 원칙

- MFA 성공 전에는 수동 로그인용 Access Token과 Refresh Token을 발급하지 않는다.
- 전자결재 상태 변경은 프론트엔드 화면뿐 아니라 백엔드 명령 경계에서도 MFA를 강제한다.
- MFA 증표는 사용자와 용도에 귀속하며 다른 사용자나 로그인·결재 간에 전용할 수 없다.
- 전자결재 MFA 증표는 상태 변경 요청 한 건에만 사용하고 서버 메모리에서 원자적으로 소비한다.
- OTP, QR 원문, 생체정보, MFA 증표 원문은 로그나 영속 저장소에 남기지 않는다.

## 3. 인증수단 모델

공통 인증수단 코드는 다음 세 값으로 제한한다.

- `FINGER_VEIN`: 지정맥. 기본 선택값이다.
- `FIDO`: OnePass FIDO 인증이다.
- `MOTP`: OnePass 모바일 OTP 인증이다.

백엔드는 공통 MFA 공급자 인터페이스를 두고 인증수단별 구현을 분리한다. 공급자는 인증 시작, 검증, 거래 취소를 담당한다. 컨트롤러와 전자결재 도메인은 공급자별 프로토콜을 직접 알지 않는다.

지정맥은 브라우저에서 `ws://127.0.0.1:8089/bio`의 BioAgent와 통신하고 필요 시 `BioAgent://`를 호출한다. 제공 문서는 클라이언트 에이전트의 `FE00` 결과 외에 서버가 독립적으로 검증할 서명값을 정의하지 않는다. 따라서 지정맥 결과는 FIDO와 mOTP보다 위변조 저항성이 낮다. 이 제약을 운영 문서에 명시하고, 향후 서버 검증 규격이 제공되면 지정맥 공급자만 교체할 수 있도록 경계를 유지한다.

## 4. 프로파일별 동작

| 프로파일 | MFA 동작 | OnePass 기본 URL |
| --- | --- | --- |
| `local-ext` | 대화상자 확인 시 모의 성공 | 호출하지 않음 |
| `local-int` | 실제 연동 | `https://dopsap.kdb.co.kr:20443/interfBiz/processRequest.do` |
| `dev` | 실제 연동 | `https://dopsap.kdb.co.kr:20443/interfBiz/processRequest.do` |
| `prod` | 실제 연동 | `https://opsap.kdb.co.kr:20443/interfBiz/processRequest.do` |

기본 `siteId`는 `SIT01KDBBANK00000000`, `svcId`는 `SVC12SIT01KDBBANK000`으로 설정하되 환경변수로 재정의할 수 있게 한다. URL, siteId, svcId, 연결 타임아웃, 응답 타임아웃을 구성 속성으로 묶는다. `local-int`, `dev`, `prod`에서 필수값이 비어 있거나 모의 공급자가 활성화되면 기동을 실패시킨다. 특히 `prod`에서는 모의 성공 설정을 어떤 경우에도 허용하지 않는다.

## 5. 수동 로그인 흐름

1. 프론트엔드는 사번과 비밀번호를 `POST /api/auth/login/start`로 전송한다.
2. 백엔드는 기존 계정 잠금과 로그인 시도 정책을 포함해 자격증명을 검증한다.
3. 성공 시 짧은 수명의 로그인 대기 거래를 만들고 대기 식별자만 반환한다. JWT 쿠키는 발급하지 않는다.
4. 프론트엔드는 공통 MFA 대화상자를 표시한다.
5. MFA 성공 후 `POST /api/auth/login/complete`가 로그인 대기 거래와 MFA 증표의 사번·용도·만료를 대조한다.
6. 대조와 소비가 성공한 경우에만 기존 방식대로 Access Token·Refresh Token httpOnly 쿠키와 사용자 응답을 발급한다.
7. 로그인 대기 거래 또는 MFA 거래가 만료되면 비밀번호 입력부터 다시 시작한다.

기존 `POST /api/auth/login`은 호환성 유지를 위해 내부적으로 시작 API로 즉시 전환하지 않는다. 구현 시 저장소 내 호출자를 전수 확인한 뒤, 프론트엔드와 API 계약을 함께 변경하고 구 경로는 제거하거나 명시적인 MFA 필요 응답을 반환한다. MFA를 우회해 기존 토큰 발급 로직에 직접 도달하는 공개 경로가 남아서는 안 된다.

## 6. 전자결재 흐름

1. 사용자가 신청, 승인, 반려, 회수 등 결재 상태 변경을 요청한다.
2. 공통 프론트엔드 실행 래퍼가 매번 공통 MFA 대화상자를 연다.
3. MFA가 성공하면 서버가 현재 JWT 사용자에게 귀속된 1회용 결재 증표를 발급한다.
4. 프론트엔드는 원래 상태 변경 요청을 실행한다.
5. 백엔드 공통 검증 계층이 사용자, 용도, 만료, 소비 상태를 검증한 후에만 도메인 명령을 호출한다.

전자결재 MFA는 인증 상태를 재사용하지 않는다. 신청, 승인, 반려, 회수 등 각 상태 변경마다 새 MFA 거래를 완료해야 한다. 1회용 증표는 명령이 서버에서 수락되어 도메인 처리 시도에 진입할 때 서버 메모리에서 원자적으로 소비한다.

검증 대상은 공통 전자결재의 신청·승인·반려·회수 API와 전자결재 신청서를 생성하거나 상태를 바꾸는 도메인별 명령 API이다. 단순 조회, 임시저장, 외부 시스템 콜백은 제외한다. 구현 계획 작성 시 변경형 엔드포인트 목록을 코드 검색으로 확정하고 각 엔드포인트를 명시적으로 테스트한다.

## 7. MFA API 계약

### 7.1 공통 엔드포인트

- `POST /api/mfa/challenges`
  - 입력: 용도(`LOGIN` 또는 `APPROVAL`), 인증수단, 로그인 대기 식별자(로그인 용도에만 필요)
  - 출력: MFA 거래 ID, 공급자 표시 데이터, 만료시각
- `POST /api/mfa/challenges/{id}/verify`
  - 입력: 인증수단별 검증 데이터. mOTP는 OTP 값, 지정맥은 BioAgent 결과와 거래 nonce를 전달한다. FIDO는 서버가 거래 결과를 조회하므로 별도 비밀 입력이 없다.
  - 출력: 성공 여부와 서버 기준 만료시각
- `DELETE /api/mfa/challenges/{id}`
  - 사용자가 대화상자를 닫을 때 미완료 거래를 취소한다.
### 7.2 공급자 호출

mOTP 시작은 `requestServiceAuth`와 `authType=OTP01`, 검증은 `requestVerifyOtp`를 사용한다. FIDO 시작은 `requestServiceAuth`, 검증은 동일한 `svcTrId`로 `trResultConfirm`을 호출한다. 공통 성공 결과는 `resultCode=100000`이며 FIDO는 추가로 `resultData.trStatus=1`이어야 한다.

서버가 생성하는 `svcTrId`는 충돌하기 어려운 20자리 거래 식별자이며 사용자 입력을 사용하지 않는다. 외부 응답의 QR 데이터, 거래 ID, 만료시간은 길이와 형식을 검증한 뒤 필요한 값만 내부 거래에 연결한다.

## 8. 서버 메모리 상태와 원자성

로그인 대기 거래와 MFA 거래는 서버 저장소에 다음 정보를 보관한다.

- 임의 거래 ID와 필요 시 외부 거래 ID
- 사번
- 용도와 인증수단
- 상태(`PENDING`, `VERIFIED`, `CONSUMED`, `EXPIRED`, `CANCELLED`)
- 생성·검증·만료·소비 시각
- 실패 횟수

로그인 대기 거래와 MFA 거래는 애플리케이션 메모리에만 저장하며 DB 테이블, JPA 엔티티, Flyway 마이그레이션을 추가하지 않는다. 원문 증표 대신 충분한 엔트로피의 임의값에 대한 해시를 키로 사용한다. 동시 요청은 원자적 제거 연산을 사용해 1회용 증표가 한 번만 소비되게 한다.

서버 재시작 시 진행 중 거래는 모두 폐기되고 사용자는 MFA를 다시 수행한다. 다중 인스턴스 배포는 이번 범위에서 지원하지 않으며, 향후 필요하면 동일 저장소 인터페이스의 공유 캐시 구현으로 교체한다.

만료 거래 정리는 조회·검증 시 지연 정리와 별도 정리 작업을 병행할 수 있지만, 정리 작업이 실행되지 않아도 만료 검증은 항상 정확해야 한다.

## 9. 쿠키 정책

- `mfa-last-method`: 마지막 성공 인증수단 코드만 저장한다. 프론트엔드가 읽어야 하므로 httpOnly가 아니며, `SameSite=Lax`, `path=/`, 프로파일별 `Secure` 정책을 적용한다. 값이 없거나 허용 목록 밖이면 `FINGER_VEIN`을 사용한다.
- 로그인 대기 및 MFA 증표 쿠키: `HttpOnly`, `SameSite=Lax`, `path=/`, 짧은 `Max-Age`, 프로파일별 `Secure` 정책을 적용한다.
- 결재 증표는 로그아웃 시 삭제한다. 쿠키만 탈취·재전송해도 다른 계정에서 쓸 수 없도록 서버가 현재 JWT 사번과 거래 사번을 대조한다.

MFA 상태 변경 요청은 기존 인증 쿠키 요청과 동일하게 CSRF 보호 규칙을 적용한다.

## 10. 프론트엔드 구성

공통 MFA 대화상자와 composable을 만들어 로그인과 전자결재 화면이 같은 상태 기계를 사용한다.

- 인증수단 선택은 `mfa-last-method` 쿠키에서 복원한다.
- 지정맥은 BioAgent 연결, `identify`, 오류코드 조회 순서로 진행한다. 에이전트 미실행 시 실행 여부를 안내한다.
- FIDO는 QR 이미지와 남은 시간을 표시하고 제한된 주기로 서버 검증을 폴링한다.
- mOTP는 QR 이미지와 OTP 입력란을 표시하고 확인 시 서버 검증을 호출한다.
- 요청 진행 중에는 중복 클릭을 막는다.
- 대화상자를 닫으면 폴링, WebSocket, 타이머를 정리하고 취소 API를 호출한다.
- `local-ext`도 동일 UI를 표시하며 확인 버튼을 누르는 시점에 모의 검증 API가 성공한다.

전자결재의 공통 실행 래퍼는 MFA 확보 후 원래 명령 콜백을 한 번만 실행한다. 백엔드가 `MFA_REQUIRED` 또는 `MFA_EXPIRED`를 반환하면 대화상자를 다시 열 수 있게 표준 오류를 처리한다.

## 11. 오류 처리

표준 오류 코드는 다음과 같다.

- `MFA_REQUIRED`: 유효한 MFA 증표가 없다.
- `MFA_EXPIRED`: MFA 또는 로그인 대기 거래가 만료됐다.
- `MFA_FAILED`: OTP 불일치, FIDO 실패, 지정맥 실패 등 인증이 거부됐다.
- `MFA_UNAVAILABLE`: OnePass 또는 BioAgent에 연결할 수 없다.
- `MFA_LOCKED`: 한 거래의 허용 실패 횟수를 초과했다.

외부 연동에는 구성 가능한 짧은 연결·응답 타임아웃을 적용한다. 자동 재시도는 결과가 불명확한 인증 생성 요청을 중복 생성할 수 있으므로 기본적으로 수행하지 않는다. FIDO 결과 조회만 만료시간 안에서 제한된 주기로 반복한다.

오류 응답과 로그에는 사용자 조치에 필요한 코드와 정제된 메시지만 포함한다. OTP, QR 데이터, 외부 응답 전문, 쿠키·증표 원문은 기록하지 않는다.

## 12. 테스트 전략

모든 동작 변경은 TDD의 RED-GREEN-REFACTOR 순서로 구현한다.

### 백엔드

- 프로파일별 실제·모의 공급자 선택과 운영 모의 설정 기동 실패
- 로그인 자격증명 성공 후 JWT 미발급, MFA 완료 후에만 JWT 발급
- 사용자·용도 불일치, 만료, 취소, 실패 횟수 제한
- 1회용 증표의 동시 요청 중 단 한 건만 성공
- 전자결재 증표의 만료 전 1회 소비, 재사용 거부, 동시 요청 중 단 한 건만 성공
- FIDO/mOTP 요청과 응답 매핑, 결과코드·`trStatus` 판정, 타임아웃, 비정상 응답
- 전자결재 변경 API의 증표 누락·만료·소비 검증
- 외부 콜백과 조회·임시저장이 MFA 대상에서 제외되는지 검증

### 프론트엔드

- 쿠키가 없을 때 지정맥 기본 선택, 정상 쿠키 복원, 비정상 쿠키 폴백
- 로그인과 전자결재 대화상자에 인증 재사용 선택 UI가 없는지 검증
- 지정맥 WebSocket 성공·오류·정리, FIDO 폴링 종료, mOTP 입력 검증
- `local-ext` 확인 즉시 성공
- 중복 클릭과 대화상자 취소 시 자원 정리
- `MFA_REQUIRED`, `MFA_EXPIRED` 수신 후 원래 명령을 중복 실행하지 않는 재인증 흐름

### 통합 검증

- 수동 로그인 MFA 성공·실패 E2E
- 전자결재 동작마다 새 MFA를 요구하고 증표 재사용을 거부하는 E2E
- 백엔드 `test`, `check`, 필요 시 `integrationTest` 및 커버리지 검증
- 프론트엔드 `format:check`, `check`, `lint:css`, 단위 테스트, E2E, `codegen:check`

## 13. 완료 기준

- `local-ext`에서 사용자가 대화상자 확인 후 수동 로그인과 전자결재를 완료할 수 있다.
- `local-int`, `dev`, `prod`에서 선택한 실제 인증수단이 성공해야 대상 동작이 진행된다.
- 기존 수동 로그인 토큰 발급 경로로 MFA를 우회할 수 없다.
- 전자결재 변경 API를 직접 호출해도 MFA 없이는 상태를 변경할 수 없다.
- 마지막 인증수단은 쿠키로 복원되며 잘못된 값은 지정맥으로 안전하게 폴백한다.
- 전자결재 MFA 증표는 한 번만 사용할 수 있고 다음 상태 변경에는 새 MFA가 필요하다.
- SSO와 외부 전자결재 콜백은 기존 동작을 유지한다.
