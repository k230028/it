# 정보화실무협의회 상세·검토표 권한과 작성 상태 보호

- 과제: [COUNCIL-001·002](../../../../TASK_COUNCIL.md)
- 범위: 협의회 상세 GET, 타당성검토표 GET/POST/PUT. 요청·응답 DTO와 DB 스키마는 유지한다.

## 문제와 처리

목록의 부서 필터와 달리 상세·검토표는 활성 협의회 존재만 검사했다. 검토표 POST/PUT은 현재 상태에 상관없이 내용을 저장하고, 작성완료 요청이면 상태를 `02`로 덮어썼다.

`CouncilAccessGuard`를 서비스 경계에 적용한다. `CouncilService.findActiveCouncil`은 내부 상태 전이·콜백에서 사용하는 존재 조회이므로 그대로 두고, 사용자 상세 조회에는 `findReadableCouncil`, 검토표 저장에는 `findWritableDraftCouncil`을 사용한다.

| 사용자 | 상세·검토표 조회 | 검토표 저장 |
| --- | --- | --- |
| 시스템관리자 | 허용 | 사업 협의회 작성중(01)만 |
| 정보보호관리자 | 심의유형 04 허용 | 심의유형 04의 작성중만 |
| 활성 연결 사업의 주관부서 | 허용 | 작성중만 |
| 해당 협의회 활성 배정위원 | 허용 | 위원 자격만으로는 불가 |
| 미인증·다른 타입 principal·사번 누락·무관한 부서 | 거부 | 거부 |

역할은 합집합이다. 정보보호관리자라도 다른 심의유형의 주관부서 또는 배정위원이면 해당 자격에 따른 조회가 가능하다. 계획협의회(02)는 사업 복합키를 조회하지 않고 관리자·배정위원으로 판정하며 검토표 저장은 허용하지 않는다. 소유권 판단은 `OwnershipVerifier`를 재사용하고 인증 사번 누락을 먼저 거부한다.

저장은 쓰기 트랜잭션 안에서 `PESSIMISTIC_WRITE`로 원장을 잠근 뒤 활성 여부·수정 권한·현재 상태를 검사한다. 조회 잠금 제한은 3,000ms이며, `LockTimeouts`로 확인한 잠금 초과는 409로 변환한다. 권한 없음은 403, 삭제·미존재 저장 대상은 404, 작성중이 아닌 상태는 409이다. 기존 공통 오류 응답을 사용한다.

## 검증과 경계

실제 서비스와 공통 예외 처리기를 사용하는 테스트로 부서 범위, 위원 읽기/쓰기 구분, 관리자·정보보호 범위, 계획협의회, 인증 누락, 비작성중 13개 상태, 완료 후 재전송, 잠금 초과, HTTP POST/PUT의 403·409를 확인한다. 기존 협의회 테스트와 백엔드 품질 게이트도 실행한다. 실행 결과는 완료 이력에 남긴다.

이 작업은 작성중 사용자 두 명이 서로 오래된 입력을 덮는 문제까지 해결하지 않는다. 조회 시점 스탬프·병합은 COUNCIL-012, 신규 신청 및 다른 하위 API 권한은 COUNCIL-011, 프론트의 편집 가능 상태와 오류 안내 정렬은 COUNCIL-004·009에서 계속 관리한다. Oracle 실제 잠금 대기 시간과 운영 사용자 연동은 별도 검증 대상이다.
