# 공통 안내 팝업 설계

## 1. 목적

관리자가 작성한 공통 안내를 인증 사용자가 포털의 어느 업무 화면으로 처음 진입하더라도 표준 다이얼로그로 확인할 수 있게 한다. 사용자는 현재 안내 버전에 대해 “다시 보지 않기”를 선택할 수 있고, 관리자가 내용을 수정하면 새 버전의 안내를 다시 확인한다.

## 2. 범위

### 포함

- `TPRMPP_BGDOCM`을 이용한 공통 안내 팝업 단일 문서 저장
- `[관리자] > [컨텐츠 관리] > [안내 팝업 관리]` 메뉴와 관리자 화면
- 관리자용 조회·저장·게시 중지 API
- 인증 사용자용 활성 팝업 조회 API
- 공통 `AppShell` 진입 시 표준 다이얼로그 표시
- 콘텐츠 버전별 “다시 보지 않기” 쿠키
- 백엔드·프론트엔드·DB 마이그레이션 테스트와 검증

### 제외

- 로그인 화면 팝업
- 사용자·역할·부서별 노출 대상 설정
- 게시 시작일·종료일 예약
- 여러 팝업의 동시 운영과 노출 순서 관리
- 팝업 조회 실패에 대한 사용자 오류 알림

## 3. 저장 모델

기존 가이드 문서 테이블 `TPRMPP_BGDOCM`을 공유하고 컬럼을 추가하지 않는다.

| 컬럼 | 사용 방법 |
| --- | --- |
| `DOC_MNG_NO` | 기존 `SQ_TPRMPP_BGDOCM_1`을 이용한 `GDOC-{연도}-{4자리 시퀀스}` |
| `DOC_TTL_CONE` | 공통 팝업 고정 구분자 `common.popup` |
| `NAC_TXT_INF` | 서버에서 정화한 팝업 HTML 본문 |
| `DEL_YN` | `N`이면 게시 중, `Y`이면 게시 중지 |
| `LST_CHG_DTM` | 사용자 응답의 콘텐츠 버전 생성에 사용 |

활성 `GDOC-*` 행 중 `DOC_TTL_CONE='common.popup'`인 행은 한 건만 허용한다. Oracle 함수 기반 유일 인덱스는 조건에 맞는 행만 상수값으로 투영하여 동시 최초 등록도 데이터베이스에서 차단한다.

```sql
CREATE UNIQUE INDEX ITPOWN.UX_BGDOCM_COMMON_POPUP
    ON ITPOWN.TPRMPP_BGDOCM (
        CASE
            WHEN DEL_YN = 'N'
             AND DOC_MNG_NO LIKE 'GDOC-%'
             AND DOC_TTL_CONE = 'common.popup'
            THEN 1
        END
    );
```

게시 중지 후 다시 저장할 때는 새 문서번호를 발급한다. 기존 논리 삭제 행은 변경 이력으로 유지하고 재활성화하지 않는다.

## 4. 백엔드 구조와 API

담당자 정보 기능과 결합하지 않고 `common popup` 전용 패키지를 둔다. 두 기능은 같은 엔티티와 리포지토리 조회 패턴만 공유한다.

### 사용자 API

`GET /api/common-popup`

- 인증 사용자에게 허용한다.
- 게시 중인 문서가 없으면 `204 No Content`를 반환한다.
- 게시 중인 문서가 있으면 다음 값을 반환한다.

```json
{
  "docMngNo": "GDOC-2026-0001",
  "contentHtml": "<p>안내 내용</p>",
  "contentVersion": "GDOC-2026-0001:2026-09-02T10:20:30.123456"
}
```

`contentVersion`은 문서번호와 `LST_CHG_DTM`을 결합한 불투명 문자열이다. 문서번호는 게시 중지 후 재등록을 구분하고, 최종 변경시각은 같은 문서의 본문 수정을 구분한다. 클라이언트는 문자열을 해석하지 않고 쿠키 값 비교에만 사용한다.

### 관리자 API

- `GET /api/admin/common-popup`: 등록 전 상태를 포함한 현재 문서 조회
- `PUT /api/admin/common-popup`: HTML 본문 최초 등록 또는 갱신
- `DELETE /api/admin/common-popup`: 현재 문서 게시 중지

컨트롤러 클래스 수준에서 `ROLE_ADMIN`을 강제한다. 저장 요청은 HTML 본문만 받고 구분자와 문서번호는 서버가 결정한다. HTML은 `HtmlSanitizer`로 정화한 뒤 실제 표시 가능한 텍스트 또는 지원 블록이 남아 있는지 확인한다. 빈 본문은 `400 Bad Request`로 거부한다.

최초 저장은 담당자 정보 기능과 같은 별도 생성 트랜잭션 및 유일 제약 충돌 재조회 패턴을 사용한다. 갱신 응답에서 최신 `LST_CHG_DTM`이 필요할 때는 저장 후 flush하여 감사 필드가 반영된 상태로 응답을 조립한다.

게시 중지는 물리 삭제하지 않고 `DEL_YN='Y'`로 바꾼다. 활성 문서가 없을 때의 반복 DELETE는 성공으로 처리하여 관리자 UI의 재시도에 안전하게 한다.

## 5. 관리자 화면

신규 경로는 `/admin/common-popup`이며 `admin` 미들웨어를 적용한다. DB 메뉴는 상위 `MADM0010` 아래에 다음 값으로 시드한다.

- 메뉴명: `안내 팝업 관리`
- 유형: `PGE`
- 아이콘: 기존 콘텐츠 관리 계열과 어울리는 PrimeIcons 아이콘
- 관리자 권한: `ITPAD001`
- 영문 번역: `Notice Popup Management`

화면은 기존 `/admin/contact-information`의 구조를 따른다.

- `PageHeader`
- 등록 상태와 문서번호 표시
- `TiptapEditor` 본문 편집
- 저장 버튼
- 등록된 문서가 있을 때만 게시 중지 버튼
- 최초 조회 실패와 저장·게시 중지 실패의 공통 오류 매핑 및 재시도
- 한국어·영어 i18n 키

게시 중지는 확인 다이얼로그를 거친다. 저장 성공과 게시 중지 성공은 Toast로 알린다.

## 6. 사용자 다이얼로그와 노출 흐름

`AppShell`에 `CommonPopupDialog`를 한 번 마운트한다. 로그인 레이아웃은 `AppShell`을 사용하지 않으므로 대상에서 자동 제외된다. 사용자가 `/`, `/info`, `/budget`, `/admin/...` 등 어느 인증 경로로 직접 들어와도 같은 흐름이 실행된다.

1. `AppShell` 초기 진입 시 사용자 API를 한 번 조회한다.
2. 활성 문서가 없거나 본문이 비어 있으면 표시하지 않는다.
3. 응답의 `contentVersion`이 “다시 보지 않기” 쿠키 값과 같으면 표시하지 않는다.
4. 값이 다르면 표준 PrimeVue `Dialog`를 표시한다.
5. 사용자가 체크하지 않고 닫으면 쿠키를 쓰지 않는다.
6. 사용자가 “다시 보지 않기”를 체크하고 닫으면 현재 버전을 쿠키에 기록한다.

다이얼로그는 `AppDialogHeader`와 `AppDialogFooter`, 공통 다이얼로그 크기 토큰을 사용한다. 제목은 고정 문구 `안내`이고 본문 HTML은 서버 정화와 별개로 렌더 직전에 DOMPurify로 다시 정화한다.

앱 셸은 SPA 내부 라우트 이동 동안 유지되므로, 체크하지 않고 닫은 팝업을 매 화면 이동마다 다시 열지 않는다. 새로고침, 재로그인, 새 탭 직접 진입처럼 앱 셸이 새로 초기화될 때 다시 표시한다.

조회 실패는 업무 화면을 막거나 Toast를 띄우지 않고 팝업만 생략한다. 다음 앱 셸 초기화 때 다시 조회한다.

## 7. 쿠키 계약

- 이름: `it-common-popup-dismissed-version`
- 값: 서버가 반환한 `contentVersion`
- 범위: `Path=/`
- SameSite: `Lax`
- 유효기간: 1년
- Secure: 운영 HTTPS 환경에서 활성화
- HttpOnly: 사용하지 않음. 화면의 UI 선호값이므로 클라이언트가 읽고 쓴다.

콘텐츠를 수정하면 `LST_CHG_DTM`이 달라져 새 버전이 노출된다. 게시 중지 후 새 문서를 등록해도 문서번호가 달라져 다시 노출된다. 쿠키에는 HTML, 사용자 정보, 인증 정보는 저장하지 않는다.

## 8. 데이터 흐름과 실패 경계

```text
관리자 저장
  → ROLE_ADMIN 검증
  → HTML 정화·빈 내용 검증
  → BGDOCM 생성 또는 갱신
  → 감사 필드·변경로그 기록

사용자 AppShell 진입
  → 활성 common.popup 조회
  → 응답 버전과 쿠키 비교
  → 다르면 표준 다이얼로그 표시
  → 체크 후 닫기 시 버전 쿠키 저장
```

- 유일 제약 충돌: 최초 저장 경쟁으로 간주하고 활성 행을 다시 조회하여 갱신한다.
- 관리자 입력 오류: 공통 API 오류 형식으로 `400`을 반환한다.
- 사용자 조회 오류: 전역 화면은 정상 렌더링하고 팝업만 표시하지 않는다.
- 손상되거나 오래된 쿠키: 현재 버전과 일치하지 않으므로 팝업을 표시하고 정상 값으로 교체할 수 있다.

## 9. 테스트와 검증

### 백엔드

- 서비스: 미등록 조회, 최초 생성, 갱신, HTML 정화, 빈 본문 거부, 게시 중지, 동시 최초 저장 충돌
- 컨트롤러: 인증 사용자 조회, 비인증 `401`, 관리자 API 일반 사용자 `403`, 관리자 성공, 유효성 오류
- 응답 버전: 같은 문서 수정 시 변경되고 게시 중지 후 재등록 시 변경됨

### 프론트엔드

- 사용자 composable: 활성 문서 없음, 버전 일치 숨김, 버전 불일치 표시, 체크 후 쿠키 기록, 미체크 닫기
- 다이얼로그: 정화된 본문, 표준 헤더·푸터, 체크박스와 닫기 동작
- `AppShell`: 임의의 인증 경로 진입에서도 공통 컴포넌트가 한 번 마운트됨
- 관리자 화면: 조회값 편집, 저장, 게시 중지 확인, 실패와 재시도
- E2E: 서로 다른 인증 경로 직접 진입, 다시 보지 않기, 콘텐츠 버전 변경 후 재노출

### 데이터베이스

- 함수 기반 유일 인덱스 존재와 표현식 검증
- 메뉴 경로·상위 메뉴·관리자 권한·영문 번역 검증
- 활성 `common.popup` 중복 건수 0 확인

### 완료 전 명령

백엔드:

```powershell
./gradlew test
./gradlew check
./gradlew bootJar
```

프론트엔드:

```powershell
npm run format:check
npm run check
npm test
npm run lint:css
npm run test:e2e
npm run codegen:check
```

API 계약을 구현한 뒤 백엔드를 기동하여 `npm run codegen`으로 생성 타입을 갱신하고 변경분을 함께 검증한다.
