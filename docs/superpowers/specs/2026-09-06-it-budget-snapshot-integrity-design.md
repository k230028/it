# 전산예산 신청서 스냅샷 무결성 설계

## 1. 목적

전산예산 결재 신청서의 JSON 스냅샷과 원장 `BPROJM`·`BITEMM`·`BCOSTM`·`BTERMM` 사이의 불일치 위험을 줄인다. 사용자가 확인한 PDF와 실제 저장되는 신청서가 같은 서버 생성 스냅샷을 사용하게 하고, 미리보기 이후 원장이 바뀌면 상신을 원자적으로 차단한다.

이 설계의 핵심은 다음과 같다.

- 신규 상신은 서버가 생성한 전산예산 전용 v2 스냅샷만 저장한다.
- 기존 v1 JSON은 변환하거나 덮어쓰지 않고 읽기 호환을 유지한다.
- 미리보기와 상신 사이의 변경은 대상별 해시와 전체 미리보기 해시로 검출한다.
- 서버 서명된 만료형 미리보기 토큰으로 미리보기 발급 결과를 상신 요청에 결속한다.
- 상신과 원장 수정이 경합하지 않도록 부모 버전 행을 같은 규약으로 잠근다.
- 사업별 다건 상신은 결재번호를 각각 만들되 한 트랜잭션으로 처리한다.
- DB 스키마는 변경하지 않는다.

## 2. 범위

### 2.1 포함

- `/budget/report`의 사업·전산업무비 통합 상신
- `/info/projects/report`의 사업별 개별 결재 다건 상신
- 전산예산 미리보기·상신 전용 API
- v2 스냅샷 생성·정규화·해시·무결성 검증
- 원장 변경 충돌 안내 UI
- BPROJM·BITEMM·BCOSTM·BTERMM 수정 경로의 잠금 규약
- 기존 v1 스냅샷 조회 및 결재 호환
- 메일·PDF의 손상 스냅샷 실패 계약
- OpenAPI 생성 타입, 단위·통합·E2E 테스트와 운영 지표

### 2.2 제외

- 기존 v1 JSON의 일괄 변환이나 백필
- CAPPLM 등에 별도 스냅샷 이력 테이블을 추가하는 DB 변경
- 전산예산 이외 신청서의 스냅샷 구조 개편
- 결재 상태 코드나 승인 완료 후 원장 승격 규칙 변경
- 원장의 업무 필드나 금액 계산식 변경

## 3. 확인된 현행 문제

### 3.1 스냅샷 생성 책임이 프론트엔드에 있음

두 상신 화면이 원장을 조회한 뒤 `apfDtlCone`, `orcItems`, `rqsEno`, 결재선 표시 정보를 직접 조합한다. 서버의 `ApplicationService.submit`은 전달받은 JSON을 그대로 저장하고 CAPPLA 연결만 별도로 만든다. 그 결과 다음 데이터가 서로 다른 조립 경로를 가진다.

- 사용자가 확인한 PDF
- CAPPLM에 저장되는 신청서 JSON
- CAPPLA 원장 연결
- CDECIM 결재선

### 3.2 미리보기와 상신 사이 변경을 검출하지 않음

현재 서버는 연결할 원장 버전이 존재하는지만 확인한다. 미리보기 뒤 원장이나 하위 항목이 수정되어도 프론트가 갖고 있던 예전 JSON을 저장할 수 있다.

### 3.3 상신과 수정의 경쟁 조건

승인 완료 시 정확한 버전 행을 잠그는 저장소 메서드는 존재하지만, 일반 수정은 부모 행을 잠그지 않은 채 결재 진행 여부를 검사한다. 수정 트랜잭션과 상신 트랜잭션이 동시에 실행되면 양쪽 검사 모두 통과한 뒤 원장과 신청서가 어긋날 여지가 있다.

### 3.4 다건 상신의 부분 성공 가능성

`/info/projects/report`는 선택한 사업마다 별도의 상신 요청을 동시에 보낸다. 일부 요청만 성공하면 사용자가 선택한 묶음과 실제 생성된 결재 건수가 달라질 수 있다.

### 3.5 v1 검증이 얕고 읽기 경로가 분산됨

현재 v1 파서는 주요 배열을 얕게 캐스팅하며, PDF·메일·결재선 처리가 각자 JSON을 해석한다. 손상된 문서를 정상 빈 값으로 오인하거나 결재선 갱신을 조용히 생략할 위험이 있다.

## 4. 결정한 접근

### 4.1 선택안: 서버 v2 스냅샷 + 해시 비교 + 원장 잠금

서버가 미리보기와 상신 시점에 같은 빌더로 원장을 읽어 v2 문서를 만든다. 미리보기 응답에 대상별 해시와 전체 해시를 포함하고, 상신은 원장을 잠근 상태에서 스냅샷을 다시 만든 뒤 해시를 비교한다.

선택 이유:

- 기존 CAPPLM JSON 저장 구조를 유지해 DB 마이그레이션이 필요 없다.
- PDF와 최종 저장 JSON의 생성 책임을 하나로 합칠 수 있다.
- 원장별 충돌 정보와 사용자 안내를 제공할 수 있다.
- 현재의 정확한 개정 순번 연결 및 승인 완료 승격 규칙과 맞는다.

### 4.2 검토했으나 선택하지 않은 안

#### 클라이언트 JSON 유지 + 서버 검증

서버가 클라이언트 JSON을 원장과 대조하는 방식이다. 현재 구조를 덜 바꾸지만 클라이언트 DTO와 서버 원장의 의미를 계속 이중 관리해야 하며, 표시 필드 추가 때 검증 누락이 반복될 가능성이 높아 선택하지 않는다.

#### 별도 불변 스냅샷 테이블

스냅샷과 대상별 해시를 관계형 테이블로 분리하는 방식이다. 감사 추적은 가장 강하지만 이번 위험을 해결하는 데 비해 마이그레이션·운영·조회 복잡도가 크다. 향후 규제상 원장 증적이나 장기 서명 요건이 생기면 별도 과제로 재검토한다.

## 5. 전체 구조

```text
[상신 화면]
    │ sourceRefs + approver(역할, 사번)
    ▼
[ItBudgetApprovalController]
    ▼
[ItBudgetApprovalFacade]
    ├─ 권한·입력 검증
    ├─ 정확한 버전 조회/잠금
    ├─ ItBudgetSnapshotBuilder
    ├─ SnapshotDigestService
    └─ 공통 결재 저장 서비스
             ├─ CAPPLM
             ├─ CAPPLA
             └─ CDECIM

[저장된 JSON]
    ▼
[ApprovalFormSnapshotReader]
    ├─ v1 legacy adapter
    └─ v2 parser + ApprovalPayloadIntegrityVerifier
             ├─ PDF
             ├─ 결재 상태 변경
             └─ 메일
```

`ItBudgetApprovalFacade`가 양식별 오케스트레이션을 담당한다. 공통 결재 서비스는 신청서 저장과 상태 전이만 맡고 BPROJM·BCOSTM의 구조나 전산예산 스냅샷 생성 규칙을 알지 않는다.

## 6. API 계약

### 6.1 미리보기

`POST /api/applications/it-budget/previews`

요청 예시:

```json
{
  "approvers": [
    { "role": "TEAM_LEAD", "eno": "K12345" },
    { "role": "DEPT_HEAD", "eno": "K23456" },
    { "role": "ADDITIONAL", "eno": "K34567" }
  ],
  "documents": [
    {
      "clientDocumentKey": "combined-budget",
      "sourceRefs": [
        { "kind": "PROJECT", "id": "P-2026-001", "revision": 2, "order": 1 },
        { "kind": "COST", "id": "C-2026-003", "revision": 1, "order": 2 }
      ]
    }
  ]
}
```

응답 예시:

```json
{
  "previewDigest": "sha256:...",
  "previewToken": "opaque-signed-token",
  "expiresAt": "2026-09-06T15:00:00+09:00",
  "documents": [
    {
      "clientDocumentKey": "combined-budget",
      "payloadDigest": "sha256:...",
      "snapshot": {
        "form": { "id": "IT_BUDGET", "version": 2 },
        "payload": {},
        "approvalLine": {}
      },
      "sources": [
        {
          "kind": "PROJECT",
          "id": "P-2026-001",
          "revision": 2,
          "sourceDigest": "sha256:..."
        }
      ]
    }
  ]
}
```

`clientDocumentKey`는 프론트의 응답 상관관계에만 사용하며 영속 식별자로 신뢰하지 않는다. 서버는 인증 주체에서 신청자를 확정하고, 전달받은 결재자 사번으로 이름·직급·소속을 다시 조회하여 표시용 결재선을 만든다.

### 6.2 상신

`POST /api/applications/it-budget/submissions`

상신 요청은 미리보기의 `approvers`, `documents`, `previewDigest`, `previewToken`, 문서별 `payloadDigest`, 대상별 `sourceDigest`를 전달한다. 원본 `snapshot` JSON은 받지 않는다.

서버가 다음 값을 확정한다.

- 신청자 사번과 신청 부점
- 신청서 제목과 표준 결재 요청 문구
- 결재자 이름·직급·소속
- CAPPLA 원장 연결
- CDECIM 결재선
- 최종 v2 JSON과 `capturedAt`

### 6.3 미리보기 토큰

해시만으로는 클라이언트가 실제 서버 미리보기를 발급받았는지 증명할 수 없다. 서버는 다음 값을 결속한 불투명 HMAC-SHA-256 토큰을 발급한다.

- 인증된 신청자 사번
- 정규화된 신청 대상·문서 순서·결재자 입력
- `previewDigest`, 문서별 `payloadDigest`, 대상별 `sourceDigest` 집합
- 발급 시각과 30분 만료 시각
- 서명 키 ID

상신 시 서버는 토큰 서명·신청자·만료·요청 및 해시 집합의 결속을 잠금 전에 확인한다. 토큰은 해시를 인증할 뿐 원장 재검증을 대신하지 않는다. 토큰이 유효해도 상신 트랜잭션에서 원장을 잠그고 현재 해시를 다시 계산한다.

서명 키는 전산예산 미리보기 전용 환경 비밀값으로 주입하고 JWT·MFA 키와 재사용하지 않는다. 운영 프로파일은 키 누락 또는 32바이트 미만이면 기동을 실패시킨다. 키 교체 시에는 토큰의 짧은 수명 동안 직전 키 ID도 검증할 수 있게 한다.

### 6.4 화면별 문서 단위

- `/budget/report`: 선택한 사업과 전산업무비를 `documents` 한 건에 담아 결재 신청서 한 건을 만든다.
- `/info/projects/report`: 사업마다 `documents` 한 건을 구성한다. 서버는 사업별 결재번호를 유지하면서 전체 요청을 한 트랜잭션으로 저장한다.

### 6.5 입력 제한

- 문서나 신청 대상이 없으면 400
- 동일한 `(kind, id, revision)`이 전체 요청에서 중복되면 400
- 한 문서 안에서 `order`가 중복되면 400
- 문서 최대 100개, 전체 신청 대상 최대 500개
- 미지원 결재 역할이나 잘못된 결재 순서는 400
- 최초 미리보기에서 원장이 없으면 404
- 미리보기 뒤 삭제·비활성화된 원장은 변경 충돌 409

요청 DTO는 Bean Validation을 사용하고 서비스가 중복·교차 필드 규칙과 데이터 범위를 다시 검증한다.

## 7. v2 저장 문서 계약

```json
{
  "form": {
    "id": "IT_BUDGET",
    "version": 2
  },
  "payload": {
    "projects": [],
    "costs": [],
    "summary": {
      "total": "0.000",
      "asset": "0.000",
      "cost": "0.000"
    }
  },
  "approvalLine": {
    "requester": {},
    "approvers": []
  },
  "integrity": {
    "algorithm": "SHA-256",
    "canonicalization": "IT_BUDGET_V2",
    "payloadDigest": "sha256:...",
    "capturedAt": "2026-09-06T14:30:00+09:00",
    "sources": [
      {
        "kind": "PROJECT",
        "id": "P-2026-001",
        "revision": 2,
        "digest": "sha256:..."
      }
    ]
  }
}
```

### 7.1 필드 포함 기준

v2는 현재의 `ProjectDetail`이나 `ItCost` 응답 전체를 복사하지 않는다. PDF·메일이 표시하는 필드와 일관성 검증용 식별자만 가진 전용 문서 DTO를 사용한다.

포함 대상:

- 사업·계약의 관리번호와 정확한 개정 순번
- 사업명·계약명, 기준연도, 기간
- 사업·계약 설명과 신청 사유
- 업무 분류 코드와 미리보기 당시 표시명
- 부점·담당자 식별자와 미리보기 당시 표시명
- 사업 금액, 자산·비용 합계와 서버 계산 요약
- 품목의 순번·분류·명칭·수량·통화·금액·산정근거
- 계약의 통화·환율·지급일·지급 사유·정보보호 여부
- 단말기의 순번·서비스·구분·용도·명칭·통화·환율·외화 및 원화 금액
- 결재 신청자와 정규화된 결재선

제외 대상:

- 현재 결재 상태처럼 저장 뒤 바뀌는 값
- `applicationInfo`
- 화면 편집용 임시 값과 GUID
- 공통 생성·수정 감사 컬럼
- 원장에 없는 프론트 계산 전용 값

정확한 필드 목록은 PDF 렌더러와 메일 요약 코드의 필드 사용 목록에서 생성하고 계약 테스트로 누락을 막는다.

### 7.2 값 표현

- 금액: 문자열, 소수점 3자리
- 환율: 문자열, 소수점 4자리
- 수량: 문자열, 정수
- 날짜: ISO 8601 날짜
- 일시: ISO 8601 offset 일시
- 코드 표시값: `{ "code": "...", "label": "..." }`
- 부모와 자식 모두 원장 식별자를 포함

백엔드는 `BigDecimal`을 사용한다. 허용 정밀도를 넘는 값은 반올림하지 않고 데이터 오류로 실패시킨다. 텍스트는 의미가 바뀌지 않도록 임의 trim이나 유니코드 정규화를 하지 않으며, null과 빈 값을 서로 바꾸지 않는다.

## 8. 미리보기 생성

미리보기는 읽기 전용으로 다음 순서를 따른다.

1. 문서·신청 대상·결재 역할·중복·상한을 검증한다.
2. 모든 대상에 대해 인증 주체의 조회·상신 권한을 검사한다.
3. 정확한 부모 버전과 자식을 IN 배치 조회하여 N+1을 방지한다.
4. `ProjectAmountCalculator` 등 기존 서버 계산 SoT로 금액을 산출한다.
5. 코드명과 담당자 표시 정보를 배치 해석한다.
6. 전용 최소 DTO로 변환하고 순서를 정규화한다.
7. 대상별 `sourceDigest`, 문서별 `payloadDigest`, 전체 `previewDigest`를 만든다.
8. PDF에 사용할 정규화된 v2 미리보기 스냅샷을 반환한다.

부모 문서의 출력 순서는 사용자가 선택한 `order`를 보존한다. 품목과 단말기는 원장 PK 및 SNO를 기준으로 안정 정렬한다.

## 9. 해시 규칙

`SnapshotDigestService`는 전용 해시 뷰와 고정된 Jackson 설정을 사용한다.

- 문자 인코딩: UTF-8
- 알고리즘: SHA-256
- 객체 속성 및 map key: 사전순
- 부모 배열: 사용자 선택 순서
- 자식 배열: 원장 PK와 SNO 순서
- 금액: scale 3, `RoundingMode.UNNECESSARY`
- 환율: scale 4, `RoundingMode.UNNECESSARY`
- 수량: scale 0, `RoundingMode.UNNECESSARY`

대상별 `sourceDigest`에는 그 부모와 하위 항목에 저장된 업무 값과 원장 식별자를 포함한다. 공통코드·인사정보에서 해석한 표시명과 감사 필드는 제외한다. 따라서 원장 변경 표의 수정자·수정일시를 실제 원장 변경에만 귀속할 수 있다.

문서별 `payloadDigest`에는 코드·사용자 표시명을 포함한 사업·계약·요약 payload를 넣는다. 결재 상태 변경이나 결재선 상태 갱신으로 payload 무결성 값이 바뀌지 않는다.

전체 `previewDigest`에는 다음을 포함한다.

- 문서 순서와 문서별 payload
- 신청 대상 순서와 식별자
- 서버가 해석한 신청자 표시 정보
- 결재자의 역할·사번·순서와 표시 정보

`capturedAt`과 공통 감사 필드는 어떤 해시에도 포함하지 않는다. 업무 데이터가 변경됐다가 의미상 완전히 같은 문서로 원복되면 충돌로 처리하지 않는다.

## 10. 상신 트랜잭션과 잠금

### 10.1 상신 처리 순서

1. 인증·결재 상신용 MFA 증표와 미리보기 토큰의 서명·신청자·만료·요청 결속을 검증한다.
2. 모든 부모 버전을 `(kind, id, revision)` 안정 순서로 `PESSIMISTIC_WRITE` 잠근다.
3. 잠금 획득 뒤 데이터 범위와 결재 진행 여부를 다시 검사한다.
4. 부모가 잠긴 상태에서 하위 항목과 표시 정보를 배치 조회한다.
5. 현재 v2 DTO와 모든 해시를 다시 계산한다.
6. 요청의 대상별 해시와 비교하여 변경된 부모를 수집한다.
7. 대상이 같더라도 전체 미리보기 해시가 다르면 오래된 미리보기로 판정한다.
8. 충돌이 없으면 최종 `capturedAt`을 넣고 CAPPLM·CAPPLA·CDECIM과 JSON을 저장한다.
9. 커밋 이후 기존 이벤트 계약에 따라 메일과 알림을 실행한다.

`/info/projects/report` 다건도 한 서비스 트랜잭션 안에서 모든 신청서를 만든다. 어느 한 대상이라도 충돌하거나 저장에 실패하면 CAPPLM·CAPPLA·CDECIM을 모두 롤백한다.

### 10.2 공통 잠금 규약

상신만 잠그면 검사 직후 원장 수정이 커밋될 수 있으므로 다음 쓰기 경로도 부모 행을 먼저 잠근다.

- BPROJM과 BITEMM의 생성된 버전 수정·삭제
- BCOSTM과 BTERMM의 생성된 버전 수정·삭제
- 일괄 등록과 데이터 이관
- 관리자성 보정 경로

쓰기 경로는 반드시 다음 순서를 지킨다.

```text
부모 정확한 버전 잠금 → 결재 진행 여부 확인 → 부모/자식 변경 → 커밋
```

기존 `findVersionForUpdate` 계열을 재사용하고 필요한 exact-version 잠금 메서드만 보완한다. 결재 진행 중인 정확한 버전을 이관·관리자 옵션으로 우회 수정하지 않는다. 변경이 필요하면 새 개정 순번을 만든다.

잠금 순서는 항상 `kind → id → revision`으로 고정해 교착 가능성을 낮춘다. 저장소 쿼리에 5초 잠금 제한을 적용하고 초과하면 `IT_BUDGET_CONCURRENT_UPDATE` 409로 응답하여 사용자가 재시도하게 한다.

## 11. 변경 감지와 사용자 안내

### 11.1 충돌 판정

대상별 현재 해시와 미리보기 해시가 다르면 변경으로 판정한다. BITEMM이나 BTERMM만 바뀌어도 부모 사업·계약이 변경 대상이다.

변경 행의 수정자는 부모와 자식의 `LST_CHG_DTM` 중 가장 최근 값에 해당하는 사번으로 정한다. 이름은 사용자 정보를 한 번에 조회해 해석하고, 해석할 수 없으면 사번을 표시한다. 삭제된 원장은 soft-delete 행의 감사 정보를 사용하고 현재 명칭이 없으면 미리보기 명칭을 사용한다.

여러 하위 항목이 바뀌어도 부모별 한 행만 반환하며, 사용자가 선택한 대상 순서대로 정렬한다.

### 11.2 오류 응답

기존 공통 오류의 `timestamp`, `status`, `message`를 유지하고 전산예산 충돌에만 `code`와 `changedSources`를 확장한다.

```json
{
  "timestamp": "2026-09-06T14:30:00+09:00",
  "status": 409,
  "code": "IT_BUDGET_SOURCE_CHANGED",
  "message": "신청 대상이 중간에 변경되었습니다.",
  "changedSources": [
    {
      "kind": "PROJECT",
      "id": "P-2026-001",
      "revision": 2,
      "displayName": "차세대 시스템 구축",
      "modifiedBy": "홍길동",
      "modifiedAt": "2026-09-06T14:25:00+09:00"
    }
  ]
}
```

오류 코드는 다음과 같이 구분한다.

| 코드 | HTTP | 의미 |
| --- | ---: | --- |
| `IT_BUDGET_PREVIEW_INVALID` | 400 | 미발급·변조·다른 신청자 또는 요청과 결속되지 않은 토큰 |
| `IT_BUDGET_SOURCE_CHANGED` | 409 | 하나 이상의 원장 업무 내용이 변경됨 |
| `IT_BUDGET_PREVIEW_STALE` | 409 | 대상·순서·결재선 또는 표시 정보가 미리보기와 달라짐 |
| `IT_BUDGET_PREVIEW_EXPIRED` | 409 | 미리보기 토큰의 30분 수명이 만료됨 |
| `IT_BUDGET_CONCURRENT_UPDATE` | 409 | 잠금 제한을 넘겨 안전하게 상신할 수 없음 |

최초 미리보기의 권한 없음은 403, 존재하지 않는 대상은 404, 입력 계약 위반은 400으로 구분한다.

### 11.3 화면 계약

충돌 모달의 안내 문구는 다음으로 고정한다.

> 신청 대상이 중간에 변경되었습니다. 변경 내역을 확인한 후 다시 결재를 상신해 주시기 바랍니다.

표 열은 다음 네 개만 표시한다.

| NO | 사업명/계약명 | 수정자 | 수정일시 |
| ---: | --- | --- | --- |

사용자가 모달을 닫으면 현재 미리보기와 해시를 폐기하고 상신 버튼을 비활성화한다. 신청 대상을 다시 조회해 재미리보기를 완료해야 상신할 수 있다. 고정 문구는 한국어·영어 i18n 트리를 함께 추가하고, 서버의 임의 오류 문자열을 직접 화면에 표시하지 않는다.

## 12. v1 호환과 손상 처리

### 12.1 버전별 읽기

`ApprovalFormSnapshotReader`가 JSON을 한 번 파싱하고 `form.id`와 `form.version`으로 분기한다.

- v1: 기존 구조를 legacy adapter로 전용 렌더 모델에 변환하고 `LEGACY_UNVERIFIED`로 분류
- v2: 필수 객체·배열·식별자를 깊게 검증하고 `payloadDigest`를 재계산하여 확인

기존 v1 JSON은 수정·재저장·백필하지 않는다. 정상 v1 문서는 기존 PDF와 결재 흐름을 유지한다.

### 12.2 실패 계약

- v2 payload 해시 불일치: PDF와 모든 결재 상태 변경을 차단하고 무결성 실패로 기록
- v2 필수 구조 손상: 정상 빈 문서로 대체하지 않고 명시적 데이터 오류
- 진행 중 v1의 결재선 또는 핵심 문서 구조 손상: 결재선 갱신을 조용히 생략하지 않고 상태 변경 차단
- 완료된 손상 문서 조회: 오류 상태를 명확히 표시하고 원장 현재값으로 문서를 재구성하지 않음
- 메일: 신청 알림 전체를 실패시키지 않고 상세 요약을 제외한 안내 메일로 대체하되 경고 로그와 지표 발생

신규 v2 상신은 저장 전에 깊은 검증과 해시 생성을 완료하므로 정상 경로에서 손상 문서가 만들어지지 않아야 한다.

공개 API와 서비스 메서드는 입력·실패 조건을 한글 JavaDoc으로 남긴다.

## 14. 프론트엔드 책임과 예상 변경 지점

페이지는 라우팅과 화면 조합만 담당하고 공통 상신 흐름은 전산예산 composable로 분리한다.

- `/budget/report`: 통합 문서 한 건의 source refs 구성
- `/info/projects/report`: 사업별 documents 구성 후 한 번의 batch 상신
- 전산예산 approval form 폴더: v1·v2 schema와 렌더 모델 adapter 분리
- 공통 composable: 미리보기 요청, stale 상태, MFA 상신, 409 매핑
- 변경 안내 컴포넌트: 합의한 문구와 4열 `StyledDataTable`
- OpenAPI 타입: `npm run codegen`으로 생성하며 수기 편집 금지

프론트는 더 이상 다음 값을 독립 생성하지 않는다.

- `apfDtlCone`
- `orcItems`
- `rqsEno`
- 신청자·결재자 이름과 직급
- CAPPLA 원장 연결

상신 명령은 기존 `useMfaProtectedAction().runWithApprovalMfa()` 계약을 유지한다. 409는 화면 전용 모달에서 처리하므로 해당 요청에만 전역 오류 토스트를 억제한다.

## 15. 보안과 개인정보

- 신청자는 인증 주체로만 결정하고 요청의 신청자 값을 받지 않는다.
- 결재자는 클라이언트가 보낸 사번과 역할만 입력으로 사용하며 이름·직급·소속은 서버가 다시 해석한다.
- 모든 원장 조회와 상신은 동일한 서비스 데이터 범위 검사를 사용한다.
- 상신은 MFA 증표를 요구하고 한 번만 소비하는 기존 계약을 유지한다.
- 서버 서명된 미리보기 토큰으로 신청자·대상·결재선·해시·만료를 결속하고 클라이언트 생성 해시를 신뢰하지 않는다.
- 미리보기 서명 키는 JWT·MFA 키와 분리하고 로그나 응답에 원문을 남기지 않는다.
- `clientDocumentKey`, 문서 순서, CAPPLA 순서를 권한 판단 근거로 사용하지 않는다.
- 로그에는 원장 종류·식별자·버전·결재번호만 남기고 전체 JSON, 이름, 문서 본문은 남기지 않는다.

## 16. 배포와 호환 순서

DB 마이그레이션은 없다. 교차 저장소 계약은 백엔드를 먼저 배포할 수 있도록 하위 호환으로 전개한다.

1. 미리보기 서명 키를 운영 비밀값으로 준비하고, v1 공통 reader와 신규 v2 백엔드 API를 배포한다.
2. 백엔드 OpenAPI·서비스·동시성 검증을 완료한다.
3. 프론트 OpenAPI 타입을 재생성한다.
4. 두 전산예산 상신 진입점을 같은 배포에서 v2 API로 전환한다.
5. 충돌·잠금·무결성 지표가 안정적인지 확인한다.
6. 한 배포 주기 뒤 기존 범용 상신 API에서 전산예산 raw v2 사용을 거부한다.

기존 `POST /api/applications`는 다른 신청서 호환을 위해 유지한다. 전산예산의 신규 화면만 전용 API를 사용하며 v1 역사 데이터 읽기는 계속 지원한다.

## 17. 테스트 전략

### 17.1 백엔드 단위 테스트

- 동일한 aggregate는 항상 동일한 해시
- 금액·환율·수량의 의미가 같은 표기는 같은 정규형
- 정밀도 초과는 반올림하지 않고 실패
- 사업·품목·계약·단말기 표시 업무 필드 변경은 해시 변경
- 감사 필드만 변경되면 해시 유지
- 자식 입력 순서가 달라도 안정 정렬 뒤 해시 동일
- 여러 자식 변경을 부모 한 행으로 집계
- v1 정상 adapter와 v1 핵심 구조 손상 구분
- v2 정상 검증, payload 변조 및 필수 구조 누락 차단

### 17.2 백엔드 통합·계약 테스트

- 미리보기 뒤 원장 변경 시 409와 저장 0건
- 미리보기 뒤 자식만 변경해도 부모 충돌 반환
- 여러 사업 중 하나만 변경돼도 전체 상신 저장 0건
- 사업별 documents N건은 CAPPLM N건과 각 CAPPLA 1:N 생성
- CAPPLA와 CDECIM이 최종 JSON과 같은 typed input에서 생성
- 상신과 수정을 두 트랜잭션으로 경쟁시켜 둘 중 하나만 성공
- 서로 다른 입력 순서도 같은 잠금 순서를 사용
- 잠금 제한 초과 시 `IT_BUDGET_CONCURRENT_UPDATE`
- 위조한 신청자 및 결재 표시 정보가 저장되지 않음
- 미발급·변조·다른 사용자·만료 미리보기 토큰이 모두 차단됨
- 활성·직전 서명 키 ID의 토큰 검증과 알 수 없는 키 ID 차단
- 400·403·404·409가 서로 구분됨
- OpenAPI 필수·nullable·enum·오류 응답 계약

동시성 테스트는 실제 트랜잭션 두 개를 latch로 제어하여 검사와 커밋 순서를 재현한다. 영속성 잠금 검증은 Oracle 호환 프로파일에서 수행한다.

### 17.3 프론트엔드 단위·컴포넌트 테스트

- `/budget/report` 요청은 document 한 건
- `/info/projects/report` 요청은 사업별 document N건이지만 submission 호출은 한 번
- 미리보기 응답 snapshot만 PDF에 전달
- raw `apfDtlCone`과 표시용 사용자 정보를 생성하지 않음
- 변경 409를 부모 한 행씩 4열 표에 표시
- 모달 종료 후 미리보기 폐기 및 상신 비활성화
- 재미리보기 성공 뒤 상신 활성화
- stale·concurrent 오류 문구 구분
- 한국어·영어 번역 키 존재

### 17.4 E2E

- 정상 미리보기 → MFA → 통합 상신
- 사업별 다건 미리보기 → MFA → 원자적 상신
- 미리보기 뒤 원장 변경 → 합의 문구 모달 → 재미리보기 → 성공
- 미리보기 뒤 결재자 변경 → stale 안내 → 재미리보기
- 기존 v1 결재 문서 조회와 결재
- v2 손상 문서의 PDF·결재 차단

## 18. 운영 관측

다음 Micrometer 지표와 구조화 로그를 추가한다.

- 미리보기 생성 성공·실패 건수와 처리시간
- 원장 변경 409 건수와 source kind
- 미리보기 stale 건수
- 미리보기 토큰 만료·서명 실패 건수
- 잠금 제한 초과 건수
- v1 조회 건수
- v2 무결성 실패 건수
- 상신당 문서 수·원장 수·전체 처리시간

무결성 실패는 운영 경고 대상으로 분류한다. 충돌은 정상적인 동시 수정일 수 있으므로 오류 스택을 남발하지 않고 식별자와 결과 코드만 구조화해 기록한다.

## 19. 완료 기준

- 두 화면의 PDF와 최종 저장 JSON이 같은 서버 생성 스냅샷에서 나온다.
- 프론트가 raw 전산예산 스냅샷, 신청자 표시 정보, CAPPLA를 생성하지 않는다.
- 상신 요청이 서버 서명된 유효 미리보기 토큰과 결속된다.
- 미리보기 이후 원장이 바뀌면 어떤 신청서 행도 저장되지 않는다.
- BITEMM·BTERMM 변경도 부모 단위로 검출된다.
- 변경 안내가 확정 문구와 `NO | 사업명/계약명 | 수정자 | 수정일시`만 표시한다.
- 사업별 다건 상신에서 부분 성공이 발생하지 않는다.
- 원장 수정과 상신이 같은 부모 잠금 규약을 사용한다.
- 기존 v1 정상 문서를 수정 없이 조회·결재할 수 있다.
- 신규 v2 저장물은 payload 무결성을 검증할 수 있다.
- 손상된 문서를 정상 빈 문서로 표시하거나 조용히 결재하지 않는다.
- 백엔드 OpenAPI 계약을 기준으로 프론트 타입이 재생성된다.
- 백엔드·프론트 전체 Health Stack과 관련 E2E가 통과한다.

## 21. 기존 설계 선례와의 정합성

Graphify 코드 지식 그래프에서 확인한 다음 기존 선례를 따른다.

- `Project and Budget Domain Schema`: 사업·업무비의 부모/자식 aggregate 경계
- `Cappla Per-Application 1~N Numbering`: 신청서별 원장 연결과 다건 결재번호 유지
- `@Valid·Bean Validation 컨트롤러 일관화`: 경계 입력 검증
- `ParsedSnapshot 단일 파서`, `ERR-08 스냅샷 손상 부분 결과`, `snapshotIncomplete 계약`: JSON을 한 번 파싱하고 손상을 정상 빈 값으로 숨기지 않는 실패 계약
- `최신 PDF revision 상태 머신`: 정확한 개정 순번을 끝까지 보존하는 원칙
- `비관적 잠금 기반 원자적 버전 전환`: 상태 검사와 저장을 같은 잠금 경계에서 수행
- `4-repo commit ordering (backend contract first, frontend follows)`: 백엔드 계약 선행 후 생성 타입으로 프론트 전환
