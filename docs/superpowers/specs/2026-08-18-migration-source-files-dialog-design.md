# 편성요청서 반입 원본 파일 조회 설계

작성일: 2026-08-18

## 1. 배경

`/admin/migration/requests`(편성요청서 반입)는 부점이 제출한 엑셀을 파싱해 정보화사업
(`BPROJM`)·전산업무비(`BCOSTM`) 원장을 만들고, `MigrationApprovalStamper`가
`[편성요청서 반입]` 제목의 결재완료 받이(`CAPPLM`/`CAPPLA`)를 붙인다.

문제는 **업로드한 엑셀이 어디에도 남지 않는다**는 점이다.
`RequestFormFileImporter`는 파싱이 끝나면 파일을 버린다. 반입 받이 `CAPPLM`에는
신청서 본문(`APF_DTL_CONE`)이 없으므로, 결재현황에서 신청서를 열면
`ApplicationViewerDialog`가 `layout.viewer.missingDetails` 오류만 낸다.

반입한 건은 애초에 결재선을 거치지 않아 신청서라는 산출물이 없다. 이 자리에서
사용자가 실제로 확인해야 하는 것은 **부점이 제출한 원본 엑셀**이다.

## 2. 목표

1. 반입 시 업로드한 엑셀을 서버에 보관한다.
2. 결재현황에서 반입 건의 신청서를 열면, 신청서 PDF 대신 **업로드 파일 목록**을 보여준다.
3. 목록의 파일은 다운로드할 수 있다.
4. 한 건에 파일이 2개 이상 붙는 경우를 정상 케이스로 다룬다.

## 3. 범위 밖

- 엑셀 내용을 브라우저에서 표로 미리 보기 (다운로드까지만 한다)
- 이번 변경 이전에 반입된 건의 원본 소급 복원 (파일이 존재하지 않는다)
- 반입 파일의 수정·삭제 UI
- 반입 화면(`/admin/migration/requests`) 자체의 UX 변경

## 4. 확정한 결정

| 항목 | 결정 |
| --- | --- |
| "동일건"의 단위 | **부점 폴더**. 한 폴더의 파일 전부가 그 폴더에서 생성된 모든 원장에 붙는다 |
| 보관 수준 | 원본 보관 + 목록 + 다운로드 |
| 진입점 | `/budget/list`와 `/approval` 양쪽 (같은 뷰어 컴포넌트를 쓰므로 한 번에 적용) |
| 기존 반입분 | 반입 건으로 판별하되 목록이 비므로 안내 문구를 낸다 |
| 저장 구조 | `TPRMPP_CFILEM` 단독. 신규 테이블 없음 |
| 열람 권한 | 관리자 전체 + 해당 부점 사용자 |
| BLOCKED 파일 | **보관하지 않는다** |

### 4.1 BLOCKED 파일을 보관하지 않는 이유

BLOCKED 파일은 원장을 만들지 않아 자기 신청서번호가 없다. 보관하려면 같은 부점 폴더의
APPLIED 건에 얹는 수밖에 없는데, 그러면 "이 사업의 원본"을 열었을 때 그 사업과 무관한
반입 실패 파일이 섞여 나온다. 반입 실패는 반입 화면의 진단 결과가 다루는 영역이고
결재현황이 다룰 일이 아니다. 따라서 **APPLIED 파일만 보관한다.**

## 5. 데이터 설계

신규 테이블·Flyway 스크립트는 없다. 기존 공통첨부파일 `TPRMPP_CFILEM`만 쓴다.

| 컬럼 | 값 |
| --- | --- |
| `PK_COL_NM` | `편성요청서반입` (신규 파일 종류) |
| `PK_CONE` | 반입 받이 신청서번호 (`APF-{연도}-{8자리}`) |
| `FL_NM` | 업로드 원본 파일명 |
| `FL_PYS_NM` / `FL_KPN_PTH` | 물리 파일 위치. **같은 파일을 가리키는 행이 여럿일 수 있다** |
| `FL_TP_CONE` | `첨부파일` |

### 5.1 물리 파일은 1벌, 메타행은 원장 수만큼

부점 폴더 하나에서 파일 3개가 원장 20건을 만들면, 필요한 연결은 60개다.
그때마다 디스크에 쓰면 같은 엑셀이 60벌 쌓인다.

그래서 **파일당 디스크 기록은 1회**로 하고, 두 번째 원장부터는 `FL_PYS_NM`·`FL_KPN_PTH`를
공유하는 `CFILEM` 행만 추가한다.

물리 파일 공유가 안전한 근거는 삭제가 논리 삭제이기 때문이다.
`FileService.deleteFile`과 `deleteFilesByOrc`는 `DEL_YN='Y'`만 세우고 디스크에 손대지
않으므로(`FileService.java:390`, `:427`), 한 행을 지워도 형제 행의 다운로드가 깨지지 않는다.
**이 전제가 깨지면(물리 삭제 도입) 이 설계도 함께 고쳐야 한다.**

### 5.2 왜 신청서번호를 키로 쓰는가

원장 PK(사업관리번호)나 `{예산연도}-{부서코드}` 파생키도 후보였다.
신청서번호를 고른 이유는 두 진입점이 모두 `apfMngNo`를 이미 들고 있고,
주관부서를 나중에 수정해도 연결이 끊기지 않기 때문이다.
파생키 방식은 주관부서를 바꾸는 순간 첨부가 조용히 사라진다.

## 6. 백엔드 변경

### 6.1 반입 시 파일 보존

`RequestFormImportService.importBatch`의 **commit 경로에만** 보존 단계를 추가한다.
dry-run은 아무것도 저장하지 않는다.

1. 파일별 반영이 모두 끝난 뒤, 결과를 부점(`deptCode`) 기준으로 묶는다.
2. 각 부점 그룹에서 **APPLIED 파일만** 추린다.
3. 그룹의 파일을 디스크에 1벌씩 저장한다.
4. 그룹에서 생성된 모든 신청서번호 × 파일에 대해 `CFILEM` 행을 만든다.

`FileService`에 "이미 저장된 물리 파일을 다른 부모에 추가 연결" 메서드를 하나 더한다.
`uploadFile`을 반복 호출하면 디스크 중복이 생기므로 재사용할 수 없다.

**트랜잭션 경계**: 원장 반영(`REQUIRES_NEW`, 파일 1건 = 1 트랜잭션)이 전부 끝난 뒤
별도 트랜잭션에서 보존한다. 보존이 실패해도 원장은 살아남고, 그 건은 기존 반입분과
동일하게 "빈 목록 + 안내" 상태가 된다. 순서를 뒤집으면 첨부 실패가 정상 반입을 통째로
되돌리게 되어 더 나쁘다. 실패는 ERROR 로그로 남긴다.

반입 받이 신청서번호는 현재 `MigrationApprovalStamper.stamp`가 반환하지만
`RequestFormFileImporter`가 버리고 있다. `CreatedRecord`에 신청서번호를 실어
`ImportService`까지 올린다.

### 6.2 반입 건 판별

`ApplicationDto.Response`에 `migrated` 필드(boolean)를 추가한다.
서버는 `CAPPLM.RGPR_DCD_REQ_CONE`가 `MigrationApprovalStamper.MIGRATION_NOTE`와
같은지로 계산한다. 이 상수는 서버 소유이므로 문자열 비교가 계약을 넘지 않는다.

이 방식이면 기존 반입분도 자동으로 `migrated=true`가 되어, 파일 0건 + 안내 문구로 흐른다.

### 6.3 조회

신규 API를 만들지 않는다. 기존 `GET /api/files?pkColNm=편성요청서반입&pkCone={apfMngNo}`를
그대로 쓴다.

### 6.4 권한

`FileReadAuthorizer` 구현체 `RequestFormFileReadAuthorizer`를 `편성요청서반입` 종류로
등록한다. 등록하지 않으면 `FileReadAuthorizerRegistry`의 default-deny로 관리자만 보게 된다.

- 관리자(`user.isAdmin()`) → 허용
- 그 외 → `PK_CONE`(신청서번호) → `CAPPLA` → 원장 → 주관부서코드를 찾아
  사용자 부서와 일치할 때만 허용
- 미인증 → 거부

`getFiles`는 `pkCone` 없이 종류 전체 조회도 허용하지만, 같은 판정기가 행마다 걸리므로
타 부점 파일은 걸러진다.

## 7. 프론트엔드 변경

### 7.1 뷰어 내부 분기

`ApplicationViewerDialog.vue`가 `fetchApplication` 결과의 `migrated`를 보고 갈라진다.

- `migrated === true` → PDF 렌더러를 타지 않고, 파일 목록을 조회해 목록 본문을 그린다.
  다이얼로그 제목도 "반입 원본 파일"로 바꾼다.
- `migrated !== true` → 지금의 `renderApprovalForm` + iframe 경로를 그대로 둔다.

별도 다이얼로그를 새로 만드는 안은 기각했다. 그러면 `/approval`과 `/budget/list`
양쪽 목록 DTO에 반입 여부 플래그를 내리고 두 화면을 각각 고쳐야 한다.
두 화면이 이미 같은 뷰어를 쓰므로 뷰어 안에서 가르는 편이 변경 범위가 작다.

### 7.2 파일 목록 컴포넌트

`components/migration/RequestFormSourceFiles.vue`를 새로 만든다.

- props: 파일 배열 하나
- 책임: 표시와 다운로드 요청뿐. 조회·판별은 뷰어가 하고 이 컴포넌트는 모른다
- 표시 항목: 파일명, 크기, 반입일시
- 클릭 시 기존 `useFiles`의 다운로드 경로를 탄다
- 목록이 비면 "보관된 업로드 파일이 없습니다" 안내를 낸다

모든 문구는 i18n 키로 넣는다(`npm run check:copy` ratchet 대상).

## 8. 검증

### 8.1 백엔드

- commit이 부점 그룹별로 APPLIED 파일만 보존하는지
- BLOCKED 파일이 보존되지 않는지
- 같은 파일의 두 번째 연결이 디스크에 다시 쓰지 않고 `FL_PYS_NM`을 공유하는지
- dry-run이 아무것도 저장하지 않는지
- 보존이 실패해도 원장이 남는지
- `RequestFormFileReadAuthorizer`가 관리자 / 동일 부점 / 타 부점 / 미인증을 가르는지
- `migrated` 플래그가 반입 받이에 true, 일반 신청서에 false인지 (MockMvc)

### 8.2 프론트엔드

- `migrated=true`일 때 PDF 렌더러가 호출되지 않고 파일 목록이 그려지는지
- `migrated=false`일 때 기존 경로가 유지되는지
- 파일 0건일 때 안내 문구가 뜨는지

### 8.3 게이트

`./gradlew check`, `npm run check`, `npm test`, `npm run codegen:check`
(`ApplicationDto.Response` 변경으로 프론트 생성 타입이 함께 바뀐다).

## 9. 기각한 대안

| 대안 | 기각 사유 |
| --- | --- |
| 반입묶음 + 매핑 테이블 신설 | `CFILEM`만으로 충분하다. 논리 삭제라 물리 파일 공유가 안전하다는 사실을 확인한 뒤 철회했다 |
| 원장마다 파일을 다시 업로드 | 같은 엑셀이 생성 건수만큼 디스크에 쌓인다 |
| `{예산연도}-{부서코드}` 파생키 | 주관부서를 수정하면 첨부 연결이 조용히 끊긴다 |
| 목록 DTO에 반입 플래그 추가 | 두 화면의 DTO와 화면을 각각 고쳐야 한다. 뷰어가 이미 호출하는 단건 조회로 충분하다 |
| 메타데이터만 기록하고 원본 미보관 | 근거자료 추적이 되지 않는다 |
