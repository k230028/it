# 2026 편성요청서 반입 보강 설계

작성일: 2026-08-19

## 1. 배경

`sample/2026`에 보강된 부점 제출 자료 61건을 현재 편성요청서 반입 로직으로 점검했다.
Excel 44건은 모두 열렸고, 이 가운데 편성요청서 시트를 가진 32건은 파싱 대상으로,
나머지 12건은 증빙 Excel로 식별되었다. Oracle 읽기 전용 dry-run 기준으로 파싱 대상은
20건 `APPLIED`, 12건 `BLOCKED`였다.

대부분의 `BLOCKED`는 비목·금액 단위·빈 필수값처럼 관리자가 확인해야 하는 정상 진단이다.
반면 다음 네 가지는 제출 자료의 정상 변형을 현재 코드가 충분히 수용하지 못해 발생한
구조적 문제다.

1. 신양식 자본예산 1-2는 `구분`이 B열, `항목`이 C열인데, 현재 리더는 그룹 열을 C열로
   고정한다. 그 결과 `기계장치(HW)`·`기타무형자산(SW)` 대신 품목 설명을 비목 그룹으로
   읽어 `CODE_UNRESOLVED`를 만든다.
2. 신양식 자본예산 1-1의 합계 라벨은 `계`인데, 현재 리더는 `총 계`·`총계`만 찾는다.
   선언 금액을 읽지 못해 금액 대사와 단위 판단의 근거가 약해진다.
3. 실제 제출본에는 `IDT본부장`, 부가 설명이 붙은 `추진계획 검토중` 같은 표기가 있다.
   현재 옵션 어휘는 정확히 일치할 때만 정규화하여, 의미가 이미 확정적인 표기도 코드
   미해석으로 남는다.
4. 원본 보관 단위가 `부서명 + 부서코드`이고 프론트 배치가 파일 20개 단위라서, 같은
   부서 아래 여러 사업의 증빙이 서로 섞이거나 같은 사업의 요청서와 증빙이 서로 다른
   요청으로 갈릴 수 있다. 또한 편성요청서 시트가 없는 증빙 Excel은 `SKIPPED`되면서
   유효 부서코드를 잃어 보관 대상에서 빠진다.

## 2. 목표

1. 구양식과 신양식의 자본예산 자원표를 모두 같은 리더로 정확히 해석한다.
2. `계` 합계 행과 확인된 옵션 표기를 안전하게 정규화한다.
3. 요청서와 PDF·HWP·증빙 Excel을 사업 폴더 단위로만 연결한다.
4. 같은 보관 그룹은 하나의 HTTP 배치에 유지한다.
5. 실제 전송 파일 수와 처리 요약의 `totalFiles` 의미를 일치시킨다.
6. 업무 판단이 필요한 기존 차단 진단은 자동 추정으로 우회하지 않는다.

## 3. 범위 밖

- `외주용역`처럼 여러 공통코드 후보가 가능한 비목의 임의 자동 매핑
- 금액 단위, 빈 사업명·금액, 실제/계획 구분 등 제출자가 확정해야 하는 값의 자동 보정
- 한 사업 폴더가 서버 상한 50개를 넘을 때 여러 HTTP 요청을 하나의 보관 트랜잭션으로
  묶는 업로드 세션 도입
- 기존에 반입된 원본 파일의 소급 재분류
- DB 스키마, 공통코드 또는 OpenAPI DTO 변경

## 4. 접근 방식과 결정

### 4.1 검토한 방식

| 방식 | 장점 | 단점 | 결정 |
| --- | --- | --- | --- |
| `fileKey`에서 보관 그룹 계산 | API 변경 없음, 현재 폴더 업로드 흐름과 바로 결합 | 프론트·백엔드에 같은 규칙을 구현해야 함 | **채택** |
| `archiveGroupKey`를 API DTO에 추가 | 그룹이 요청에 명시됨 | OpenAPI·생성 타입 변경, 클라이언트 입력 신뢰 문제 | 보류 |
| 서버 업로드 세션 도입 | 50개 초과 그룹도 여러 요청에 걸쳐 연결 가능 | 영속 상태·만료·재시도 설계가 추가됨 | 범위 밖 |

### 4.2 API를 유지하는 이유

보관 그룹은 사용자가 새로 입력하는 업무 데이터가 아니라 이미 전달되는 `fileKey`의 폴더
구조에서 결정되는 전송 메타데이터다. 현재 문제를 해결하기 위해 외부 계약을 늘릴 필요가
없다. 프론트는 그룹 보존 배치에, 백엔드는 첨부 연결 제한에 같은 순수 규칙을 사용한다.
양쪽의 계약 테스트에 동일한 경로 예시와 기대 그룹 키를 두어 규칙의 이탈을 막는다.

## 5. 상세 설계

### 5.1 자본예산 자원표 그룹 열

`ResourceTableReader`는 자본예산 1-2 헤더를 찾은 뒤 `item` 열 위치로 그룹 열을 결정한다.

- 기존 기본 그룹 열 C(0-based 2)가 `item` 열보다 왼쪽이면 기존 C열을 유지한다.
- 기본 그룹 열과 `item` 열이 같거나 오른쪽이면 `item - 1` 열을 그룹 열로 쓴다.
- 결과 열 번호는 0보다 작아지지 않게 한다.

이 규칙은 기존 양식의 `구분=C, 항목=D`와 중간 보조 열이 있는 양식의 C열을 유지하면서,
신양식의 `구분=B, 항목=C`만 B열로 이동한다. 데이터 내용이나 공통코드 조회 성공 여부로
열을 추정하지 않으므로 제출 값이 비어 있어도 레이아웃 판정은 결정적이다.

### 5.2 `계` 합계 행

`CapitalOverviewReader.declaredAmounts()`의 합계 라벨 후보에 `계`를 추가한다. 검색 열은
현재와 같이 A/C열(0, 2)로 제한하고, 정확히 정규화된 셀 값만 일치시키므로 문장 속 `계`나
일반 데이터 셀을 합계 행으로 오인하지 않는다. 기존 `총 계`·`총계` 우선순위는 유지한다.

합계 행을 찾은 뒤의 연도 합계 컬럼 탐색, 합계 셀이 비었을 때 데이터 행을 더하는 폴백,
전체기간 금액 단위 판정은 변경하지 않는다.

### 5.3 옵션 어휘 정규화

`FormLexicon`에 다음 확인된 별칭을 추가한다.

- `IDT본부장` → `부문(본부)장`

`canonicalOptionName()`은 먼저 기존 정확 일치를 수행한다. 정확 일치가 없을 때만 정규화된
원문에 포함된 등록 별칭을 찾는다.

- 포함된 별칭들이 모두 같은 표준값으로 수렴하면 그 표준값을 반환한다.
- 서로 다른 표준값이 하나의 원문에 포함되면 자동 결정하지 않고 원문을 반환한다.
- 등록 별칭이 없으면 기존처럼 원문을 반환한다.

따라서 `추진계획 검토중 (유관부서검토 여부 : ) (변동가능성 有), N`은 두 별칭이 모두
`미정(검토중)`으로 수렴하여 해석된다. 반면 서로 다른 옵션 문구가 섞인 비정상 셀은 기존
차단 진단으로 남는다.

### 5.4 보관 그룹 키

프론트와 백엔드는 `fileKey`를 다음 순서로 정규화한다.

1. `\\`를 `/`로 바꾸고 빈 경로 조각을 제거한다.
2. 파일명을 제외한 폴더 중 `부서명(영숫자코드)` 규칙을 만족하는 가장 안쪽 폴더를
   부서 폴더로 찾는다. 없으면 첫 폴더를 사용한다.
3. 부서 폴더 아래에서 `숫자.`으로 시작하는 첫 폴더를 찾으면 그 폴더까지의 경로를 그룹
   키로 사용한다. 예: `01. (자본예산) 스마트워크 인프라`.
4. 번호 폴더가 없고 부서 아래 폴더가 있으면 첫 하위 폴더까지를 그룹 키로 사용한다.
   예: `_품질관리팀`.
5. 부서 바로 아래 파일이면 부서 폴더까지를 그룹 키로 사용한다.

그룹 키는 선택 루트부터 위에서 결정한 폴더까지의 `/` 구분 상대경로다. 파일명은 포함하지
않는다. 번호 폴더 아래의 견적서 하위 폴더는 같은 사업 그룹에 남는다.

예시는 다음과 같다.

| `fileKey` | 보관 그룹 키 |
| --- | --- |
| `2026/IT기획부(180)/_품질관리팀/요청서.xlsx` | `2026/IT기획부(180)/_품질관리팀` |
| `2026/IT기획부(180)/_품질관리팀/근거.pdf` | `2026/IT기획부(180)/_품질관리팀` |
| `2026/IT기획부(180)/_IT인프라팀/붙임2/01. VDI/요청서.xlsx` | `2026/IT기획부(180)/_IT인프라팀/붙임2/01. VDI` |
| `2026/IT기획부(180)/_IT인프라팀/붙임2/01. VDI/(견적서)/견적.pdf` | `2026/IT기획부(180)/_IT인프라팀/붙임2/01. VDI` |
| `2026/PF2실(127)/요청서.xls` | `2026/PF2실(127)` |

경로 조각의 대소문자와 공백은 원문을 유지한다. 동일 업로드 안에서 브라우저가 전달하는
`fileKey`가 단일 출처이므로 임의 소문자화나 이름 변환은 하지 않는다.

### 5.5 그룹 보존 배치

`useRequestFormUpload`는 파일을 먼저 보관 그룹별 `LinkedHashMap`에 모아 최초 등장 순서를
유지한다. 이후 목표 크기 20을 기준으로 그룹 전체를 배치에 넣는다.

- 현재 배치에 다음 그룹을 더했을 때 20개를 넘고 현재 배치가 비어 있지 않으면 현재
  배치를 닫는다.
- 단일 그룹이 20개보다 크고 50개 이하이면 그 그룹 하나를 한 배치로 보낸다.
- 단일 그룹이 서버 상한 50개를 넘으면 실행 전에 명시적인 오류를 던진다. 그룹을 나누어
  일부 증빙의 연결이 사라지는 것보다 안전하다.
- dry-run과 commit은 같은 배치 계산을 사용한다.

일반 `chunk<T>()`는 더 이상 반입 배치를 담당하지 않는다. 사용처가 없으면 제거하고,
보관 그룹을 입력으로 받는 전용 함수로 책임을 명확히 한다.

### 5.6 백엔드 보관 계획

`RequestFormImportService`는 모든 manifest 항목에 대해 `fileKey`에서 보관 그룹 키를
계산하여 `ArchivePlanItem`에 담는다.

- `archiveOnly=true`: 지금처럼 부서코드를 해석하고 결과 없이 보관 계획에 넣는다.
- 편성요청서 시트 있음: 처리 결과와 실제 적용 부서코드를 보관 계획에 넣는다.
- 편성요청서 시트 없음: 결과는 `SKIPPED`로 유지하되 부서코드를 해석하여 보관 계획에
  넣는다. 이 파일은 APF를 만들지 않지만 같은 그룹의 APF에 연결될 수 있다.
- 부서코드를 해석하지 못한 파일은 기존처럼 보관하지 않는다.

`RequestFormSourceFileArchiver`의 그룹 키는 `(archiveGroupKey, effectiveDeptCode)`로 바꾼다.
같은 부서라도 사업 그룹이 다르면 파일과 APF 번호가 절대 섞이지 않는다. 한 그룹 안에서는
`APPLIED` 결과가 만든 모든 APF 번호를 수집하고, `APPLIED`·`SKIPPED`·보관 전용 파일을
그 번호들에 연결한다. `BLOCKED` 파일은 APF를 만들지 않지만 같은 그룹에 정상 반영된
요청서가 있을 때 원본 자료의 일부로 연결된다. 이는 파일 처리 상태가 아니라 제출 사업
폴더를 보관 단위로 삼는 이번 설계의 결과다.

파일당 물리 저장 1회, 두 번째 APF부터 메타행만 연결하는 기존 동작과 보관 실패를 원장
반영 실패로 되돌리지 않는 예외 정책은 유지한다. 로그에는 부서명 대신 보관 그룹 키와
부서코드를 남겨 문제 범위를 식별할 수 있게 한다.

### 5.7 처리 요약

`RequestFormImportService`는 `summarize(results.size(), results)` 대신
`summarize(files.size(), results)`를 사용한다. `ImportSummary.totalFiles`의 DTO 설명인
“보낸 파일 수”와 실제 값을 맞춘다. `archiveOnly` 파일은 결과 목록에는 없지만 전체 파일
수에는 포함된다. `appliedFiles`, `blockedFiles`, 생성 건수 계산은 변경하지 않는다.

## 6. 데이터 흐름

1. 브라우저가 폴더에서 임시 Excel 파일을 제외하고 모든 파일을 수집한다.
2. 각 파일의 부서 폴더와 보관 그룹 키를 `fileKey`에서 계산한다.
3. 같은 보관 그룹을 나누지 않는 배치를 만들고 dry-run 또는 commit API를 호출한다.
4. 백엔드는 Excel을 열어 요청서 시트 유무를 분류하고, 모든 파일의 보관 그룹 키를 다시
   계산한다.
5. commit에서 파일별 원장 반영이 끝난 후 그룹별 APF 번호와 원본 파일을 결합한다.
6. 각 원본은 첫 APF에 물리 저장하고 같은 그룹의 나머지 APF에는 기존 파일을 연결한다.
7. 응답 요약은 실제 전송 파일 수와 파일별 처리 결과를 각각 집계한다.

## 7. 오류 처리와 안전성

- 보관 그룹 키 계산은 파일 시스템에 접근하지 않는 순수 함수로 만든다.
- 경로에 폴더가 없으면 빈 그룹 키를 반환한다. 백엔드 보관기는 빈 그룹을 건너뛴다.
- 부서코드 해석 실패는 기존 진단·차단 정책을 유지하고 보관 대상에서도 제외한다.
- 50개 초과 단일 그룹은 프론트에서 실행 전에 중단하며 그룹 경로와 파일 수를 오류에
  포함한다.
- 옵션 포함 매칭이 여러 표준값으로 갈리면 자동 선택하지 않는다.
- 보관 실패는 기존처럼 ERROR 로그만 남기며 이미 커밋된 원장을 실패로 되돌리지 않는다.
- 경로 그룹은 첨부 연결 범위만 제한한다. 부서코드 검증, 원장 생성, 권한 판정에는 사용하지
  않는다.

## 8. 파일 구조와 책임

### 백엔드

- `RequestFormArchiveGroup.java` 신규: `fileKey`와 `deptName`에서 정규화된 보관 그룹 키를

## 9. 테스트 전략

모든 제품 코드 변경은 실패 테스트를 먼저 추가하는 TDD 순서로 진행한다.

### 백엔드 단위 테스트

- `ResourceTableReaderTest`
  - `구분=C, 항목=D` 기존 양식이 C열 그룹을 유지한다.
  - `구분=B, 항목=C` 신양식이 B열 그룹을 읽는다.
  - `항목=E`이고 C열이 그룹인 중간 열 양식이 C열을 유지한다.
- `CapitalDeclaredAmountsTest` 또는 `CapitalOverviewReaderTest`
  - `계` 행에서 당해연도·이후 합계를 읽는다.
  - 기존 `총 계`·`총계`도 그대로 읽는다.
- `FormLexiconTest`
  - `IDT본부장`을 `부문(본부)장`으로 바꾼다.
  - 복합 추진가능성 문구가 `미정(검토중)`으로 수렴한다.
  - 서로 다른 표준값이 포함되면 원문을 유지한다.
- `RequestFormArchiveGroupTest`
  - 번호 사업 폴더, 팀 폴더, 부서 직속 파일, Windows 구분자, 빈 경로를 검증한다.

### 백엔드 서비스 테스트

- `RequestFormImportServiceTest`
  - `SKIPPED` Excel도 해석된 부서코드와 그룹 키로 보관 계획에 포함된다.
  - `archiveOnly`를 포함한 응답의 `totalFiles`가 실제 전송 수와 같다.
- `RequestFormSourceFileArchiverTest`

  - 같은 그룹의 요청서·`SKIPPED` Excel·PDF가 그 그룹의 APF에 모두 연결된다.
  - 다른 부서코드는 같은 경로 그룹처럼 보여도 분리된다.

### 프론트엔드 단위 테스트

## 10. 완료 기준

1. 신양식의 B열 자원 그룹과 `계` 합계를 읽는다.
2. 확인된 `IDT본부장`·복합 추진가능성 표기가 코드로 해석된다.
3. 같은 부서의 서로 다른 번호 사업 폴더가 서로의 원본을 공유하지 않는다.
4. 요청서와 같은 그룹의 증빙 Excel·PDF·HWP가 해당 APF에서 조회된다.
5. 한 보관 그룹은 HTTP 배치 사이에서 나뉘지 않는다.
6. `totalFiles`가 manifest/files로 전송한 실제 파일 수와 같다.
7. 백엔드·프론트엔드 전체 품질 게이트와 2026 샘플 회귀 검증을 통과한다.
8. DB·OpenAPI 계약은 변경되지 않는다.
