# 한국어·영어 다국어 적용 설계

- 작성일: 2026-08-15
- 대상 저장소: `it_database`, `it_backend`, `it_frontend`
- 기본 언어: 한국어(`ko`)
- 지원 언어: 한국어(`ko`), 영어(`en`)
- 언어 저장 위치: 브라우저 쿠키 `it-portal-locale`

## 1. 배경과 목표

IT 정보화 포탈의 사용자 화면을 한국어와 영어로 제공한다. 사용자가 상단 언어 선택기에서 언어를
바꾸면 현재 URL과 작업 상태를 유지한 채 화면 고정 문구, 시스템 메뉴, 공통코드 표시명이 함께
전환되어야 한다.

현재 프론트엔드는 Nuxt 4와 PrimeVue 4를 사용하며 별도 i18n 모듈이 없다. PrimeVue 로케일은
`nuxt.config.ts`에 한국어로 고정되어 있고, 날짜·숫자 포맷에도 `ko-KR` 리터럴이 존재한다. 사용자
메뉴는 `/api/menus`가 반환하는 `TPRMPP_CMENUM.MNU_NM`이 헤더·사이드바·Breadcrumb·탭 제목의
단일 출처다. 공통코드도 여러 화면이 `CDVA_NM`, `CO_CDVA_ABV_NM`, `CO_CDVA_SPS` 등을 직접 표시한다.

목표는 다음과 같다.

1. 쿠키가 없거나 올바르지 않으면 항상 한국어로 시작한다.
2. 언어 전환으로 URL, 라우트, 열린 탭, 입력 중인 폼 상태가 바뀌지 않는다.
3. 화면 고정 문구와 PrimeVue 내장 문구를 선택 언어로 표시한다.
4. 시스템 메뉴와 공통코드 표시명은 DB에서 관리하며 관리자가 한국어 원본과 영어 번역을 편집한다.
5. 영어 번역이 없으면 해당 필드만 한국어 원본으로 안전하게 대체한다.
6. 언어별 프론트·백엔드 캐시를 분리해 다른 언어의 응답이 재사용되지 않게 한다.
7. 이후 언어 추가 시 기존 업무 테이블에 언어별 컬럼을 추가하지 않는다.

## 2. 범위

### 2.1 포함

- 화면 제목, 버튼, 표 컬럼, 라벨, placeholder
- Toast, 확인창, 오류·빈 상태·로딩 문구
- `aria-label`, `title` 등 접근성 문구
- 날짜, 숫자, 금액, 단위의 로케일별 표시
- PrimeVue DatePicker·필터·업로드 등 내장 문구
- 헤더·사이드바·Breadcrumb·상단 탭의 시스템 메뉴명
- 공통코드의 사용자 표시용 명칭·약어·적요
- 로그인 화면과 로그인 후 공통 셸의 언어 선택
- 관리자 메뉴·공통코드 화면의 영어 번역 등록·수정·삭제
- 프론트가 사용자에게 표시하는 표준 API 오류 문구

### 2.2 제외

- 사용자가 입력한 게시글, 사업명, 문서 제목·본문
- DB 기술 식별자, 코드값, 업무 분기용 값
- 개발 로그, 소스 주석, OpenAPI 설명
- PDF, HWPX, Excel 등 공식 출력 서식의 본문 번역
- `TPRMPP_CMENUD.SRE_MNU_NM` 화면경로 카탈로그 설명 번역

화면경로 카탈로그명은 관리자 경로 선택용 설명이고 실제 사용자 메뉴명이 아니다. 사용자 메뉴는
`TPRMPP_CMENUM.MNU_NM`만 번역한다.

## 3. 검토한 접근법

### 3.1 프론트 고정 문구 + 범용 번역 테이블 — 채택

- 화면 고정 문구는 `@nuxtjs/i18n` 번역 리소스로 관리한다.
- 기존 업무 테이블의 한국어 컬럼은 기본 원본으로 유지한다.
- 영어 및 향후 언어 번역은 범용 번역 테이블 `TPRMPP_CLANGM`에 행으로 저장한다.
- 일반 조회 API는 기존 필드명에 선택 언어 또는 한국어 fallback 값을 담아 반환한다.

기존 프론트 소비자 변경을 최소화하면서 언어를 행 단위로 확장할 수 있어 채택한다.

### 3.2 원본 테이블에 영어 컬럼 추가 — 기각

구현은 단순하지만 언어가 늘 때마다 메뉴·공통코드 테이블, 엔티티, DTO, 관리 화면을 모두 변경해야
한다. `우선 한국어/영어`라는 확장 가능성과 맞지 않는다.

### 3.3 메뉴·공통코드까지 프론트 번역 파일에 저장 — 기각

관리자가 DB 메뉴나 공통코드를 수정하면 프론트 번역 파일과 즉시 불일치한다. 메뉴 DB를 표시명의
단일 출처로 사용하는 현재 구조도 깨뜨린다.

## 4. 데이터 모델

### 4.1 번역 마스터 `TPRMPP_CLANGM`

| 순서 | 물리 컬럼    | 타입                  | 의미                          | 제약         |
| ---: | ------------ | --------------------- | ----------------------------- | ------------ |
|    1 | `TC_ID_CONE` | `VARCHAR2(255 CHAR)`  | 원본 레코드 식별값            | PK, NOT NULL |
|    2 | `DTT_LAN_C`  | `VARCHAR2(2 CHAR)`    | 언어코드(`ko`, `en`)          | PK, NOT NULL |
|    3 | `TC_COL_NM`  | `VARCHAR2(255 CHAR)`  | 번역 대상의 실제 물리 컬럼명  | PK, NOT NULL |
|    4 | `TC_DES`     | `VARCHAR2(2000 CHAR)` | 번역문                        | NOT NULL     |
|    5 | `DTT_NM`     | `VARCHAR2(100 CHAR)`  | 대상 구분(`메뉴`, `공통코드`) | NOT NULL     |

복합 PK는 `(TC_ID_CONE, DTT_LAN_C, TC_COL_NM)`이다. `TC_COL_NM`이 번역 속성을 구분하므로 한
대상·언어에 여러 필드 번역을 저장할 수 있다.

프로젝트의 모든 업무 엔티티 규약에 맞춰 다음 공통 컬럼을 둔다.

| 컬럼           | 역할               |
| -------------- | ------------------ |
| `DEL_YN`       | 논리 삭제 여부     |
| `GUID`         | 전역 식별자        |
| `GUID_PRG_SNO` | GUID 진행일련번호  |
| `FST_ENR_USID` | 최초등록 사용자 ID |
| `FST_ENR_DTM`  | 최초등록 일시      |
| `LST_CHG_USID` | 최종변경 사용자 ID |
| `LST_CHG_DTM`  | 최종변경 일시      |

엔티티는 `BaseEntity`를 상속하고 `@IdClass`로 세 PK 컬럼을 모두 매핑한다. 번역 삭제는 물리 삭제가
아니라 `DEL_YN='Y'`로 처리한다. 같은 번역을 다시 등록하면 기존 행을 복원하고 내용을 갱신한다.

### 4.2 허용 번역 컬럼

`TC_COL_NM`에는 별칭이나 Java 필드명이 아니라 실제 원본 물리 컬럼명을 저장한다.

| `DTT_NM`   | `TC_COL_NM`      | 번역 대상                       |
| ---------- | ---------------- | ------------------------------- |
| `메뉴`     | `MNU_NM`         | 메뉴명                          |
| `공통코드` | `CO_C_NM`        | 공통코드 그룹명                 |
| `공통코드` | `CDVA_NM`        | 코드값명                        |
| `공통코드` | `CO_CDVA_ABV_NM` | 화면 표시 약어명                |
| `공통코드` | `CO_CDVA_SPS`    | 화면 표시 적요·계층명           |
| `공통코드` | `CO_C_INTN_CONE` | 관리자 화면의 코드인스턴스 설명 |

`CO_C_INTN_NM`은 자본예산·일반관리비 분류 같은 업무 분기에 사용하고, `CO_CDVA_NM`은 환율·금액
상한·계정코드·진행률 같은 기계 처리값으로 사용하므로 번역하지 않는다.

DB와 애플리케이션은 `DTT_NM`과 `TC_COL_NM`의 허용 조합을 검증한다. 현재 두 대상의 허용 컬럼
집합은 서로 겹치지 않으므로 `DTT_NM`을 PK에 포함하지 않는다. 향후 같은 `TC_COL_NM`을 사용하는 새
대상을 추가하려면 먼저 `DTT_NM`을 PK에 포함하는 마이그레이션을 적용한다.

`DTT_LAN_C`에는 소문자 ISO 639-1 코드인 `ko`, `en`을 저장한다. 이후 언어 추가를 막지 않기 위해
DB에는 `ko/en` 한정 CHECK를 두지 않고 백엔드의 지원 언어 설정에서 허용값을 검증한다.

### 4.3 원본 식별값 `TC_ID_CONE`

- 메뉴: `MNU_ID` 원문
- 공통코드: `(CO_C_ID_NM, CDVA_ID, STT_DT)`를 길이 접두 방식으로 결합한 문자열

공통코드 예시는 다음과 같다.

```text
CO_C_ID_NM = ABUS_TC, CDVA_ID = 10, STT_DT = 20260101
TC_ID_CONE = 7:ABUS_TC2:108:20260101
```

각 값의 Java 문자열 길이, 콜론, 값을 순서대로 붙인다. 구분자가 원본 값에 포함되어도 충돌하지 않고,
최대 길이는 현재 원본 컬럼 한도를 기준으로 255자 안에 들어온다. 생성 규칙은 백엔드 공통 유틸 한
곳에서만 구현하며 조회·저장·테스트가 같은 함수를 사용한다.

범용 테이블 한 개가 서로 다른 두 원본 테이블을 참조하므로 일반 FK는 걸 수 없다. 관리자 저장
서비스가 `DTT_NM`별 원본 존재 여부를 검증한다.

### 4.4 인덱스

PK 외에 `(DTT_NM, DTT_LAN_C, TC_ID_CONE)` 순서의 조회용 인덱스를 둔다. 메뉴 트리나 공통코드
목록을 언어별로 일괄 번역할 때 사용하는 조건 순서와 맞춘다.

## 5. 백엔드 설계

### 5.1 언어 해석

사용자용 메뉴·공통코드 조회 API는 선택적 `lang` 쿼리 파라미터를 받는다.

```http
GET /api/menus?lang=en
GET /api/ccodem/{cId}?lang=en
GET /api/ccodem/{cId}/{cdva}?lang=en
GET /api/ccodem/type/{cTp}?lang=en
```

- 생략: `ko`
- 지원하지 않는 값: `ko`
- 대소문자나 공백이 섞인 값: 정규화 후 지원 여부를 판정하고, 미지원이면 `ko`

쿼리에 언어를 명시하면 요청 URL과 Nuxt `useFetch` 키가 함께 달라져 언어별 캐시가 자연스럽게
분리된다. 헤더만 사용하면 현재 `useApiFetch`가 따르는 Nuxt 자동 키에 헤더가 포함되지 않아 다른 언어
응답이 같은 asyncData 엔트리를 공유할 수 있으므로 번역 데이터 조회에는 헤더만 사용하지 않는다.

### 5.2 번역 조회와 fallback

메뉴와 공통코드는 원본 목록을 먼저 조회한 뒤 대상 키 전체의 번역을 한 번에 읽는다. 행마다 번역
리포지토리를 호출하지 않는다.

각 필드의 결과는 다음 우선순위로 정한다.

1. 요청 언어의 활성 번역(`DEL_YN='N'`)이며 `TC_DES`가 공백이 아닌 값
2. 원본 한국어 컬럼값

`ko` 요청은 번역 테이블을 조회하지 않고 원본을 그대로 반환한다. `en` 요청에서도 일부 필드 번역이
없으면 해당 필드만 한국어로 대체하고 나머지 영어 필드는 유지한다.

일반 사용자 DTO의 필드명은 바꾸지 않는다. 예를 들어 영어 메뉴명도 `mnuNm`, 영어 코드값명도
`cdvaNm`으로 반환한다. 코드 ID·코드값·정렬·상위 관계 같은 비표시 필드는 원본과 동일하다.

### 5.3 관리자 API

관리자 메뉴·공통코드 조회는 현재 화면 언어와 무관하게 한국어 원본과 번역 목록을 함께 반환한다.
번역 DTO는 언어·대상 컬럼·번역문을 명시하는 목록형 계약을 사용한다.

```json
{
  "language": "en",
  "columnName": "MNU_NM",
  "text": "System Administration"
}
```

목록형 계약은 새 언어나 번역 대상 컬럼을 추가해도 DTO에 `...En` 필드를 계속 늘리지 않는다. 기존
요청과의 호환을 위해 번역 목록은 선택 입력으로 추가하고, 목록이 없는 기존 요청은 한국어 원본만
변경한다.

한국어 원본과 번역 저장은 같은 서비스 트랜잭션에서 처리한다.

- 한국어 원본: 기존 `TPRMPP_CMENUM` 또는 `TPRMPP_CCODEM` 갱신
- 비어 있지 않은 영어 번역: 기존 활성·삭제 행을 찾아 복원·갱신하거나 신규 생성
- 빈 영어 번역: 기존 번역 행이 있으면 논리 삭제
- 허용하지 않은 언어·컬럼 조합: 400
- 존재하지 않는 원본 키: 400
- 요청의 `DTT_NM`과 실제 관리 API 도메인이 다름: 400

### 5.4 캐시

- 메뉴 캐시 키에 사용자 권한 범위와 언어를 모두 포함한다.
- `codesByCid`, 코드타입 조회 등 공통코드 캐시 키에 기준일과 언어를 포함한다.
- 번역 저장은 영향받는 메뉴·공통코드 캐시의 모든 언어 엔트리를 커밋 후 무효화한다.
- 한글 원본 저장도 같은 방식으로 모든 언어 엔트리를 무효화한다. 영어 fallback 결과가 한국어 원본을
  포함할 수 있기 때문이다.
- HTTP 응답 캐시를 추가할 경우 쿼리의 `lang`을 캐시 키에 포함한다.

## 6. 프론트엔드 설계

### 6.1 i18n 설정

`@nuxtjs/i18n`을 추가하고 다음 정책을 사용한다.

- `strategy: 'no_prefix'`
- `defaultLocale: 'ko'`
- 브라우저 언어 자동 감지 비활성화
- 지원 locale: `ko`, `en`
- locale 메시지는 공통·레이아웃·업무 도메인 단위로 분리

브라우저 감지를 끈 상태에서 프로젝트가 직접 `it-portal-locale` 쿠키를 읽고 쓴다. 앱 초기화 플러그인이
렌더 전에 쿠키값을 검증해 locale을 정한다. 쿠키가 없거나 값이 올바르지 않으면 `ko`로 정규화한다.
쿠키는 인증정보가 아닌 UI 선호값이며 `SameSite=Lax`, 1년 수명을 사용한다.

번역 키는 한국어 문장 자체가 아니라 의미가 안정적인 도메인 키를 사용한다.

```text
common.actions.save
layout.tabs.closeAll
budget.validation.requiredYear
admin.menu.translation.fallback
```

한국어와 영어 리소스는 같은 키 집합을 가져야 하며 보간·복수형은 Vue I18n 기능을 사용한다.

### 6.2 언어 선택기

재사용 가능한 `LocaleSwitcher`를 다음 두 곳에 배치한다.

- 로그인 화면 우측 상단
- 로그인 후 `AppHeader`의 테마 버튼 옆

표시는 `한국어 / English`로 한다. 선택 시 다음 순서로 처리한다.

1. `it-portal-locale` 쿠키 갱신
2. Vue I18n locale 변경
3. `<html lang>` 갱신
4. PrimeVue locale 갱신
5. 메뉴·공통코드의 언어별 반응형 요청 갱신
6. 열려 있는 모든 탭 제목 재계산

라우트 이동이나 전체 새로고침은 하지 않는다. `NuxtPage` KeepAlive 인스턴스와 입력 중인 폼 상태를
유지한다.

### 6.3 PrimeVue와 포맷터

현재 `nuxt.config.ts`의 고정 한국어 PrimeVue locale을 `ko/en` 로케일 객체로 분리한다. PrimeVue
locale 설정은 반응형이므로 언어 변경 시 `usePrimeVue()`를 통해 현재 객체를 교체한다.

날짜·숫자·금액은 공통 포맷터가 현재 locale에 따라 다음 Intl locale을 사용한다.

| 앱 locale | Intl locale |
| --------- | ----------- |
| `ko`      | `ko-KR`     |
| `en`      | `en-US`     |

화면에 흩어진 `toLocaleString()`, `toLocaleDateString('ko-KR')`, `locale="ko-KR"`, `원` 접미사는
공통 포맷터 또는 번역 키로 옮긴다. 정렬·검색에 자연어 비교가 필요한 경우 현재 locale의
`Intl.Collator`를 사용하고, 코드 ID 정렬은 locale과 무관한 기존 비교를 유지한다.

### 6.4 메뉴·Breadcrumb·탭

`useMenu()`의 요청 URL을 locale에 반응하도록 만들고 `/api/menus?lang={locale}`를 사용한다. 새 트리가
도착하면 헤더·사이드바·Breadcrumb는 기존 computed 인덱스를 통해 자동 갱신된다.

현재 `AppHeader`는 활성 라우트의 탭만 `nodeByPath` 변화에 맞춰 다시 등록한다. 언어 변경 시에는
`useTabs`가 보관한 모든 탭을 새 `nodeByPath`와 페이지 meta 번역 키로 순회해 제목을 다시 계산한다.
경로와 탭 순서는 바꾸지 않는다.

탭 제목 우선순위는 기존 정책을 보존하되 값만 현 locale로 해석한다.

1. 번역 가능한 `meta.tabTitleKey`
2. 선택 언어의 DB 메뉴명
3. 번역 가능한 `meta.titleKey`
4. 홈 번역 키
5. 경로 마지막 세그먼트

기존 문자열 `meta.tabTitle`·`meta.title`은 전환 기간에만 fallback으로 허용하고 최종적으로 번역 키로
이관한다.

### 6.5 공통코드

`useCodeOptions` 등 공통 조회 파사드가 locale을 쿼리에 포함하도록 한다. 일반 화면은 기존과 같이
`cdvaNm`, `cdvaDes`, `cdvaDtl`을 읽지만 서버가 이미 현 locale 또는 한국어 fallback 값을 채운다.

업무 분기에는 `cdva`, `cTp`, `cdvaDtlC` 등 기존 안정 식별값만 사용한다. 번역된 명칭으로 분기하거나
저장하지 않는다. 이름을 코드값으로 역변환하는 기존 Excel 반입은 한국어 양식 호환이 필요하므로 화면
locale과 무관하게 공통코드를 `lang=ko`로 별도 조회해 해석한다. 반입 결과를 화면에 표시할 때만 현재
locale의 공통코드 조회 결과를 사용한다. 이번 범위에서 영문 Excel 입력·출력 서식은 추가하지 않는다.

### 6.6 관리자 UI

- 메뉴 편집: 한국어 메뉴명 필수, 영어 메뉴명 선택 입력
- 공통코드 편집: 기존 한국어 필드와 별도의 영어 번역 영역
- 영어 미입력 필드: `한국어 대체 표시` 상태 표시
- 영어 입력 삭제 후 저장: 번역 행 논리 삭제
- 필드별 최대 길이: 원본 컬럼 길이와 `TC_DES` 2000자 중 더 작은 값
- 기술 필드 `CO_C_INTN_NM`, `CO_CDVA_NM`: 번역 입력을 제공하지 않음

공통코드의 영어 필드를 기존 DataTable에 모두 가로로 추가하지 않는다. 행 편집 다이얼로그 또는 전용
번역 영역에 묶어 표 밀도와 기존 열 구성을 유지한다.

### 6.7 API 오류 문구

프론트가 소유하는 Toast·확인·검증 문구는 i18n 리소스에서 가져온다. 서버가 표준 오류코드를 제공하는
경우 코드에서 번역 키로 매핑한다. 영어 화면에서 알 수 없는 서버 오류의 한국어 `message`를 그대로
노출하지 않고 현 locale의 일반 오류문과 HTTP 상태·요청 ID 같은 진단 식별자만 표시한다.

한국어 화면은 전환 기간 동안 기존 서버 메시지 fallback을 유지할 수 있지만, 최종적으로 사용자에게
노출되는 고정 오류는 코드 기반 번역으로 수렴한다.

## 7. 번역 누락과 실패 처리

| 상황                       | 동작                                         |
| -------------------------- | -------------------------------------------- |
| locale 쿠키 없음           | `ko`                                         |
| locale 쿠키가 `ko/en` 이외 | `ko`로 정규화하고 쿠키 갱신                  |
| API `lang` 누락·미지원     | `ko`                                         |
| 번역 행 없음               | 해당 한국어 원본                             |
| 번역 행 논리 삭제          | 해당 한국어 원본                             |
| `TC_DES` 공백              | 저장 거부 또는 기존 번역 논리 삭제           |
| 일부 필드만 번역됨         | 번역 필드와 한국어 fallback 필드를 함께 반환 |
| 알려진 API 오류코드        | 현 locale 번역문                             |
| 알 수 없는 API 오류        | 현 locale 일반 오류문 + 진단 식별자          |

번역 누락은 사용자 조회를 실패시키지 않는다. 원본 메뉴·공통코드 조회 실패는 기존 오류 처리 규약을
그대로 따르고 번역 테이블 오류를 빈 번역으로 오인해 숨기지 않는다.

## 8. 전환과 배포

### 8.1 구현 순서

1. `it_database`: `TPRMPP_CLANGM` DDL, PK·CHECK·인덱스
2. `it_backend`: 엔티티·복합키·키 생성기·번역 저장소·서비스
3. `it_backend`: 메뉴·공통코드 `lang` 계약과 관리자 번역 계약
4. `it_database`: 기존 메뉴·공통코드 영어 번역 초기 데이터
5. `it_frontend`: Nuxt i18n·쿠키·PrimeVue·공통 포맷터
6. `it_frontend`: 로그인·AppShell·공통 컴포넌트
7. `it_frontend`: 업무 화면을 도메인별로 전환
8. `it_frontend`: 관리자 메뉴·공통코드 번역 편집
9. 전 범위 번역 누락·회귀 검증
10. 운영 언어 선택기 노출

교차 저장소 커밋은 DB → 백엔드 API 계약 → 프론트 순서로 만들고 호환 조합을 루트
`versions.lock`에 기록한다. 배포도 같은 순서를 따른다. 기존 프론트가 `lang`을 보내지 않으면 새
백엔드는 한국어를 반환하므로 백엔드 선배포가 호환된다.

부분 번역 상태가 운영에 노출되지 않도록 언어 선택기 노출은 모든 포함 범위 전환 뒤 마지막에 한다.

### 8.2 정적 문구 전환

코드에 존재하는 한글은 주석·테스트 설명·업무 데이터 예시도 포함하므로 단순 정규식 건수를 번역
진척률로 사용하지 않는다. Vue 템플릿 텍스트, 사용자 노출 prop, Toast·Dialog 호출, 접근성 속성,
페이지 meta를 대상으로 인벤토리를 만들고 도메인별로 제거한다.

신규 사용자 노출 한글 리터럴을 막는 정적 테스트를 추가한다. 기존 리터럴은 기준선을 두고 도메인
전환마다 줄이는 ratchet으로 관리하며, 번역 리소스·주석·테스트 fixture·업무 코드값은 검사에서
제외한다.

## 9. 테스트

### 9.1 데이터베이스·백엔드

- `TPRMPP_CLANGM` 세 컬럼 복합 PK와 엔티티 `@IdClass` 일치
- 같은 대상·언어에 여러 `TC_COL_NM` 행 분리
- 메뉴와 공통코드 `TC_ID_CONE` 생성의 결정성·충돌 방지·최대 길이
- `DTT_NM`·`TC_COL_NM` 허용 조합 검증
- 존재하지 않는 원본 대상 저장 거부
- 메뉴·공통코드 번역 일괄 조회와 N+1 부재
- `ko`, `en`, 누락, 미지원 `lang` 계약
- 번역 없음·일부 누락·논리 삭제의 필드별 한국어 fallback
- 언어별 캐시 격리
- 원본·번역 저장 후 모든 언어 캐시 무효화
- 원본과 번역 저장 실패 시 전체 롤백
- OpenAPI 응답·요청 계약과 프론트 생성 타입 일치

### 9.2 프론트 단위 테스트

- 쿠키 없음·오염 시 `ko`
- `ko/en` 전환과 쿠키 저장
- 같은 URL 유지
- `<html lang>`과 PrimeVue locale 전환
- 날짜·숫자·금액 포맷 전환
- 메뉴 locale 변경 시 전체 열린 탭 제목 재계산
- 공통코드 요청 URL과 asyncData 키의 언어 분리
- 한국어·영어 번역 키 집합 일치
- 신규 사용자 노출 한글 리터럴 ratchet
- 관리자 번역 입력 변환과 빈값 삭제 요청

### 9.3 Playwright

1. 쿠키 없는 로그인 화면이 한국어로 표시된다.
2. 로그인 화면에서 영어로 바꾸면 URL 변화 없이 문구가 전환된다.
3. 로그인 후에도 영어가 유지된다.
4. 헤더·사이드바·Breadcrumb·상단 탭·공통코드가 함께 영어로 표시된다.
5. 새로고침·로그아웃·재로그인 후 쿠키 언어가 유지된다.
6. 언어 전환 중 작성 중인 폼 값과 열린 탭이 유지된다.
7. 관리자가 영어 메뉴·공통코드명을 등록·수정·삭제할 수 있다.
8. 삭제하거나 누락한 영어 번역만 한국어로 fallback된다.
9. 한국어로 돌아가면 원본 한국어 값이 표시된다.

### 9.4 품질 게이트

- 백엔드: 관련 단위 테스트, Oracle 통합 테스트, `./gradlew test`
- 프론트: `npm run format:check`, `npm run check`, `npm test`, 관련 `npm run test:e2e`
- API 변경: 백엔드 기동 후 `npm run codegen`, `npm run codegen:check`
- 정적 배포: `npm run generate -- --dry-run`과 실제 `generate` 검증

## 10. 완료 기준

- 쿠키가 없으면 모든 환경에서 한국어가 기본이다.
- `it-portal-locale=ko|en`만 사용자 선택값으로 인정한다.
- 언어 전환으로 URL·탭·폼 상태가 바뀌지 않는다.
- 영어 모드에서 포함 범위의 고정 문구가 한국어로 남지 않는다.
- 메뉴·공통코드의 번역 누락 필드만 한국어로 fallback된다.
- 헤더·사이드바·Breadcrumb·모든 열린 탭이 같은 언어를 사용한다.
- 공통코드 표시 언어가 바뀌어도 저장·분기에는 기존 코드값만 사용한다.
- 관리자 저장 직후 모든 사용자 조회 캐시에서 최신 번역이 보인다.
- 로그인 화면과 로그인 후 화면에서 언어 선택이 가능하고 새로고침·재로그인 후에도 유지된다.
- 한국어·영어 번역 키 집합과 정적 문구 품질 게이트가 통과한다.
