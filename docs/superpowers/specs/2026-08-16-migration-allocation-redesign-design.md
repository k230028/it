# 데이터 일괄 반입의 편성 전용 전환 설계

- 작성일: 2026-08-16
- 대상: `/admin/migration`(데이터 일괄 반입)을 원장 생성에서 **편성금액 계산**으로 전환
- 관련 저장소: `it_backend`, `it_frontend`
- 선행 설계: `2026-08-11-excel-bulk-migration-design.md`(이 화면의 최초 설계), `2026-08-13-budget-request-form-migration-design.md`(편성요청서 반입)

## 1. 배경

### 1.1 업무 흐름

전산예산 편성은 세 단계로 진행된다.

| 단계 | 문서 | 주체 | 화면 |
| --- | --- | --- | --- |
| 1 | 전산예산 편성요청서 | 부점 | `/admin/migration/requests` |
| 2 | 편성요구서 종합 (전산업무비·정보화사업·경상사업) | 예산 담당자 취합 | `/admin/migration` |
| 3 | 하반기 계획 조정 | 예산 담당자 (사업별 진행상황 반영) | `/admin/migration` |

2·3단계 문서는 1단계가 만든 요청 원장 위에서 **편성률(조정률)을 반영해 편성금액을 계산**하기 위한 것이다. 새 사업을 등록하는 문서가 아니다.

### 1.2 두 화면이 서로를 모른다

`2026-08-13-budget-request-form-migration-design.md` §1이 "기존 화면·어댑터는 수정하지 않고 별도 경로를 만든다"고 못박았다. 그 결과 두 화면이 같은 원장에 각자 쓰면서 서로를 인식하지 못한다.

**① 요청서를 먼저 반입하면 종합본이 전량 차단된다.**

`MigrationValidator.java:259`가 정규화 사업명이 DB에 있으면 `DUPLICATE_EXISTS` BLOCKER를 낸다. 1단계가 그 사업들을 이미 만들어 두므로 2단계의 정보화사업 행은 하나도 통과하지 못한다. 업무 순서대로 하면 `/admin/migration`은 **실행 자체가 불가능**하다.

**② 전산업무비는 반대로 조용히 중복 생성된다.**

자연키가 서로 다르다.

| 화면 | 자연키 |
| --- | --- |
| `/admin/migration/requests` | `(BSE_YY, SVN_DPM_C, IOE_C, CTT_OPP_NM, CTT_NM)` |
| `/admin/migration` | `(BSE_YY, BG_UNT_ABUS_C, IOE_C, CTT_OPP_NM, CTT_NM)` |

부서코드와 사업코드는 다른 값이라 같은 계약이 매칭되지 않는다. 1단계가 만든 행이 2단계에서 새 행으로 다시 생겨 예산 집계가 이중 계상된다. 차단보다 나쁜 실패다.

**③ 하반기 조정이 요청 원장을 훼손한다.**

`MigrationImportService.replaceItems`가 대상 사업의 활성 `BITEMM`을 `DEL_YN='Y'`로 닫고 조정 금액으로 새 품목을 만든다. 부서가 제출한 요청 품목이 활성 원장에서 사라져 요청 대비 편성 비교가 불가능해진다.

### 1.3 실측으로 확인한 엑셀 구조

`C:\it\sample`의 세 파일을 직접 읽었다.

**`2026년 전산자본예산 편성 요구서.xlsx` › `1-1. 26년정보화사업(전산예산반영)`** (29열)

   일반관리비 | 총 사업예산 | 사전보고 | 전결권 | 구분 | 조정비율 |

| 신규사업 | 신규 | 0.7 | |
| 후행사업 | 후행 | 0.7 | |
| 2억이하사업 | 2억이하 | 1 | 신규 + 2억이하 |

**`2026년 전산일반관리비 편성 요구서.xlsx` › `전체취합(국내외)`** (19열)

```

요구부서 | 팀 | 25년 통화 | 25년 요구액 | 25년 요구액(원화) |

```

**조정률 열이 없다.** `26년 요구액`이 이미 취합·조정된 결과다.

**`2026년 정보기술부문계획 조정.xlsx` › `26년정보화사업(자본예산)`**

`'26년 6월 조정 기준` 블록에 개발비·기계장치·기타무형자산 확정금액이 있다. 웹한글 사업은 요청 `1406` → 조정 `416`(29.58%)이고 비고가 `6.10자 품의 완료, 7.9자 계약 완료`다. 비율 곱이 아니라 **실제 계약금액**이다.

### 1.4 포탈에 이미 있는 편성 경로

`/budget/work`(예산 작업)이 사업별 편성률 입력 → `BudgetRateApplicationService.applyItemRates` → `BBUGTM` 경로를 이미 갖고 있다. 기본 편성률을 `DUP_IOE_CPIT`(70%)·`DUP_AMT_CPIT`(2억)·`DUP_IOE_MNGC`(100%) 공통코드로 자동 계산하는데, 이것이 `조정구분` 시트의 규칙과 정확히 일치한다.

즉 `/admin/migration`을 편성 전용으로 바꾸면 그 화면의 **대량 입력 경로**가 되고 목적지(`BBUGTM`)를 공유한다. 새 개념을 도입하는 것이 아니라 이미 있는 개념에 합류시키는 변경이다.

## 2. 목표와 원칙

### 2.1 역할 분리

| 계층 | 내용 | 쓰는 화면 |
| --- | --- | --- |
| 요청 원장 `BPROJM`·`BITEMM`·`BCOSTM` | 부서가 제출한 요청 (품목 단위 상세) | `/admin/migration/requests` |
| 편성 `BBUGTM` | 편성금액 + 편성률 | `/admin/migration`, `/budget/work` |

`/admin/migration`은 기본적으로 원장을 만들지 않는다. 종합본·조정본의 각 행을 기존 요청 원장에 **매칭**하고 편성금액만 계산한다.

두 가지 예외가 있고 둘 다 명시적이다.

- 매칭된 `BCOSTM`의 `BG_UNT_ABUS_C`가 비어 있으면 종합본 값으로 채운다(§4.1). null → 값이라 요청 내용을 훼손하지 않고, 예산 집계에 필요한 값이다
- 관리자가 행을 `CREATE_NEW`로 결정하면 종전 어댑터 경로로 원장을 만든다(§4.2). 요청서 없이 종합본만 있는 최초 이관을 위한 경로이며, 기본값이 아니다

### 2.2 금액 기준

종합본 금액이 1단계 반입 금액과 다르면 **종합본을 기준으로 삼는다.** 예산담당자가 취합 단계에서 이미 1차 조정한 값이므로 편성의 출발점으로 맞다. 요청서 금액과 다르면 `AMOUNT_ADJUSTED` WARNING으로 알리되 반영은 진행한다.

조정비율도 종합본의 `조정비율` 열을 쓴다. `조정구분` 시트나 `DUP_IOE_*` 공통코드로 재계산하지 않는다 — 예산담당자가 사업별로 기본 규칙에서 벗어난 비율을 넣을 수 있고, 그 판단이 이 문서의 본질이기 때문이다.

## 3. 핵심 모델 — 실효 편성률

### 3.1 문제

종합본은 사업 단위로 비목그룹 총액을 준다. `BBUGTM`은 품목(`GCL_MNG_NO`) 단위다. 이 간극을 메워야 한다.

`ASG_RT`가 `Integer`인 것도 걸림돌이었다. 하반기 조정의 `416/1406 = 29.58%`를 정수로는 담지 못해 종전 설계가 `BITEMM` 버전 교체를 택했다(§1.2 ③의 원인).

### 3.2 실측: 물리 컬럼은 이미 소수를 담는다

로컬 Oracle(`ITPAPP@127.0.0.1:11521/XEPDB1`) 실측이다.

```
TPRMPP_BBUGTM.ASG_RT       NUMBER(8,5)
TPRMPP_BBUGTM.BG_DUP_AMT   NUMBER(18,3)
TPRMPP_BBUGTL.ASG_RT       NUMBER(8,5)
TPRMPP_BBUGTL.BG_DUP_AMT   NUMBER(18,3)

기존 데이터: ASG_RT = 100 이 78건 (전부 정수)
```

`Bbugtm.asgRt`의 Java 매핑만 `Integer`고, `BbugtL.asgRt`는 `precision=3, scale=0`으로 **물리와 어긋나 있다**. 두 매핑을 물리에 맞추면 **DDL 변경 없이** 소수 편성률을 쓸 수 있다.

### 3.3 계산식

```
비목그룹 목표 편성액
  = 종합본 기준액 × 종합본 조정비율          (편성요구서 종합)
  = 조정 확정금액                            (하반기 계획 조정)

실효 편성률 = 목표 편성액 / 그 그룹의 요청 품목 합계 × 100    (소수 5자리)

품목별: BG_DUP_AMT = BITEMM.AMT × 실효편성률 / 100
        ASG_RT     = 실효편성률
```

세 경우가 한 식으로 떨어진다.

| 경우 | 계산 | 실효 편성률 |
| --- | --- | --- |
| 종합본 금액 = 요청 합계 | `1406 × 0.7 / 1406 × 100` | `70.00000` (현행과 동일) |
| 종합본에서 취합 조정됨 | `(1200 × 0.7) / 1406 × 100` | `59.74395` |
| 하반기 확정금액 | `416 / 1406 × 100` | `29.58748` |

`요청금액 × 편성률 = 편성금액` 불변식이 세 경우 모두 성립한다.

### 3.4 비목그룹의 정의

**정보화사업**은 종합본의 금액 열 3개가 곧 그룹이다. 각 그룹에 속하는 `IOE_C`는 `MigrationIoeCodes`의 기본값과 미리보기 보정 후보를 합친 집합이다.

| 종합본 열 | 그룹에 속하는 `IOE_C` |
| --- | --- |
| 개발비 | `103` 개발비(일반), `104` 감리/컨설팅 |
| 기계장치 | `101` 국내기계장치, `102` 국외기계장치 |
| 기타무형 | `105` 국외기타무형자산, `106` 국내기타무형자산(일반), `107` SW라이선스 |

매칭된 사업의 활성 품목 중 그 집합에 드는 것들의 `AMT` 합계가 분모다. 세 그룹 어디에도 속하지 않는 비목(1단계가 `BITEMM`에 함께 담은 일반관리비 계열 `001`·`007`·`013` 등)은 종합본의 `일반관리비` 열을 기준액으로 하는 네 번째 그룹으로 묶고, 그 열이 비어 있으면 기존 편성률을 그대로 유지한다.

**전산업무비**는 `BCOSTM` 한 행이 곧 하나의 단위다. 분모는 `COST_TOT_XP_AMT`이고 그룹 개념이 필요 없다.

### 3.5 반올림

그룹 합계를 목표액과 정확히 일치시키고, 반올림 잔차는 그 그룹에서 **금액이 가장 큰 품목**에 흡수한다. 품목 단위 오차는 `BG_DUP_AMT`의 scale 3 기준 0.001원 이하다. `ASG_RT`에는 그룹 공통 실효율을 그대로 기록하므로, 잔차를 흡수한 품목 하나만 `AMT × ASG_RT`와 `BG_DUP_AMT`가 0.001원 어긋난다. 예산 집계는 그룹 합계로 이뤄지므로 합계 정확성을 택한다.

요청 품목 합계가 0인데 목표 편성액이 0보다 크면 배분할 대상이 없다. `ITEM_BASE_ZERO` BLOCKER로 막는다. 반대로 목표 편성액이 0이면(하반기 조정의 `문자메시지 안심마크 도입` 사례) 실효 편성률 `0`으로 그 그룹의 편성행을 모두 0원으로 만든다 — 정상 경로이므로 진단을 내지 않는다.

### 3.6 계약 변경

| 대상 | 변경 |
| --- | --- |
| `Bbugtm.asgRt` | `Integer` → `BigDecimal` |
| `BbugtL.asgRt` | `Integer` → `BigDecimal`, 매핑을 `precision=8, scale=5`로 정정 |
| `BudgetWorkDto.ItemRate` | `assetDupRt`·`costDupRt` 유지 + `ioeRates`(비목코드 → 편성률) 선택 필드 추가 |
| `BudgetRateApplicationService.applyItemRates` | `ioeRates`가 있으면 그것을, 없으면 종전 2버킷을 적용 |
| `BudgetWorkController` | 시그니처 전파만 |

`/budget/work`는 계속 2버킷 경로를 쓰므로 동작이 바뀌지 않는다. DDL 변경도 신규 라이브러리도 필요 없다.

## 4. 매칭

### 4.1 시트별 매칭 키

| 시트 | 매칭 키 | 대상 |
| --- | --- | --- |
| `1-1. 26년정보화사업(전산예산반영)` | 정규화 사업명 | `BPROJM` |
| `2. 위임예산(경상)` | 부점명 → 부서코드 + `ODN_YN='Y'` | `BPROJM`(경상) |
| `전체취합(국내외)` | `(BSE_YY, SVN_DPM_C, IOE_C, CTT_OPP_NM, CTT_NM)` | `BCOSTM` |
| `26년정보화사업(자본예산)` | 정규화 사업명 | `BPROJM` |

**정보화사업**은 기존 `MigrationYearSnapshot.projectNoByNormalizedName`을 그대로 쓴다. 현행이 이 조회로 `DUPLICATE_EXISTS` BLOCKER를 냈는데, 편성 모드에서는 같은 조회가 **매칭 성공** 신호로 뒤집힌다.

**위임예산**은 사업명 매칭이 성립하지 않는다. 종합본은 부점명으로만 그룹핑되고(런던 / 런던 PF), 1단계 경상사업의 사업명은 부점이 시트 ②에 적은 임의 문자열이다 — 샘플 런던지점 파일은 사업명이 아예 공란이라 관리자가 미리보기에서 보정 입력한다. 그래서 **부서코드 + `ODN_YN='Y'`로 후보를 조회**한다. 1건이면 자동 매칭, 0건·2건 이상이면 결정을 요청한다. 런던과 런던 PF가 같은 부서코드(920)로 묶여 2건이 나올 수 있어 이 경로가 실제로 쓰인다.

**전산업무비**는 자연키에서 **사업코드를 뺀다.** 1단계 양식에 그 열이 없어 `BG_UNT_ABUS_C`가 대부분 null이기 때문이다(§1.2 ②의 원인이 바로 이것이다). 대신 매칭 성공 후 원장의 `BG_UNT_ABUS_C`가 비어 있으면 종합본 값으로 채운다. 값이 있는데 다르면 WARNING만 낸다.

완화 매칭은 `OrgIdentityResolver`와 같은 3단계다.

1. 5요소 정확 일치
2. 상대처를 뺀 4요소 일치 (계약업체명 공란 표기가 흔들린다)
3. 부서 + 비목만으로 후보 목록 제시

### 4.2 미매칭 행의 결정

행마다 서버가 결정 종류를 지정한다(`RequestFormDecisionKind`와 같은 방식).

| 결정 | 동작 |
| --- | --- |
| `MATCH_TARGET` | 후보에서 기존 원장을 선택한다 |
| `CREATE_NEW` | 원장을 새로 만들고 편성한다 (기존 어댑터 경로 재사용) |
| `SKIP` | 이 행을 편성 대상에서 제외한다 |

기본값은 없고 BLOCKER가 유지된다. 요청서 없이 종합본만 있는 최초 이관을 위해 **전 행 `CREATE_NEW` 일괄 지정** 버튼을 둔다. 현행 동작이 이 버튼 하나로 재현되므로 회귀가 아니다.

### 4.3 전산업무비의 편성률 출처

종합본 `전체취합(국내외)`에 조정률 열이 없다(§1.3). 편성률은 **`DUP_IOE_MNGC` 공통코드**를 읽어 쓴다 — `/budget/work`가 일반관리비 기본 편성률로 쓰는 바로 그 값이다(`it_frontend/app/pages/budget/work.vue:132`). `100`을 상수로 박지 않는다.

편성 목표액 = 종합본 `26년 요구액(원화)` × 그 편성률이다.

### 5.2 원장 검증은 `CREATE_NEW` 행에만 적용한다

`LENGTH_EXCEEDED`·`REQUIRED_MISSING`·`CODE_UNRESOLVED`는 `CREATE_NEW`로 결정된 행에서만 검사한다. 매칭된 행은 원장을 만들지 않으므로 물리 길이나 필수값을 검사할 이유가 없다. 전 행에 걸면 종합본의 긴 사업개요 하나 때문에 편성이 통째로 막힌다.

### 5.3 연도 전체 보존

`applyItemRates`가 연도 전량을 논리삭제한 뒤 `items`에 담긴 것만 재삽입하므로(`BudgetRateApplicationService.java:136`), 종합본에 없는 기존 사업·전산업무비의 편성률을 미리 읽어 함께 넘기는 현행 로직(`MigrationImportService.java:165`)은 유지한다. 이 부분은 이미 정확하다.

다만 비목별 맵을 쓰게 되므로 스냅샷도 비목별로 읽어야 한다. `MigrationYearSnapshot.projectRates()`가 지금 자본·일반 2버킷으로 접으면서 서로 다른 편성률을 `Math.min`으로 뭉개는데(`MigrationYearSnapshot.java:196`), `Map<품목관리번호, ASG_RT>` 원본 보존으로 바꾸면 그 손실 자체가 사라진다.

### 6.2 반영 흐름

```
1. 재검증 — BLOCKER가 남으면 아무것도 쓰지 않는다 (현행 유지)
2. 연도 스냅샷: 기존 편성률(품목별 원본) + 품목 인덱스 + 원장 자연키
3. 행별 매칭 — 매처가 대상 PK를 정하거나 결정을 요구한다
4. CREATE_NEW 행만 원장 생성 (일반관리비 → 자본예산 → 위임예산 순, 현행 어댑터 경로)
   생성 직후 MigrationApprovalStamper로 결재완료 받이 생성 (현행 유지)
5. 하반기 조정 계획 문서(BPLANM·BPLANA) 생성 (현행 유지, BITEMM은 건드리지 않는다)
6. 플래너가 비목그룹 목표액 → 실효 편성률 → 품목별 편성 의도를 만든다
7. applyItemRates 단일 호출 — items에 그 연도의 모든 사업 + 모든 전산업무비
```

전 과정이 하나의 트랜잭션이라는 현행 성질을 유지한다.

## 10. 결정 요약

| 항목 | 결정 |
| --- | --- |
| 화면 성격 | 원장 생성 → **편성금액 계산**. 종합본·조정본은 원장을 만들지 않는다 |
