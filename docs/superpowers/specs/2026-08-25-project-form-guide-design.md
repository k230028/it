# 사업 입력 길라잡이 설계

## 1. 목적과 범위

`/info/projects/form`에서 정보화사업과 경상사업을 입력할 때 선택한 필드의 길라잡이를 우측에 표시한다. 관리자는 고정된 대상 필드 카탈로그에서 필드를 선택해 길라잡이 본문을 등록·수정·삭제한다.

대상은 사업 폼의 모든 편집형 사업 데이터 필드다. `InputText`, `InputNumber`, `AutoComplete`, `Textarea`, `Select`, `MultiSelect`, `IoeCategorySelect`, `DatePicker`, `TiptapEditor`와 소요자원 상세 편집 셀을 포함한다. 저장·검색 버튼과 첨부파일 업로더처럼 사업 데이터 값을 직접 표현하지 않는 조작 요소는 제외한다.

## 2. 확정된 제품 규칙

- 정보화사업과 경상사업은 길라잡이를 공유하지 않는다.
- 대상 ID는 `info.*`와 `cost.*`로 분리한다.
- 소요자원 동적 행은 행 번호를 ID에 넣지 않고 같은 열의 길라잡이를 공유한다.
- 관리자는 서버가 제공하는 고정 카탈로그에서만 대상을 선택한다. 임의 ID를 입력할 수 없다.
- 등록된 본문이 없는 필드를 선택하면 패널과 빈 안내를 모두 표시하지 않는다.
- 길라잡이 조회 실패는 사업 작성·저장을 막지 않는다. 패널을 숨기고 공통 오류 안내를 한 번만 노출한다.

## 3. 데이터 모델과 분류

기존 `TPRMPP_BGDOCM`을 공유하며 컬럼을 추가하지 않는다.

| 컬럼 | 단계별 가이드 | 입력 길라잡이 |
| --- | --- | --- |
| `DOC_MNG_NO` | `GDOC-{year}-{seq:04d}` | `FDOC-{year}-{seq:04d}` |
| `DOC_TTL_CONE` | 기존 단계명 | 고정 대상 ID (`info.*`, `cost.*`) |
| `NAC_TXT_INF` | 가이드 HTML 본문 | 길라잡이 HTML 본문 |
| `DEL_YN` | 논리 삭제 | 논리 삭제 |

기존 `SQ_TPRMPP_BGDOCM_1`을 공유하되 채번 서비스가 문서 종류에 맞는 접두사를 붙인다. `DOC_MNG_NO`의 접두사가 1차 문서 종류 경계이며, 입력 길라잡이 조회는 유효한 `info.*` 또는 `cost.*` 카탈로그 ID도 함께 검증한다.

신규 Flyway 마이그레이션은 활성 `FDOC-*` 행에 한해 `DOC_TTL_CONE`을 유일하게 만드는 Oracle 함수 기반 유니크 인덱스를 추가한다. 조건에 해당하지 않는 행은 `NULL`로 투영해 기존 `GDOC-*`에 영향을 주지 않는다. 적용 전 중복 진단과 적용 후 유일성 검증 SQL을 함께 제공한다.

## 4. 카탈로그 계약

서버의 고정 카탈로그는 다음 메타데이터를 가진다.

- `guideId`: 안정된 대상 ID
- `scope`: `info` 또는 `cost`
- `section`: 관리 화면 그룹
- `fieldLabel`: 사용자용 필드명
- `controlType`: 실제 입력 종류

ID는 `info.{section}.{field}` 또는 `cost.{section}.{field}`를 기본 형식으로 한다. 예를 들어 소요자원 비목 선택은 `info.resource.ioe`, `cost.resource.ioe`로 분리한다. 구체 ID 목록은 구현 계획에서 폼 전체를 기계적으로 조사해 확정한다.

프론트는 대상 입력에 명시적 `guide-id`를 연결한다. 서버 카탈로그 ID 집합과 프론트 연결 ID 집합이 정확히 일치하는지 계약 테스트로 검증한다. 이로써 타이포, 누락, 삭제된 필드의 잔존 ID를 방지한다.

## 5. API 설계

### 5.1 사용자 조회

`GET /api/form-guides?scope=info|cost`

- 일반 인증 사용자가 조회한다.
- 해당 scope의 등록된 본문이 있는 활성 `FDOC-*`만 반환한다.
- 응답 항목은 `guideId`, `fieldLabel`, `contentHtml`이다.
- 빈 본문, `DEL_YN='Y'`, 다른 scope, `GDOC-*`, 카탈로그 밖 ID는 제외한다.
- 폼 진입 시 한 번 일괄 조회하고 명시적 재시도 전에는 추가 요청하지 않는다.

### 5.2 관리자

- `GET /api/admin/form-guides/catalog?scope=info|cost`: 등록 여부와 현재 `docMngNo`를 포함한 전체 카탈로그
- `PUT /api/admin/form-guides/{guideId}`: 미등록이면 신규 `FDOC-*` 생성, 등록이면 현재 문서 수정
- `DELETE /api/admin/form-guides/{guideId}`: 현재 활성 문서 논리 삭제

관리 API는 클래스 수준에서 `ROLE_ADMIN`을 강제한다. 요청 본문은 HTML 내용만 받고, `DOC_TTL_CONE`은 경로의 검증된 카탈로그 ID로 서버가 설정한다. 논리 삭제한 대상을 다시 등록하면 새 `FDOC-*` 관리번호를 발급한다.

### 5.3 기존 단계별 가이드 경계

`/api/guide-documents`는 모든 목록·상세·수정·삭제 대상을 `GDOC-*`로 제한한다. POST 자동 채번은 계속 `GDOC-*`를 사용한다. 조회는 인증 사용자, 생성·수정·삭제는 `ROLE_ADMIN`만 허용한다. `FDOC-*`는 기존 `/guide` 화면에 노출되지 않는다.

## 6. 프론트엔드 사용자 경험

`useFormGuide`는 현재 사업 유형의 일괄 조회 데이터와 활성 ID를 관리한다. 공통 `GuidePanel`은 선택된 길라잡이를 표시하는 책임만 가진다.

대상 입력이 포커스되거나 선택 패널·달력이 열리면 해당 `guide-id`를 활성화한다. 포커스가 빠져도 마지막 길라잡이를 유지하여 사용자가 읽을 수 있게 하고, 다른 대상을 선택할 때만 교체한다. 다만 새 대상에 등록된 본문이 없으면 패널을 즉시 숨긴다.

- 데스크톱: 기존 폼 본문과 약 280~320px 우측 스티키 패널
- 작은 화면: 폼 아래 접힘 가능 카드
- 본문이 없거나 아직 대상을 선택하지 않음: 패널 미렌더링
- 조회 실패: 패널 미렌더링, 공통 오류 안내 1회, 사업 입력·저장 정상 진행

`NAC_TXT_INF`는 서버 저장 시 새니타이징하고, 프론트 표시 시점에도 `isomorphic-dompurify`로 다시 정화한다. 패널 본문과 링크는 선택·조작할 수 있게 한다.

## 7. 길라잡이 관리 화면

관리자 메뉴에 `길라잡이 관리` 라우트를 신설한다. 메뉴와 한국어·영어 표시 데이터는 DB 번역 데이터를 SoT로 추가한다.

화면은 좌측 선택 영역과 우측 편집 영역으로 구성한다.

- 좌측: 사업 유형, 섹션 필터, 대상 필드 목록, 등록 상태
- 우측: ID 읽기 전용 표시, 입력 종류, 현재 `docMngNo`, Tiptap 본문 편집기
- 미등록 대상: `신규 등록`
- 등록 대상: `저장`, `삭제`

자유 ID 입력과 동일 ID의 중복 생성은 허용하지 않는다.

## 8. 오류·권한·동시성

- 카탈로그 밖 ID 또는 scope 불일치: 400
- 활성 길라잡이 중복 생성: 409
- 미등록 대상 삭제: 404
- 비관리자 관리 API 호출: 403
- 미인증 조회: 401

서비스가 중복을 사전 검증하고, 동시 등록 경쟁은 DB 유니크 인덱스가 최종 차단한다. 제약 위반은 공통 409 응답으로 변환한다. 기존 단계별 가이드와 신규 길라잡이의 쓰기 경로는 모두 서버에서 `ROLE_ADMIN`을 검증한다.

## 9. 테스트와 검증

### 백엔드

- scope·접두사·활성 여부·빈 본문 필터링 서비스 테스트
- 카탈로그 밖 ID, 중복, 삭제 후 재등록 테스트
- 일반 조회·관리자 CRUD·비관리자 403 MockMvc 테스트
- 기존 `/api/guide-documents`의 `GDOC-*` 경계와 쓰기 권한 회귀 테스트
- Oracle 함수 기반 인덱스와 일괄 조회 저장소 통합 테스트

### 프론트엔드

- 카탈로그–필드 연결 ID 집합 계약 테스트
- 모든 입력 종류의 활성화 이벤트 단위 테스트
- 정보화·경상 scope 분리와 소요자원 동적 행 ID 공유 테스트
- 빈 본문 시 완전 미렌더링, 조회 실패, 재시도, HTML 정화 테스트
- 데스크톱 스티키 패널과 작은 화면 접이식 카드 테스트

## 10. 배포 순서와 호환성

1. 함수 기반 유니크 인덱스와 관리자 메뉴·번역 데이터 마이그레이션
2. 백엔드 API·권한·카탈로그 배포
3. 백엔드 기동 후 OpenAPI 타입 재생성
4. 프론트엔드 폼·관리 화면 배포
5. 루트 `versions.lock` 호환 조합 갱신

기존 `GDOC-*` 데이터는 변환하지 않는다. 신규 길라잡이는 관리 화면에서 등록하기 전까지 사용자 폼에 아무것도 표시하지 않는다.

## 11. 비범위

- `TPRMPP_BGDOCM` 컬럼 추가 또는 기존 데이터 이관
- 길라잡이 다국어 본문 별도 저장
- 필드별 사용 통계, 버전 비교 화면, 승인 워크플로
- 폼 외 화면에 대한 범용 길라잡이 프레임워크
