# 스파이크: Access Token Blocklist 도입 결정 메모 (T10b)

> **성격**: 본 문서는 구현물이 아니라 **의사결정 산출물(decision note)** 입니다.
> Phase 3 보안 하드닝 계획 `2026-06-22-phase3-security-hardening.md`의 Task 10b에 해당합니다.
> Task 10a(Refresh Token 회전)는 구현·커밋 완료되었고, Access Token 즉시 무효화(블록리스트)는
> 인프라 부재로 본 메모에서 옵션을 비교하고 결정을 게이트에 올립니다.

## 1. 현황

- **분산 캐시/Redis 부재**: 코드베이스에 분산 캐시 인프라가 없습니다. Spring Cache는
  `@Cacheable` 로컬(인메모리) 캐시로만 사용 중이며(`CodeService` 등), 다중 인스턴스 간
  공유 가능한 블록리스트 저장소가 없습니다.
- **Access Token 단기 만료**: Access Token 유효시간은 **15분**(`jwt.access-token-validity=900000`).
- **즉시 무효화 미지원**: JWT는 Stateless 검증이므로, 발급된 Access Token은 만료 전까지
  서버에서 강제로 무효화할 수 없습니다. 현재 로그아웃은 Refresh Token만 삭제하며
  Access Token은 클라이언트 쿠키 삭제(만료)에 의존합니다.
- **T10a 적용 효과**: Refresh Token 회전으로 탈취된 Refresh Token의 재사용 창이 크게 줄었습니다.

## 2. 옵션 비교

### 옵션 A — 도입 안 함 (현행 유지)
- **방식**: 단기 만료(15분) + Refresh Token 회전(T10a)으로 위험을 관리.
- **장점**: 추가 인프라 비용 0. 매 요청 추가 조회 없음(성능 영향 없음). 운영 복잡도 증가 없음.
- **단점**: 강제 로그아웃/즉시 차단 불가. 탈취된 Access Token은 최대 15분간 유효.
- **적합 상황**: 즉시 강제 로그아웃 요건이 없고, 15분 노출 창이 위협 모델상 수용 가능할 때.

### 옵션 B — DB 블록리스트
- **방식**: JWT에 `jti`(토큰 고유 식별자) 클레임 추가 → 폐기 테이블에 jti 적재
  → `JwtAuthenticationFilter` 단계에서 폐기 여부 DB 조회.
- **장점**: 신규 인프라 도입 불필요(기존 Oracle 사용). 즉시 무효화 가능.
- **단점**: **매 인증 요청마다 DB 조회** 발생 → 지연·부하 증가. 만료 토큰 정리(GC) 배치 필요.
- **적합 상황**: 강제 로그아웃 요건은 있으나 별도 캐시 인프라 도입이 어려울 때.

### 옵션 C — Redis 블록리스트
- **방식**: Redis에 폐기 jti를 저장하고 **TTL = 토큰 잔여 수명**으로 자동 만료.
  필터 단계에서 Redis 조회.
- **장점**: 즉시 무효화 + 빠른 조회. TTL로 자동 정리되어 GC 배치 불필요.
- **단점**: **Redis 인프라 도입 필요**(운영·HA·모니터링 비용). 신규 의존성.
- **적합 상황**: 강제 로그아웃이 상시 요건이고 트래픽 규모가 DB 조회로 감당 어려울 때.

## 3. 권고

- 운영 트래픽 규모와 위협 모델이 확정되기 전까지 **옵션 A(도입 안 함)를 유지**합니다.
  단기 만료(15분) + Refresh 회전(T10a)으로 사실상 충분하며 추가 인프라 비용이 0입니다.
- **강제 로그아웃(즉시 차단) 요건이 실제로 발생하면 옵션 C(Redis 블록리스트)를 채택**합니다.
  TTL 기반 자동 정리와 빠른 조회로 운영 부담이 가장 작습니다. (DB 블록리스트는
  매 요청 조회 부하 때문에 중간 단계로만 검토.)
