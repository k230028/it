# COUNCIL-027 실제 연동 종단 검증 계획

## 목적과 범위

로컬 프론트엔드(`http://localhost:3000`), `local-ext` 백엔드(`http://localhost:28080`), 로컬 Oracle을 실제로 연결해 정보화실무협의회 `/info/council`의 전체 상태 전이를 검증한다. 일반 Playwright E2E는 API 목을 사용하는 회귀 테스트이므로 이 검증과 섞지 않는다. 개발계 배포와 운영 데이터 검증은 범위에 포함하지 않는다.

검증 대상은 사업 협의회 심의유형 03 한 건이다. 정보보호관리자 경계는 같은 실행에서 03 조회·관리 거부를 확인하고, 별도의 심의유형 04 데이터가 준비된 경우에만 허용 경계까지 확장한다.

## 실행 전 게이트

다음을 모두 충족한 뒤 실제 검증을 시작한다.

1. 프론트엔드와 백엔드를 각각 3000, 28080 포트에서 실행하고 백엔드는 `local-ext` 프로파일과 개발용 사용자 전환을 활성화한다.
2. 로컬 전용 사업 1건을 `BPROJA.IT_PTL_STS_TC='09'` 상태로 준비한다. `BPROJM.DEL_YN='N'`, 자기 참조 상태행(`CNCD_RFR_NO=ABUS_MNG_NO`) 존재, 해당 사업·순번의 활성 `BASCTM` 부재를 함께 확인한다.
3. 사업명에는 로컬 검증용임을 식별할 표식을 두고 주관부서에 활성 일반사용자가 존재하는지 확인한다.
4. 검증 직전 로컬 PDB 백업 또는 되돌릴 수 있는 스냅샷을 만든다. 완료 상태 13은 취소 API 대상이 아니므로 전체 흐름을 끝낸 뒤에는 스냅샷 복원이 가장 안전한 정리 방법이다.
5. 아래 역할표를 로컬 비공개 메모에 채운다. 사번과 이름은 저장소 문서, 테스트 코드, 터미널 출력에 남기지 않는다.

| 역할 변수                 | 조건                                   | 사용 구간                              |
| ------------------------- | -------------------------------------- | -------------------------------------- |
| `COUNCIL_OWNER_ENO`       | 대상 사업 주관부서의 활성 사용자       | 신청, 검토표 작성, Q&A 답변, 상신·회수 |
| `COUNCIL_APPROVER_ENO`    | 결재 가능한 팀장                       | 타당성검토표 반려·승인                 |
| `COUNCIL_ADMIN_ENO`       | `ITPAD001`                             | 위원·일정·개최·결과서·콜백 관리        |
| `COUNCIL_INFOSEC_ENO`     | `ITPAD002`                             | 심의유형 03 관리 거부 확인             |
| `COUNCIL_EVALUATOR_A_ENO` | 활성 사용자, 위원 유형 01 또는 02      | 일정 응답, 6개 평가, 결과 확인         |
| `COUNCIL_EVALUATOR_B_ENO` | A와 다른 활성 사용자                   | 다중 위원 완료 조건과 결과 확인        |
| `COUNCIL_OUTSIDER_ENO`    | 주관부서·관리자·배정위원이 아닌 사용자 | 상세·쓰기 403 확인                     |

## 실행 순서와 합격 기준

각 역할은 별도 브라우저 컨텍스트에서 `/sso/business`로 로컬 SSO를 만든 뒤 `POST /api/auth/dev/switch-user`로 전환한다. 역할 전환 후 `/api/auth/me`와 화면 헤더를 모두 확인해 쿠키와 화면 상태가 같은 사용자를 가리키는지 확인한다.

| 순서 | 수행                                                                                 | 합격 기준                                                             |
| ---: | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
|    1 | OWNER가 `/info/council`에서 대상 사업의 유형 03 협의회를 신청                        | 201, 상태 01, 사업 상태 45, 새 `ASCT-*` 식별자 확보                   |
|    2 | OUTSIDER와 INFOSEC가 상세·수정·개최준비 URL/API에 접근                               | 유형 03 관리 요청은 403, 데이터 변경 없음                             |
|    3 | OWNER 컨텍스트 A/B가 같은 작성중 검토표를 연 뒤 A가 작성완료, B가 낡은 화면에서 저장 | A는 02 전이, B는 409와 재조회 안내, 저장 내용 역행 없음               |
|    4 | OWNER가 MFA 후 결재 상신하고 곧바로 공통 결재 화면에서 회수                          | 03→02, 신청서는 회수, 재상신 가능                                     |
|    5 | OWNER가 재상신하고 APPROVER가 반려                                                   | 03→01, 기존 입력을 불러와 수정 가능                                   |
|    6 | OWNER가 수정·작성완료·재상신하고 APPROVER가 승인                                     | 03→04, 작성 화면 쓰기 차단                                            |
|    7 | ADMIN이 개최준비로 전이하고 평가위원 2명을 확정                                      | 04→05, 위원만 해당 협의회를 조회                                      |
|    8 | 위원들이 서로 다른 브라우저에서 일정 응답, ADMIN이 일정 확정·개최                    | 05→06→07, 새로고침·재방문 후 선택과 상태 유지                         |
|    9 | 위원 A가 평가 5개만 입력한 상태에서 완료 시도 후 6개를 채우고, 위원 B도 6개 입력     | 미완료 시 차단, 전원 완료 뒤 08 및 결과서 단계 진입 가능              |
|   10 | ADMIN이 결과서를 저장·확정하고 위원 2명이 각각 결과 확인                             | 09→10→11, 확정 뒤 결과서 PUT은 409                                    |
|   11 | ADMIN이 결과 결재를 상신하고 결재선이 승인                                           | 11→12→13, 완료 후 평가·결과·일정 쓰기 요청은 409                      |
|   12 | 각 단계에서 새로고침, 목록 이탈 후 재진입, 직접 URL 진입을 반복                      | 서버 상태와 화면 상태가 일치하고 빈 화면·이전 성공 데이터 오인이 없음 |

반려와 회수는 같은 협의회에서 순서대로 수행한다. 공통 결재 화면의 처리가 협의회 콜백까지 반영되는지 확인하며, 관리자용 `PATCH /api/council/{id}/approval`을 직접 호출해 정상 흐름을 대신하지 않는다. 콜백 자체 권한의 별도 확인에만 관리자 API 호출을 사용한다.

## 데이터 확인과 정리

실행 중에는 화면 결과와 함께 다음 원장만 읽기 전용으로 대조한다.

- 협의회·검토표: `TPRMPP_BASCTM`, `TPRMPP_BPOVWM`, `TPRMPP_BCHKLM`, `TPRMPP_BPERFM`
- 위원·일정·평가: `TPRMPP_BCMMTM`, `TPRMPP_BSCHDM`, `TPRMPP_BEVALM`
- 질의·결과: `TPRMPP_BPQNAM`, `TPRMPP_BMQNAM`, `TPRMPP_BRSLTM`
- 사업 상태: `TPRMPP_BPROJA`
- 결재: 생성된 `APF-*` 번호로 공통 결재 원장과 협의회 원본 연결을 조회

상태 01 또는 02에서 중단하면 화면의 신청 취소 API를 사용해 `BASCTM.DEL_YN='Y'`와 사업 상태 09 복원을 확인한다. 결재 이력이 생겼거나 상태 03 이상으로 진행한 실행은 개별 테이블을 수동 삭제하지 않는다. 완료 후 사전 PDB 스냅샷을 복원하고, 복원할 수 없다면 로컬 검증용 표식과 생성된 `ASCT-*`, `APF-*`를 기록해 데이터를 보존한다.

## 증적과 완료 판정

실행 결과는 `docs/superpowers/evidence/` 아래 날짜가 포함된 Markdown으로 남긴다. 역할은 사번 대신 OWNER, ADMIN처럼 표기하고 다음 항목을 기록한다.

- 실행한 프론트엔드·백엔드 Git 커밋과 로컬 프로파일
- 전용 사업 키와 협의회·결재 식별자(로컬 증적에만 기록)
- 위 표 12개 시나리오의 PASS/FAIL, HTTP 상태, 화면 캡처 경로
- DB 상태 전이 대조 결과와 정리 또는 스냅샷 복원 결과
- 재현 가능한 결함, 미검증 범위, 후속 TASK ID

12개 시나리오와 데이터 정리를 모두 통과해야 COUNCIL-027을 완료 처리한다. 역할 또는 신청 대상 데이터가 없으면 준비 실패가 아니라 실행 대기로 유지하고 부족한 게이트를 TASK에 적는다.
