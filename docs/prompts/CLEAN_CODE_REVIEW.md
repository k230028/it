## 기본 지침
 - 이 작업은 모든 계획과 실행(cli 명령어 포함)에 대해 확인받지 않고 작업을 진행한다.
 - 로버트 마틴(Robert C. Martin)의 『Clean Code』를 기준으로 코드베이스 전반의 품질을 **진단**하는 작업이다. 진단 중에는 **비즈니스 로직(코드 자체)을 절대 수정하지 않는다.** 수정은 보고서 확정 후 별도 작업으로 분리한다.
 - 속도보다 정확도가 중요한 작업이다. 에이전트 탐지 결과를 그대로 믿지 않고, CRITICAL/HIGH 판정은 반드시 직접 교차 검증 후 보고서에 싣는다.
 - [Task 0]부터 [Task 4]까지 순서대로 진행하고, 각 Task 내에서 지정된 에이전트를 병렬로 활용한다.
 - 모든 Task를 완료한 후에는 [검증] 단계를 실행하여 보고서의 근거가 실제 코드와 일치하는지 확인한다.
 - Reference: 모든 작업의 최우선 순위는 루트의 CLAUDE.md에 정의된 규범을 따름 (한글 주석 원칙, 800줄 파일 상한 등 프로젝트 자체 규약도 진단 기준에 포함)

### 산출물
 - 보고서: `C:\it\docs\clean-code-review-YYYY-MM-DD.md` (실행일 날짜)
 - 직전 보고서: `docs/clean-code-review-*.md` 중 최신 파일 — 델타 비교의 기준선
 - 후속 과제: **모든 개선사항(CRITICAL~LOW 및 개선 로드맵 전 항목)을 `TASK.md`에 등록**

### 진단 제외 범위
 - `node_modules`, `.nuxt`, `build`, `dist` 등 빌드 산출물
 - `it_database/migrations/` (Flyway 체크섬 추적 대상 — 수정 금지 영역이므로 진단 대상에서도 제외)

    - 이전 CRITICAL/HIGH 발견 사항 목록 → 이번 진단에서 "해결/잔존/신규" 델타 판정에 사용

## [Task 1: 병렬 진단]

### 에이전트 (병렬 실행)
다음 3개 에이전트를 병렬 서브에이전트로 실행한다. 각 에이전트에게 Task 0의 대형 파일 목록을 우선 조사 대상으로 지정한다.

| 에이전트 | 담당 범위 | 진단 관점 (Clean Code 장 기준) |
|---------|---------|---------|
| `java-reviewer` | `it_backend/src/main` | 이름(2장)·함수(3장: 길이/인자 수/플래그 인자)·주석(4장)·오류 처리(7장: 예외 삼킴/광범위 catch)·클래스 SRP(10장)·DRY·냄새(17장: 매직 넘버/죽은 코드) |
| `typescript-reviewer` | `it_frontend/app`, `it_frontend/server` | 위와 동일 + 타입 안전(`any`/`eslint-disable`/`ts-ignore` 우회)·거대 컴포넌트/composable·페이지 간 copy-paste·`console.log` 잔존·`v-html` 새니타이징 |
| `code-reviewer` | 양쪽 테스트 + 아키텍처 경계 | 단위 테스트(9장: F.I.R.S.T/AAA/테스트 비대화)·계층 규율(11장: Controller→Repository 직접 호출/Entity 노출/의존 방향)·커버리지 게이트 실효성·`TASK.md` 자인 부채와의 대조 |

### 에이전트 공통 프롬프트 요구사항
 - 발견 사항은 **파일:라인 + 짧은 코드 인용(증거)** 필수. 추측 금지.
 - 심각도 4단계: CRITICAL(실사용자 영향 버그·보안) / HIGH(버그 위험·규약 위반) / MEDIUM(유지보수성) / LOW(스타일)
 - 전역 패턴 스캔 병행: `catch (Exception`, `printStackTrace`, `System.out`, `@Valid` 누락, `any` + `eslint-disable`, TODO/FIXME, 매직 넘버
 - 대형 파일만이 아니라 중소형 파일 표본 2~3개도 함께 읽어 "전반적 경향 vs 국소 문제"를 구분
 - 강점도 실제 확인된 것만 보고 (좋은 선례가 사내에 있으면 반례로 명시 — 예: 잘 분리된 테스트 파일)
 - 한글 주석은 프로젝트 규약이므로 문제로 보고하지 않음

## [Task 2: 교차 검증 (필수)]

### 절차 (직접 실행)
 1. 에이전트가 보고한 **CRITICAL 전건 + HIGH 중 버그성 판정**을 Grep/Read로 직접 재확인한다.
    - 필드명 불일치·오타류: 타입 정의, 백엔드 DTO, 실제 사용처를 모두 대조
    - 중복 로직: 두 위치의 코드를 실제로 비교
    - 규약 위반: 같은 규약을 지키는 다른 파일이 있는지 확인 (산발적 누락 vs 의도적 패턴 구분)
 2. 검증 중 에이전트가 놓친 동일 패턴의 추가 발생 위치가 있으면 보고서에 추가한다.
 3. 검증 실패(오탐) 항목은 보고서에서 제외하고, 제외 사유를 기록한다.

### 규칙
 - `as any` 캐스팅 뒤에 숨은 필드 접근은 반드시 원 타입 정의와 대조한다. (2026-07-07 진단에서 `ornYn`/`odnYn` 오타를 이 방법으로 확정하고, 에이전트가 놓친 3번째 발생 위치까지 발견한 선례)

## [Task 3: 보고서 작성]

### 보고서 구조 (직전 보고서와 동일 골격 유지 — 회차 간 비교 가능성 확보)
 1. **메타**: 진단일, 기준, 범위(파일 수), 방법
 2. **종합 평가**: 영역별 점수표 (백엔드 / 프론트엔드 / 테스트 품질 / 아키텍처 경계, 각 5점 만점) + 한 줄 결론
 3. **직전 대비 델타**: 해결됨 / 잔존 / 신규 발견 (직전 보고서의 CRITICAL·HIGH 기준. 최초 회차는 생략)
 4. **CRITICAL 발견** (Task 2 검증 완료 건만)
 5. **Clean Code 원칙별 진단**: 함수(3장) / 클래스·SRP(10장) / DRY / 오류 처리(7장) / 타입 안전 / 테스트(9장) / 아키텍처(11장) / 기타 냄새(17장)
 6. **강점 요약** (실제 확인된 것만)
 7. **개선 로드맵**: 우선순위·시기·근거 표
 8. **부록**: 주요 참고 파일 경로

### 점수 기준 (회차 간 일관성 유지)
 - 5.0: 규약·원칙 위반이 사실상 없음
 - 4.0: 국소적 위반만 존재, 구조적 문제 없음
 - 3.0: 구조적 문제(God Class, 중복 관행 등)가 특정 도메인에 집중
 - 2.0: 구조적 문제가 코드베이스 전반에 확산
 - 1.0: 기본 위생(예외 삼킴, 죽은 코드, 계층 붕괴) 실패

## [Task 4: 후속 조치 등록]

### 절차
 1. **모든 개선사항을 `TASK.md`에 등록한다** — 심각도(CRITICAL/HIGH/MEDIUM/LOW)와 무관하게 보고서의 발견 사항 및 개선 로드맵 전 항목이 대상이다.
    - 등록 형식: `TASK.md`의 기존 항목 형식을 따르고, 심각도를 우선순위(🔴High/🟡Medium/🟢Low)로 매핑한다 (CRITICAL·HIGH→🔴, MEDIUM→🟡, LOW→🟢).
    - 각 항목에 출처 보고서 경로(`docs/clean-code-review-YYYY-MM-DD.md`)와 근거 파일:라인을 함께 기록한다.
    - 중복 확인 필수: 이미 `TASK.md`에 자인된 부채(예: BE-02, BE-04)는 재등록하지 않고, 해당 항목에 이번 진단 결과를 근거로 우선순위 재확인 메모만 추가한다.
 2. CRITICAL 발견: `TASK.md` 등록에 더해, 즉시 수정 가능하도록 별도 수정 태스크로 스핀오프하거나 사용자에게 수정 착수 여부를 보고서와 함께 제시한다.
 3. 이전 보고서의 발견 사항 중 이번에 "해결됨"으로 확인된 항목이 `TASK.md`에 남아 있으면 `[Done]` 처리하고 조치 일자를 기록한다.
 4. 문서 불일치 발견(예: CLAUDE.md의 낡은 기록)은 `REVIEW.md` 워크플로우의 처리 대상으로 메모한다.

## [검증: Verification Loop]

### 절차
 1. 보고서의 모든 파일:라인 인용이 실제 코드와 일치하는지 표본 점검한다. (최소: CRITICAL 전건 + HIGH 절반)
 2. 점수가 직전 회차 대비 ±1.0 이상 변동한 영역은 근거(해결/신규 발견 목록)가 델타 섹션에 설명되어 있는지 확인한다.
 3. 보고서의 발견 사항·개선 로드맵 전 항목이 `TASK.md`에 등록(또는 기존 항목 메모)되었는지 대조한다 — 누락 항목이 없어야 완료.
 4. 누락 또는 불일치가 발견되면 해당 Task만 재실행한다.
 5. 완료 후 보고서 경로를 사용자에게 전달한다. 커밋은 사용자 요청 시에만 수행한다.
