#### 3.7.1 `MAX VALUE` — 39건 (표기 아티팩트 유력, 조치 불필요)

| 운영 표기 | 로컬 실제값 | 건수 |
| --- | --- | ---: |
| `999999999999999000` | `999999999999999999` (9 × 18) | 37 |
| `9.99999999999999E21` | `9999999999999999999999` (9 × 22) | 2 (`SQ_TPRMPP_CLOGNH_1`, `SQ_TPRMPP_CRTOKM_1`) |

**실제 차이가 아니라 운영 기준 파일의 정밀도 손실로 판단합니다.** 근거:

- 로컬 값을 **15 유효자리에서 절삭**하면 운영 표기와 정확히 일치합니다.
  `999999999999999999` → `999999999999999` × 10³ = `999999999999999000`,
  `9999999999999999999999` → `999999999999999` × 10⁷ = `9.99999999999999E21`.
  서로 다른 두 값이 **같은 규칙 하나로** 설명됩니다.
- **15자리 이하인 `MAX VALUE`는 전부 정확히 일치합니다** — `9999`, `9999999`, `99999999`, `999999999`.
  즉 15자리를 넘는 값만, 그것도 전부 어긋납니다. 실제 설정 차이라면 나타날 수 없는 분포입니다.
- 15 유효자리는 스프레드시트 숫자 저장의 한계값이며, 지수 표기(`9.99999999999999E21`)도 같은 원인을
  가리킵니다(1.3).

`999999999999999000`이라는 값을 DBA가 의도적으로 지정했을 개연성은 낮습니다. 확인이 필요하면 5.4의
쿼리로 운영 실제값을 조회하면 됩니다. 실제로 `999999999999999000`이었다면 그때 정렬 대상이 됩니다.

`SQ_TPRMPP_BASCTM_1`, `BBUGTM_1`, `BCONTM_1`, `BCOSTM_1`, `BDELIM_1`, `BESTIM_1`, `BGDOCM_1`,
`BITEMM_1`, `BPAYMM_1`, `BPLANM_1`, `BPROJM_1`, `BRDOCM_1`, `BTERMM_1`, `CBLBCM_1`


(`it_backend/.../domain/budget/project/service/ProjectService.java:121`,
`.../repository/ProjectRepository.java:143` — `SELECT SQ_TPRMPP_BPROJM_1.NEXTVAL FROM DUAL`)

따라서 `9999` 도달 시 동작이 갈립니다.

| | 운영 (`CYCLE`) | 로컬 (`NOCYCLE`) |
| --- | --- | --- |
| `9999` 다음 채번 | `1`로 순환 → `PRJ-2027-0001` | **`ORA-08004`로 채번 실패** |

즉 **로컬에서만 재현되는 장애가 아니라, 로컬에서만 발생하는 장애**입니다. 4자리 포맷을 전제로 한 설계와도
`NOCYCLE` 쪽이 어긋납니다(순환하지 않으면 `10000`이 되어 `PRJ-2026-10000`처럼 자릿수가 깨집니다).

**긴급도는 낮습니다.** 현재 로컬 카운터는 최대 474(`SQ_TPRMPP_BTERMM_1`)로 `9999`와는 거리가 멉니다.
다만 운영·로컬의 설정 자체가 다르므로 정렬 대상입니다(5.3).

주의: 순환은 같은 연도 안에서 10,000건을 넘길 때 관리번호 중복을 만듭니다. 이는 운영 설계에 내재한
성질이고 본 Gap 분석의 범위를 넘으므로, 정렬은 운영 설정을 그대로 따르는 선에서 합니다.

#### 3.7.3 `START WITH` — 50건 (스키마 Gap 아님, 미집계)

운영은 61개 전부 `1`이고, 로컬은 50개가 `3` ~ `3,874` 범위입니다.
`DBMS_METADATA`가 `CREATE SEQUENCE`를 렌더링할 때 `START WITH`에 **현재 카운터(`LAST_NUMBER`)** 를 넣기
때문이며, 로컬 값은 개발 중 채번이 진행된 흔적입니다(2026-08-01 회차에서도 같은 판정).

운영이 전부 `1`인 것은 1.3의 정황과 함께 운영 기준 파일이 정의서임을 시사합니다.
어느 쪽이든 **스키마 차이가 아니므로 조치 대상이 아닙니다.**

### 3.8 동작상 동일한 표기 차이 — 32건 (조치 불필요·정렬 불가)

로컬에만 `DEFAULT NULL`이 명시된 컬럼이 32개 있으며 **2026-08-01 회차와 동일한 목록**입니다.
Oracle에서 `DEFAULT NULL`은 기본값 미지정과 동작이 같아 Gap으로 집계하지 않았습니다.

조치하지 않는 근거는 2026-08-01 회차에서 확정했고 이번에도 변동이 없습니다 — 요약하면
(1) `MODIFY (컬럼 DEFAULT NULL)`은 `DATA_DEFAULT`를 비우지 못하고 오히려 이 잔재를 만드는 구문이며,
(2) Oracle에는 `DROP DEFAULT` 구문이 없어 테이블 재생성 외에 제거 수단이 없고,
(3) `table.txt`의 `Default Value` 열에 `NULL` 표기가 한 건도 없어 **운영이 같은 잔재를 갖고 있는지 자체를
확인할 수 없습니다.**

`BCONTM.LST_YN`, `BDELIM.LST_YN`/`TASK_DBR_OMT_YN`, `BESTIM.LST_YN`,
`BITEMM.ITR_INFR_YN`/`SECT_SYS_UTZ_YN`/`LST_YN`, `BPAYMM.LST_YN`, `BPROJM.DPL_YN`/`ODN_YN`,
`CAPPLM.DCD_REQ_DTM`, `CAUTHI.USE_YN`, `CBLBCM` 7개, `CBLBMM` 6개, `CCMMTM` 2개,
`CINFMM.INQ_YN`/`RE_TRY_NOT`, `CMENUD.USE_YN`, `CMENUM.HID_YN`, `CROLEI.USE_YN`

## 4. 이번 비교로 확인할 수 없는 항목

운영 기준 파일에 정보가 없어 판정 대상에서 제외했습니다.

- **문자 길이 semantics (`CHAR` / `BYTE`)** — 운영은 길이 숫자만 제공합니다.
  로컬은 `VARCHAR2` 1,092개 중 **799개가 `CHAR`, 293개가 `BYTE`**(세션 기본값이라 미표기)이며
  **51개 테이블이 두 방식을 혼용**합니다. 직전 회차의 49개에서 2개 늘었는데, `V20260806_002`가 추가한
  `CMENUM.IMK_NM`·`CMENUL.IMK_NM`이 `BYTE`(미표기)로 생성돼 두 테이블이 새로 혼용에 들어갔습니다.
  멀티바이트 저장 한계가 달라질 수 있어 별도 확인이 필요합니다.
- **인덱스, FK, CHECK 제약, UNIQUE 제약** — 운영은 PK 여부만 제공합니다.
  로컬에는 인덱스 66개와 CHECK 제약 15개(그중 `CK_*_DEL_YN` 계열 6개)가 존재합니다.
- **시퀀스 `CACHE` / `ORDER` / `KEEP` / `SCALE`** — 운영 시퀀스 파일에 열이 없습니다.
  로컬은 61개 중 32개가 `CACHE 20`, 29개가 `NOCACHE`로 갈려 있어 운영과의 일치 여부를 확인할 수 없습니다.
- **뷰, 트리거, 프로시저** — 운영 기준 파일에 없습니다. 로컬에는 뷰 1개가 정의되어 있습니다.
- **가상 컬럼 / INVISIBLE 컬럼** — 로컬에는 0건이며 운영 여부는 확인 불가입니다.
- **컬럼 순서·시퀀스 `MAX VALUE`·`START WITH`의 운영 실제값** — 1.3의 이유로 기준 파일 값이 운영 DB의
  실제 상태와 다를 수 있습니다. 5.4의 쿼리로 확인해야 합니다.

## 5. 권고 조치

방향이 서로 다른 3건입니다.

### 5.1 운영 반영 요청 — `TPRMPP_CMENUL.IMK_NM` (3.3)

로컬을 되돌리는 것이 아니라 **운영 변경로그 테이블에 컬럼을 추가**해야 합니다.
기본 테이블 `CMENUM`에는 이미 반영되어 있으므로 짝을 맞추는 작업입니다.

```sql
ALTER TABLE TPRMPP_CMENUL ADD (IMK_NM VARCHAR2(100));
COMMENT ON COLUMN TPRMPP_CMENUL.IMK_NM IS '이미지키명';
```

기존 행은 아이콘 변경 이력이 없으므로 `NULL`로 둡니다(`V20260806_002`의 판단과 동일).
반영 후 `meta/table.txt` 재추출이 필요합니다.

**앱 측 조치(2026-08-13)** — `IMK_NM`이 없는 환경에서 메뉴 조회가 `ORA-00904`로 죽지 않도록 백엔드에
내성을 넣었습니다(`docs/superpowers/specs/2026-08-13-menu-icon-missing-column-fallback-design.md`).
컬럼이 없으면 조회 select에서 빼고 `MenuIconDefaults` 스냅샷으로 아이콘을 채웁니다.

**이 조치는 위 DDL 반영을 대체하지 않습니다.** 내성이 걸린 범위는 조회뿐이며, 아이콘 편집(`CMENUM`)과
아이콘 변경 이력(`CMENUL`)은 컬럼이 있어야 동작합니다.

### 5.2 운영 반영 요청 — `TPRMPP_CINFMM.INFM_SD_STS_C` 기본값 (3.5)

```sql
ALTER TABLE TPRMPP_CINFMM MODIFY (INFM_SD_STS_C DEFAULT '01');
```

기존 행의 값은 건드리지 않습니다. 앱이 모든 INSERT에서 발송상태를 명시하므로 반영 여부와 무관하게
현재 동작은 바뀌지 않으며, 도달 불가능한 코드가 향후 유입되는 것을 막는 예방 조치입니다.

**운영 측이 `'10'`을 정본으로 유지하기로 결정한다면** 반대로 로컬을 되돌리고
`Cinfmm.DISPATCH_*` 상수와 `NotificationDispatcherRouter` 분기에 `'10'`을 추가해야 합니다.
`V20260808_001`의 되돌리기 구문은 해당 스크립트 주석에 있습니다.

### 5.3 로컬 정렬 — 시퀀스 `CYCLE` 14건 (3.7.2)

운영 설정(`CYCLE`)을 정본으로 삼아 로컬 14개 시퀀스를 순환으로 맞춥니다.
**적용된 마이그레이션은 Flyway 체크섬 대상이므로 새 버전 스크립트로 추가합니다.**

```sql
-- it_database/migrations/V2026MMDD_NNN__AlignSequenceCycleWithProduction.sql (미작성)
ALTER SEQUENCE SQ_TPRMPP_BPROJM_1 MAXVALUE 9999 CYCLE;
-- ... 14개 시퀀스 동일 (BASCTM / BBUGTM / BCONTM / BCOSTM / BDELIM / BESTIM / BGDOCM
--     / BITEMM / BPAYMM / BPLANM / BPROJM / BRDOCM / BTERMM / CBLBCM)
```

주의사항:

- 로컬 `MAXVALUE`는 이미 `9999`이므로 `CYCLE`만 지정해도 되지만, 순환 상한이 무엇인지 스크립트에서
  드러나도록 `MAXVALUE 9999`를 함께 적었습니다. 값은 바뀌지 않습니다.
- **`ALL_SEQUENCES.CYCLE_FLAG`를 확인해 `'N'`인 경우에만 실행하는 PL/SQL 블록**으로 감싸 재실행에
  안전하게 만듭니다(`V20260801_001`의 선례).
- `dev`/`prod`는 `spring.flyway.enabled=false`이므로 DBA가 별도 적용합니다.
  운영이 이미 `CYCLE`이면 운영 적용은 불필요합니다.
- 애플리케이션 변경은 필요하지 않습니다. 채번 코드는 `NEXTVAL` 결과를 `%04d`로 포맷할 뿐이라
  순환 여부를 알지 못합니다.

이 스크립트는 **본 리포트에서 작성하지 않았습니다.** 3.7.2의 순환 시 관리번호 중복 성질을 운영 측과
확인한 뒤 적용하는 편이 안전하다고 보기 때문입니다.

### 5.4 운영 실제값 확인 (판단 유보 항목 해소용)

3.4(컬럼 순서)와 3.7.1(`MAX VALUE`)은 운영 기준 파일이 정의서일 가능성 때문에 판정을 유보했습니다.
운영 DB에서 아래를 조회하면 확정됩니다.

```sql
-- 컬럼 실제 위치
SELECT table_name, column_name, column_id
  FROM all_tab_columns
 WHERE owner = 'ITPOWN'
   AND (table_name, column_name) IN (('TPRMPP_CFILEM','APG_FL_SZ'), ('TPRMPP_CMENUM','IMK_NM'))
 ORDER BY table_name, column_id;

-- 시퀀스 실제 MAXVALUE / CYCLE / LAST_NUMBER
SELECT sequence_name, max_value, cycle_flag, last_number
  FROM all_sequences
 WHERE sequence_owner = 'ITPOWN'
 ORDER BY sequence_name;
```

`column_id`가 각각 15·17이면 3.4의 Gap 23건은 소멸합니다.
`max_value`가 `999999999999999999`·`9999999999999999999999`면 3.7.1의 Gap 39건은 소멸합니다.
